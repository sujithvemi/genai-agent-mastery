PART V · CHAPTER 26

Communication and durable execution

An agent run is a long, multi-step process that must survive crashes, deployments and waits for people, and must never perform an effect twice or lose one. That is exactly the problem messaging and workflow systems were built for. This chapter covers the communication patterns, the delivery guarantees that actually hold, the outbox and saga patterns, and durable execution engines, and shows how an agent framework's checkpoints fit among them.

26.1Synchronous and asynchronous

Generic Synchronous calls couple caller and callee in time: both must be up, and the caller waits. Asynchronous messaging decouples them: the producer hands work to a durable channel and moves on. Agents need both. Tool calls inside a step are usually synchronous (the model needs the result to continue); the run as a whole, approvals, notifications and background agents are asynchronous.

26.3Delivery guarantees

Generic Networks force a choice: at most once (never redelivered, may be lost) or at least once (never lost, may be duplicated). The first prediction question: "exactly once" in a broker means exactly-once within that system, for example a message processed once into the broker's own state. Across a broker and an external side effect, you get at-least-once delivery plus an idempotent consumer, which together give effectively-once effects. For agents, that means every effectful tool call carries an idempotency key the target system honours, and a duplicate is detected before the effect, not after (Chapter 25).

26.4The outbox and the evidence-first write

Generic The second prediction question is the dual-write problem: two writes to two systems cannot be atomic, so a crash between them leaves them inconsistent (the row exists, the event never went out, or the reverse). The transactional outbox fixes it: write the business change and the outgoing message to the same database in one transaction, and let a relay publish the message afterwards, at least once.

Reference build ARB's evidence plane faces the same problem between the decision record and the effect, and solves it with ordering rather than a shared transaction: the decision is recorded before the effect, the action record after, an evidence failure before the effect refuses the action, and an effect whose action record fails is reversed (Chapter 22). The principle is the outbox's: never let the world change in a way your records cannot account for.

26.5Sagas and compensation

Generic A long business process that spans systems cannot hold one transaction. A saga runs it as steps, each with a compensating action that semantically undoes it (refund reverses charge; cancel reverses booking). Orchestrated sagas have a coordinator; choreographed ones react to events. An agent that performs several effects in one run is a saga whether or not it is designed as one; design the compensations deliberately, record each step's outcome, and know which effects cannot be compensated (an email sent) so they are placed last and gated hardest.

26.6Durable execution

Generic Durable execution engines (Temporal, AWS Step Functions, Google Workflows, Azure Durable Functions, and libraries such as DBOS and Restate) let you write a long process as ordinary code that survives crashes: the engine records each step's result in an event history and, after a failure, replays the code, skipping steps already done.

The third prediction question: replay only works if the workflow code makes the same decisions given the same history, so it must be deterministic. Anything non-deterministic (time, randomness, network calls and therefore model calls and tool calls) runs as an activity, whose result is recorded once and replayed from history thereafter. That fits agents well: each model call and tool call is an activity with retries and timeouts; human approvals are signals or timers that can wait for days without a process running; and the history doubles as a step-by-step record.

26.7pm-agent's checkpoints and interrupts

pm-agent pm-agent uses the first option. Its planning graph runs on LangGraph behind the Orchestrator seam, with a Postgres checkpointer (P4-S0) so state survives restarts; a governed write is a graph interrupt that parks the run until an approver answers; cancellation sets a token that "stops the graph at the next node boundary, leaving consistent state" with a terminal evidence event (pm-agent's safe-interruption control). Its design notes record the alternative considered: "Temporal vs graph checkpoints (operational weight vs guaranteed durability — defer)". That is a sound default for a run of seconds to minutes; it becomes the wrong default when runs last days, span many effects, or need guaranteed timers, at which point the effectful steps should move into a workflow engine as activities.

26.8Event-driven agents

Generic Background agents start from events rather than users: a new ticket, a changed record, a schedule, a data arrival (GEAP supports BigQuery and Pub/Sub triggers; Foundry has Routines; Amazon Quick and Agentforce have scheduled agents). Three design points: the event's producer is not a principal, so the agent acts under a service identity whose authority must be explicitly granted and narrow; events arrive at least once, so the agent's effects need idempotency keys derived from the event id; and a flood of events needs back-pressure and per-source budgets, or one noisy system exhausts the model quota for everyone (Chapter 29).

Generic How to choose. A queue moves work; a log lets you replay it; a workflow service remembers where a process is. If an agent run can pause for a person, take more than a few minutes, or perform more than one effect, the run belongs in something that remembers, and the effect steps belong inside it as activities. Which one is a coupling decision more than a feature decision: an engine you run yourself (Temporal) moves between clouds; a cloud's workflow service integrates with its identity, quotas and console but stays on that cloud.

Check before quoting

Maximum durations, history size limits and pricing units differ by service and change: Step Functions Standard and Express differ by orders of magnitude in duration and price; Lambda durable functions and the Azure Durable Task extension for Agent Framework are recent. Check the current limits page before you put a number in a design.

26.11In the room

In the room
  • "What happens if the server restarts halfway through?" "Every step the agent completes is recorded before the next starts. After a restart, it carries on from the last recorded step rather than starting again, and anything that changes your systems carries a key so it cannot happen twice."
  • "Can it wait for my approval over the weekend?" "Yes. A waiting run costs nothing while it waits; nothing is running. When you approve, the run picks up where it parked, and the approval itself is part of the record."
  • "Why not just use a message queue?" "A queue delivers a message at least once. It does not remember that step three of seven is done. For agent work that pauses and has several effects, we need both."
