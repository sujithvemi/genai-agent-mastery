PART VI · CHAPTER 40

Maintenance and evolution

An agent that nobody changes still changes: its model is updated or retired, its framework moves on, its knowledge goes stale, its users ask new things and its adversaries learn. Maintenance is therefore planned work with a budget, not a residue. This chapter covers the sources of change, how to absorb each without losing control, how to recertify agents that have not changed, and how to retire one properly.

40.1Agents decay without anyone touching them

Generic Sculley et al.'s "Hidden Technical Debt in Machine Learning Systems" (2015) warned that ML systems accumulate debt through entanglement, hidden feedback loops and dependencies on external data. Agents add more: a dependency on a model you do not control, on prompts whose behaviour shifts with the model, on tools other teams own, and on content that ages. The first 2026 lessons are already in: Microsoft moved Semantic Kernel and AutoGen to maintenance mode in favour of Agent Framework; OpenAI announced that Agent Builder and its hosted Evals leave the platform on 30 November 2026; Google renamed Vertex AI's agent services when it launched the Gemini Enterprise Agent Platform. Each forced work on teams that had changed nothing.

40.3Model deprecations

Generic Every hosted model version has a retirement date, and providers publish lifecycle schedules with notice periods that vary by provider and model Verify. The first prediction question: it is all three. The pin is configuration, the migration may need prompt or code changes, and the new pin is a new model identity that must be evaluated and, at high tiers, re-approved. A playbook:

  1. Know your exposure. The registry lists every agent's pins, so a retirement notice maps to affected agents in minutes.
  2. Choose a candidate per task, from models already priced and approved where possible (Chapter 10).
  3. Measure: golden set over repeated runs (pass^k), red-team subset and injection obey rate, typed-output rate, cost and latency.
  4. Adapt prompts and tool descriptions if needed; these are part of the same release.
  5. Release through shadow and canary; re-sign where the tier requires it (Chapter 38).
  6. Keep a fallback pin tested, because the retired model cannot be a rollback target.

Reference build ARB treated its move from a local Qwen model to Vertex Gemini as "a deliberate configuration change" that "re-gates through CTL-0021/0022. It is a demo beat, not a chore" (D57, D66). The first live runs on the new pin then exposed typed-output and budget issues that the old pin had hidden (D71). That is the normal shape of a model migration: the controls hold, and the measurements move.

40.4Framework and dependency upgrades

Reference build Two decisions give a complete method:

  • D48, the method. "Regression-guarded native rewrite, not TDD: pin the target version, run the suite, and let the red tests draw the worklist." The ADK version swap came up green, touching two pins and zero code, because every framework import sat behind two adapter files (Chapter 7).
  • D53, the policy. Pin the latest stable release at the start of each phase; run a currency bump at least quarterly; a host more than one major or two minor versions behind is a named residual; "a bump that changes any enforced decision is a finding, not a merge"; remove convenience extras that constrain packages the build does not import.

Add the usual software hygiene: lock files committed, automated dependency update proposals, vulnerability scanning on every build, and an image rebuild cadence for base-layer patches (Chapter 32).

40.6Knowledge and memory hygiene

  • Every retrieval source has an owner and a review date. Stale content produces confident, well-cited wrong answers, which grounding checks will not catch because the citation is real (Chapter 4).
  • Index rebuilds are releases. A new embedding model or chunking strategy changes retrieval; evaluate before switching.
  • Memories expire. Time-to-live by memory type; memories tagged with the agent version and session that wrote them, so a bad version's memories can be purged.
  • Erasure works end to end: sessions, memories, caches, evaluation samples and traces, with evidence handled under its own retention rule (Chapter 21).

40.7Living documentation

Reference build D50 draws a line that every agent programme needs. A living document states current posture and is corrected, with a pointer, when a later decision supersedes it; a dated document records what was true on its date and is never rewritten. ARB found seven living lines that contradicted later decisions, some for weeks, while a sales pack was quoting them. The fix was a test over a declared list of living files that fails when they contradict the ratified state, reading the state from parsed configuration rather than text matches. Documentation that a test can falsify stays maintained.

40.8Recertification

Generic An unchanged agent still needs periodic re-approval, because its context changed: users, data, threats, owners, regulation. Assumption A starting cadence: CRITICAL quarterly, HIGH twice a year, MEDIUM yearly, LOW on change only. A recertification reviews:

  • Is it still needed, and is its value case still true?
  • Are the owner and sponsor still in role?
  • Incidents, escalations and control-decision trends since the last review.
  • Evaluation and drift trends; red-team results against current techniques.
  • Permissions actually used against permissions granted (remove the unused).
  • Dependencies approaching end of life: model pins, frameworks, MCP servers.

The second prediction question has a platform answer now: Microsoft Entra Agent ID assigns owners, sponsors and managers to agent identities, with sponsor lifecycle workflows for when people leave. Whatever the platform, an agent without an accountable sponsor should be suspended, not left running. ARB's inventory reconciliation flags orphans and agents running on a maker's personal credentials for exactly this reason (D59).

40.9Retirement

Generic Retirement is a designed event with a checklist:

  1. Decide and announce: reason, date, replacement, and who is told (users, dependent agents, owners of tools it uses).
  2. Stop new work: refuse new sessions; let in-flight runs finish or cancel them safely with compensation where needed.
  3. Revoke the agent's identity, credentials, tokens and delegated grants; remove it from gateways, tool allow-lists and A2A directories.
  4. Mark it retired in the registry; do not delete the entry. Its id must never be reused.
  5. Data: delete or archive sessions, memories and caches by retention policy.
  6. Keep the evidence for its retention period, with the verification keys needed to check it later (Chapter 22).
  7. Close the record: a short retirement report stating what was done and what remains.

The third prediction question: keep decision evidence, sign-offs and the registry entry (they are what an auditor asks for later); delete operational personal data on schedule. The two have different owners and different clocks.

40.10Planning the maintenance budget

Assumption Plan a standing share of each agent team's capacity for maintenance, from the first release. Quarterly model and framework currency work, monthly drift review, red-team refresh, content reviews and recertification add up. Budget it per agent in the business case at intake, so "maintenance" is not discovered as an overrun (Chapter 34). This book uses the same mechanism on itself: every dependency on something unfinished or fast-moving carries a trigger in Appendix H.

40.13In the room

In the room
  • "What does an agent cost after launch?" "Tokens, plus a standing maintenance load: model migrations, framework upgrades, drift review, content upkeep and recertification. Budget it per agent from the start."
  • "How do we turn an agent off safely?" "Stop new sessions, drain or cancel the rest, revoke its identity everywhere, mark it retired in the registry, and keep its evidence. Deleting it is the one thing not to do first."
