PART I · CHAPTER 5

Protocols and trust between agents

MCP connects agents to tools, A2A connects agents to agents, and ACP connects a client to an agent harness. Each moves bytes and claims; none of them decides whether a claim is true or a message may cause anything. That decision belongs to the receiving side's enforcement plane, and the governance of a fleet lives mostly at these boundaries.

5.1Three protocols, three boundaries

ProtocolConnectsCarriesTrust question
MCP (Model Context Protocol)An agent (client) to a tool or data serverTool, resource and prompt definitions; tool calls and resultsIs this the server and the tool we reviewed, and is its result data or instruction?
A2A (Agent2Agent)An agent to another agentAgent cards (capabilities), tasks and messagesWho really sent this, is that edge allowed, and what may this message cause?
ACP (Agent Client Protocol)A client (editor, orchestrator) to an agent harnessSessions, prompts, permission requests, file and terminal operationsWhat may the harness do in my environment, and who grants its permission requests?

Generic The source-code study of harnesses found MCP in 8 of 11 systems and ACP in 6, with ACP picking up a role beyond its design brief: hosting one harness inside another. A2A appeared as one vendor's cross-vendor bet. All three are young and changing; the governance pattern for each is stable even when the specifications are not.

Check before quoting

MCP, A2A and ACP specifications revise frequently (transports, authorisation, capability negotiation). Quote features against the current specification version: modelcontextprotocol.io, a2a-protocol.org, agentclientprotocol.com.

5.2MCP and tool integrity

Generic An MCP server tells the agent what tools it offers by sending names, descriptions and input schemas, and the model reads those descriptions as instructions about when and how to use each tool. That makes a tool description a prompt delivered by a third party. Three attacks follow: tool poisoning (a description containing hidden instructions), the rug pull (a reviewed tool that later changes its description or behaviour), and shadowing (a tool named to collide with one of the agent's own). Add the ordinary supply-chain risk of an unreviewed server and the result is that "connect any MCP server" is "run any third party's prompt".

Your build CTL-0024 handles it with two checks, at gateway session start and on every tool-list refresh:

  • The endpoint must appear in the authored registry (governance/registry/mcp_servers.yaml) under the same name and the same endpoint string. Anything else is refused before a connection is opened, so an unregistered server never puts a byte in front of the model.
  • Each tool is hashed (SHA-256 over its canonical name, description and input schema) and must match the pin reviewed for it. A tool with no pin, a different hash, a name that shadows the agent's own tools, or a name the platform cannot represent is withheld: not shown to the model, and a call to it refused.

Pins are authored, never generated, because a pin is an approval: each records who requested it and who approved it, and a registry containing a pin approved by its own requester is refused as a whole. Changes go through aicoe gov mcp repin, which refuses self-approval and records the change. Evidence records every tool manifest per refresh (pinned hash, observed hash, exposed or not), every endpoint decision and every refused call. make demo-mcp-rugpull shows a changed tool being withheld.

Gotcha

The configuration digest a CRITICAL sign-off binds (CTL-0022) does not cover the MCP registry: its inputs were fixed before CTL-0024 existed. A changed pin is reviewed by the approver it records, not by re-signing the agent (D60). That is a defensible choice for a pin owned by AI security rather than the agent owner, and a question an auditor may ask; know the answer.

5.3A2A and the edge between agents

Your build When ARB's two agents were connected, the build's own threat analysis found that an agent-to-agent hop launders provenance: the upstream agent consumes untrusted text under a control that is satisfied, then emits clean-looking prose that carries none of the taint and arrives looking more authoritative than a retrieval, not less. D40's response is the core of fleet governance and is worth knowing verbatim in spirit: a fleet is a graph; govern nodes by tier and edges by interaction shape; a message has no authority. Four controls attach to any agent with a declared interaction, at the lowest tier:

ControlSaysMechanism
CTL-0016An inter-agent message is untrusted data with no authorityWrapped as data at the boundary, like a retrieval; it can inform reasoning and can never permit an act, lift a limit or waive a control
CTL-0017The sender is a resolved, channel-authorised subjectSender resolved in the identity directory as a service subject; the channel authorised by the declared topology, enforced in Rego
CTL-0018Declared topology equals observed topology; no undeclared edgeEdges declared in manifests (interactions); observed edges reconciled; the gate reports undeclared edges
CTL-0019Cross-agent provenance is recorded; fail closed on influenceA provenance envelope on every message, recorded against the act it influenced

One rider closes a whole class of attack: an approver must be a human subject, so a service subject (another agent) can never approve or satisfy separation of duties. Agent-approves-agent is impossible by construction.

5.4The provenance envelope

Your build Every cross-agent message carries {sender_subject_id, sender_run_id, upstream_record_hash, payload_digest, attestation}. The upstream_record_hash ties the receiver's evidence chain to the sender's own record, so a refund can be traced to the answer that influenced it across two chains. The envelope carries a digest of the payload, never the text, because putting the text in the provenance record would reopen the evidence-minimisation gap at the fleet boundary. The attestation is a signature with a domain separator (a2a-message), so a signature over one kind of object cannot be replayed as another.

5.5ACP and harness hosting

Generic ACP standardises how a client drives an agent harness: open a session, send a prompt, stream progress, and answer the harness's permission requests ("may I edit this file? run this command?"). It was designed for editors embedding coding agents, and it is now also how one harness hosts another. For governance that is the key property: the permission requests are an interception point. Whoever answers them controls what the hosted harness may do.

pm-agent pm-agent's executor contract (ADR-0008) uses exactly that. A coding agent joins as an executor via ACP; one ACP session is one delegation; the harness's permission requests are mapped onto pm-agent's approval gate, denied by default, and only permissions inside the delegation's constraints can be granted. The executor runs in its own sandbox with its own credentials, never pm-agent's, and its diff or pull request returns as a proposal verified against acceptance criteria. Where an agent lacks ACP, opencode's headless server (REST plus an event stream) is the fallback adapter.

5.6Transport is not the decision point

Your build ARB's A2A seam says it in its first line: transport, not the PDP. The module moves a message and says who claims to have sent it; it decides nothing. A transport that also adjudicated would be the natural place to "fix" provenance laundering by trusting first-party senders, which is exactly backwards. The same rule applies to MCP clients, A2A libraries and ACP hosts: keep them thin and swappable, and put every decision in the enforcement plane behind them, so swapping a transport cannot move a control decision.

5.9In the room

In the room
  • "We'd like our agents to use the MCP marketplace." "Every MCP tool description is a prompt written by a third party. Allow-list the servers, pin each tool's description and schema, and withhold anything that changes until someone reviews it."
  • "Our agents will collaborate." "Then each message between them is untrusted input with no authority, every connection is declared, and influence is recorded across the hop."
