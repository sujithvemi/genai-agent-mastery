PART V · CHAPTER 28

State, data and scale

Agents look stateless from the outside and are full of state inside: conversations, checkpoints, memories, counters, approvals, caches, indexes and evidence. Each has its own consistency, durability and isolation needs, and the security-relevant ones (counters and approvals) are the ones most often built on the wrong store. This chapter applies the core ideas of data-intensive systems to agents.

28.1Stateless workers, stateful system

Generic Scale out by keeping workers stateless: any instance can run any step of any run, because all state lives in stores designed for it. A worker that keeps a run, a counter or a session in memory cannot be scaled, restarted or replaced without losing it. The design work is choosing the right store for each kind of state.

28.3Concurrency: the write skew in every limit

Generic The first prediction question is Kleppmann's write skew: two transactions read the same data, each makes a decision that is valid on what it read, and each writes something different; together they violate a constraint neither violated alone. Every agent limit (a daily refund budget, a token budget, "one approval per action") is exposed to it, because turns run concurrently across replicas. Snapshot isolation does not prevent write skew; you need one of:

  • Serializable isolation for the read-decide-write sequence;
  • Atomic conditional writes: "decrement if the remainder stays at or above zero" as one operation;
  • Explicit locks on the row being budgeted (SELECT … FOR UPDATE);
  • Reservations: reserve before acting, reconcile after.

ARB's model budget does the last: a call is reserved in both the agent and principal ledgers "inside the store's atomic transact, so two replicas cannot both spend the last of a budget", and released if a later scope refuses (D58; Chapter 10). A property test runs seeded workloads to check the ledger never exceeds a budget.

28.4Partitioning and replication

  • Partition by tenant first (isolation, noisy-neighbour control, residency), then by run or user within a tenant. Avoid hot partitions: a single global counter is a bottleneck and a single point of contention; shard counters or scope them per tenant.
  • Replicate for durability and read scale. Single-leader replication keeps writes consistent; read replicas lag, so never read a counter or approval state from a replica when deciding.
  • Consistency is per decision: run history can tolerate seconds of lag in a dashboard; a budget check cannot tolerate any.

For agents, tenancy must reach every store, not only the main database: checkpoints, memories, caches (keys include the tenant and the principal's permission scope, as pm-agent's permission-scoped cache does), vector indexes (filter by tenant and permission at query time, or separate indexes), evidence, quotas and model budgets (Chapter 32).

28.6Caching tiers

Generic From nearest to farthest: provider prompt caching (state the provider keeps for a repeated prefix), response caches, read-through caches of tool results, and CDN caches for static content. Each needs an invalidation rule and a scope. Cache tool reads keyed by tenant, principal scope and resource version; never cache anything that authorises an effect; and remember that a cache hit returns yesterday's answer to today's question (Chapter 10).

28.7Vector and search indexes

Generic Retrieval indexes are derived data: rebuildable from source documents, versioned by embedding model and chunking. Approximate nearest-neighbour indexes (HNSW, IVF) trade recall for speed; hybrid search (vector plus keyword) usually wins on enterprise content. The data-design questions are permission filtering at query time, freshness when sources change, and the cost of re-embedding everything when the model changes (Chapter 4, Chapter 40).

28.8Append-only evidence storage

Generic The second prediction question: no. A "no deletes" policy in an application is a convention the database administrator can break. Append-only, in the sense an auditor accepts, needs three things: a structure that makes changes detectable (a hash chain), copies of chain heads in storage that even administrators cannot rewrite for a period (write-once-read-many storage such as GCS bucket lock or S3 Object Lock), and signatures attributing records to keys held in a KMS. ARB anchors its chain heads in a GCS bucket under a locked retention policy, exercised live in October 2026 (Chapter 22). Plan retention and partitioning for evidence early: it grows with every decision, must be queryable by run and subject, and must outlive the agent.

28.9Derived data and rebuildable indexes

pm-agent The third prediction question: pm-agent's ledger (artefacts and their typed links across intent, requirements, decisions, work and releases) is "a derived index rebuilt from the systems of record, not a system of record itself; losing it loses only a cache" (ADR-0007). That buys three things: no dual-write consistency problem with Jira and git (the sources stay authoritative), freedom to change the ledger's schema by rebuilding, and a smaller security surface (it holds nothing that does not exist elsewhere). It costs rebuild time and requires that every fact in it can be traced to a source. DDIA calls this separating systems of record from derived data; it is one of the most useful habits in data design.

Generic Two choices dominate cost and risk. Vector storage now spans two orders of magnitude in price: an index held in memory for high query rates (dedicated vector databases, OpenSearch, Vector Search) against durable, cheap object-backed vectors for large, infrequently queried corpora (S3 Vectors), so match the store to the query rate. And every memory and retrieval service is a copy of enterprise data outside its source system, which brings it under residency, retention and erasure (Chapter 21).

Check before quoting

Vector service limits (dimensions, filterable metadata, query latency at a given rate) and memory services' extraction behaviour change often. Check whether filtering happens before or after the nearest-neighbour search, because post-filtering by permission can return too few results or, worse, depends on a filter the application might forget.

28.12In the room

In the room
  • "Could two copies of the agent both spend the last of the budget?" "Not in this design. The database takes the money out only if enough remains, in one step, so the second request is refused rather than overspent. We test that with concurrent load."
  • "If a customer asks us to delete their data, does that include the agent's memory?" "Yes. Memory, caches and search indexes are copies, so each is listed with its retention and an erasure path. The evidence record keeps what is legally required and nothing more."
  • "Where does our data live?" "Per tenant and per store, in the regions we agree; the table of stores is part of the design pack, so you can check each one."
