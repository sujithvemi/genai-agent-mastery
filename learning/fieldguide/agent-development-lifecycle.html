PART VI · CHAPTER 34

The agent development lifecycle

An agent is software, a model integration, a set of permissions and a product, all at once, and its behaviour is measured rather than specified. That combination needs a lifecycle of its own: one that starts with whether the work should be an agent at all, puts evaluation before code, treats prompts and pins as versioned configuration, and runs after release as a continuous improvement loop rather than a handover to operations.

34.1Why agents need their own lifecycle

Generic Classic software lifecycles assume behaviour follows from specification: write it, test it against the spec, ship it. Classic machine-learning lifecycles assume a model is trained on data you own and validated before deployment. An agent breaks both assumptions:

  • Behaviour is emergent. It comes from a model you did not train, instructions written in prose, tools, retrieved content and the user. You cannot fully specify it; you can only measure it against cases.
  • Small changes have large effects. A sentence in a prompt, a tool description or a model version can change outcomes as much as a code change.
  • It acts. Effects on real systems make permissions, oversight and evidence part of the product, not an afterthought (Part IV).
  • It drifts without anyone touching it. Providers update models, data changes, users find new requests. Quality must be measured continuously.

So the lifecycle borrows from three traditions: product management for framing and value, software engineering for build and release discipline, and model risk management for evaluation, monitoring and change control. Chapter 15 described the governance gates on this lifecycle. This chapter describes the lifecycle itself.

34.2The lifecycle at a glance

34.3Intake and framing

Generic Most failed agent projects fail here, by automating the wrong thing or the right thing in the wrong shape. Intake answers five questions before anyone chooses a framework:

  1. What job, for whom, measured how? Name the user, the task and the outcome metric (resolution rate, cycle time, cost per case, human minutes saved), with today's baseline.
  2. Should it be an agent at all? Walk down the ladder from Chapter 6: a single model call, a fixed workflow with model steps, then an agent. Use an agent only where the path genuinely cannot be fixed in advance. Many "agent" requests are a workflow with one judgement step.
  3. What will it touch? Systems, data classes, effects (read, reversible write, irreversible or financial write), and who it acts for. This is the raw input to tiering (Chapter 13).
  4. How autonomous? Suggest only, act with approval, act within limits, or act and report. Start lower than the business wants; earn autonomy with evidence (Chapter 19).
  5. Is the data ready? Can the agent retrieve what it needs with the user's permissions, and is that content current and owned?

The output is a one-page brief and a decision: proceed, reshape (often to a workflow), or stop. An AICoE should keep these briefs as the start of the agent's record, because every later artefact traces back to the claims made here.

34.4Design

Generic The design stage produces an agent specification: goal and non-goals, users and channels, autonomy level, tools with their effects and contracts, data sources and their permissions, the model per task (Chapter 10), the context strategy (Chapter 3), oversight points, failure behaviour, and the derived tier with its control set.

Two practices separate mature teams from the rest:

  • The golden set comes first. Write 20–50 representative cases, including the hard and adversarial ones, with what a correct outcome looks like, before writing prompts. It turns "the agent should be good at refunds" into something testable, and it is the first answer to the first prediction question. Hamel Husain and Shreya Shankar's practical writing on evals makes the same argument: error analysis on real cases, not generic metrics, drives quality.
  • Tools are designed as contracts. Each tool has a typed schema, a stated effect class, preconditions the enforcement plane can check, and an idempotency rule (Chapter 2, Chapter 16). Tool design is the highest-leverage design work in an agent: the model can only do what the tools let it do.

Reference build In ARB the design artefacts are machine-readable: an agent manifest (governance/agents/<agent>.yaml) declares tools, effects, data, model pin and owner, and the tier and control set are derived from it on every gate run. Onboarding the second archetype, the knowledge advisor, needed "zero framework edits" (D39): a new manifest, a new golden set and the same gate.

34.5Build: the inner loop

Generic The inner loop is how fast a developer can change something and see what the agent does. Good loops share four properties:

  • Runs locally on fakes. The whole governed path runs offline with fake models and fake systems, deterministically (Chapter 7). Live models are a second, slower loop.
  • Traces from the first run. Every step, tool call and model call is visible. Each framework now ships a local developer UI for this: ADK's web UI, LangGraph Studio, Microsoft Agent Framework's DevUI, AgentCore's Agent Inspector, and the Foundry Toolkit for VS Code Verify.
  • Evals in the loop. The golden set runs on every change, at least offline. A failing case is a better bug report than a complaint.
  • The real gate runs locally. In ARB, make check, make eval and make gov-fleet are the same commands CI runs, so "it passed on my machine" means the controls were exercised (docs/operating/GATE_AS_PROMOTION.md).

34.6Prompts and configuration as code

Generic The second prediction question has a firm answer: a system prompt is behaviour, so it is versioned, reviewed, evaluated and released like code, whatever tool stores it. The same goes for tool descriptions, model pins, routing rules, thresholds and policy parameters. Three storage patterns exist:

PatternExampleStrengthRisk
In the repository, beside the codepm-agent's src/pm_agent/prompts/*.txt, loaded package-relative; ARB's manifests and params.yamlOne review, one version, one release; digests cover themNon-engineers cannot edit; changes need a deploy
Prompt-management serviceLangfuse prompt management, LangSmith, Vertex prompt management, Bedrock prompt managementFast iteration, labels per environment, A/BBehaviour can change without a code release; needs the same gate
Platform-native configurationLow-code studios (Agent Studio, Copilot Studio, Agentforce Builder)Business teams can buildVersioning and review depend on the platform; export to code where possible

Whichever you choose, the rule is the same: the configuration that governs behaviour is inside the release unit and inside the sign-off digest (Chapter 38). ARB's CTL-0022 binds a sign-off to a digest of the governing configuration so that a changed parameter re-gates by itself; a prompt service that bypasses that digest is a bypass of the control.

34.8Roles and decision rights

Generic An agent needs more owners than a service does. A workable set:

RoleOwns
Agent product ownerThe brief, the outcome metric, the golden set's definition of correct, release decisions on quality
Agent engineerPrompts, tools, orchestration, the inner loop
Evaluation engineerEval design, judges and their calibration, red-team cases, baselines
Platform engineerRuntime, gateways, enforcement plane, observability, CI wiring
Business process ownerThe process the agent acts in, approval policies, exception handling
Risk, security and data ownersTier, controls, sign-off at high tiers, data entitlements

Reference build ARB's RACI (docs/operating/RACI.md) maps every control's authored owner_role to five functional roles (Director of Engineering, CDO, CISO, agent owner, platform) and adds the per-agent owner from each manifest. It changes no governance semantics; it is a lens over fields that already exist, which is the right way to introduce an operating model to a codebase.

34.9Building agents with agents

Your builds Both builds were written mostly by coding agents. The third prediction question is answered by how the work was divided (THREAD_MODEL.md):

  • T1, architect and governance design, owns the plan and the decision log, designs controls (objective, trigger, owner, evidence, test, exception) and rules on escalations. Since D72, T1 runs in exactly one thread.
  • T2, build, implements against ratified specifications and prompt chains, and "makes no governance-semantic calls". Where a build choice touches semantics, it takes the most fail-closed option, logs it as a numbered addendum, and T1 rules on it at phase close.
  • T6, red team and assurance, attacks what was built.
  • You ratify governance semantics and hold the sign-offs; whole-catalog ratification was "withheld as an accountable human's signature, never a build self-inference" (D49).

This is separation of duties applied to AI-assisted development: the agent that writes the code does not rule on what the controls mean, a different agent attacks it, and a human signs. Accountability stays with the people who ratify, whoever typed the code. Two supporting habits are worth copying: a decision log in which dated records are never rewritten and living documents are corrected with a pointer (D50), and repository skills that encode the house method (pm-agent ships skills/adr-author, skills/phase-gate-review and skills/artifact-discipline for the coding agents that work in it).

34.12In the room

In the room
  • "We want to build 50 agents this year." "Start with an intake that says no or 'make it a workflow' to half of them. The rest share one lifecycle, one registry and one set of gates, so agent fifty costs a fraction of agent one."
  • "Can business users build agents in a studio?" "Yes, inside a lifecycle: the studio's output is versioned, evaluated against a golden set and gated like any other agent. The studio changes who builds, not what must be proven."
  • "What does an agent team look like?" "A product owner, agent and evaluation engineers, a platform team shared across agents, and named business, risk and data owners. Evaluation engineering is the role most teams forget to staff."

34.13Prove it

Defend cold · LL1
  1. RecallThe five intake questions and the artefact each produces.
  2. ApplyTake one request from a client (for example, "an agent that answers HR policy questions and updates leave balances") through intake and design. Where does it split into a workflow and an agent?
  3. ApplyWrite ten golden cases for it, including three adversarial ones.
  4. DesignA prompt-change process for a team that uses a prompt-management service but must keep ARB-style sign-off digests honest.
  5. Trade-offThe T1/T2/T6 split against a single coding agent with human review only.

Card candidates: golden set before code · a prompt is a release · the builder does not rule on semantics.
