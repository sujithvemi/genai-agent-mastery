PART V · CHAPTER 30

Deployment and CI/CD for agents

An agent deploys like a service, with three additions: its release unit includes prompts, pins and policy as well as code; its pipeline must run the governance gate, not only the tests; and its runtime choice (containers, Kubernetes or a managed agent runtime) decides how much of identity, sessions and isolation you build yourself. This chapter covers the deployment mechanics; Chapter 38 covers what goes in a release and how it is rolled out.

30.1The deployment unit for an agent

Generic What ships: a container image (code, dependencies from a lock file, framework version), the configuration that governs behaviour (prompts, manifest, model pins, policy bundle, parameters), infrastructure definitions, database migrations and, for the gate, the evaluation sets and baselines. The image and the configuration may deploy separately, but they are versioned and approved together (Chapter 38).

The third prediction question: isolation needs, how much platform you want to inherit, and operational capacity. Many estates use all three: Agent Runtime for agents, Cloud Run for APIs and tools, GKE for sandboxed executors (Chapter 37).

30.3Infrastructure as code

Generic Every environment is created from code (Terraform, Pulumi, or the cloud's own tooling), reviewed, planned and applied by the pipeline, never by hand. For agent platforms the code includes the agent's identity and its grants, gateway and policy configuration, Model Armor templates, VPC Service Controls perimeters, buckets with retention locks for evidence anchors, KMS keys, and monitoring. Policy-as-code checks on the infrastructure itself (for example, no public buckets, retention locked on evidence buckets) run in the same pipeline.

30.4A keyless pipeline

Generic The first prediction question: a long-lived key in CI is a standing credential that leaks through logs, forks and compromised runners, and it cannot tell which workflow is using it. Replace it with workload identity federation: the CI system (GitHub Actions, GitLab, Cloud Build) gets a short-lived OIDC token for each job; the cloud trusts tokens from that repository, branch or environment, and exchanges them for short-lived cloud credentials scoped to what the job needs. Your M0 milestone built exactly this for GCP; the M1 rep rebuilds it from memory. Add environment protection rules so production deploys require approval and run only from the main branch.

30.5The gate as a required check

Reference build ARB's CI runs four steps in one job: sync the locked environment, make check (lint, types and tests), make gov-validate (catalog, crosswalk and parameter consistency), and make gov-fleet, the ADLC gate run against the live enforcement plane for every agent. Branch protection makes the job a required check, so a BLOCKED agent cannot merge. Because gov-fleet discovers manifests by directory, onboarding an agent extends the required check without editing the workflow (docs/operating/GATE_AS_PROMOTION.md). The conformance report the gate reads is generated in the run, never committed, so nobody can edit a table to make an agent look deployable.

30.6Images, signing and provenance

  • Minimal base images and multi-stage builds; pinned digests for base images.
  • Lock files installed in frozen mode (uv sync --frozen in ARB), so CI builds exactly what was reviewed.
  • SBOM generated per image; vulnerability scanning in the pipeline and on a schedule.
  • Signing and provenance: sign images (for example with Sigstore cosign) and produce SLSA provenance; enforce at deploy time with Binary Authorization or an admission policy.

The second prediction question has a real answer in your build. ARB's Dockerfile notes that the Rego engine's native library links libatomic, which the slim Python image does not include: "Without it the policy engine cannot load, the plane fails closed (GBL-DENY-01 refuses every call) and the gate BLOCKS - correct behaviour, wrong image (found E1-S3)." It is a packaging fault, and the refusal is exactly right. A container-level smoke test that runs the gate inside the built image catches it before production.

30.7Environments, secrets and configuration

  • Environments differ in what they connect to: fakes in CI, live models with synthetic data in test, production-like integrations in staging (Chapter 38).
  • Secrets live in a secret manager, are fetched at runtime with the workload's identity, and never appear in images, prompts, logs or sandboxes.
  • Configuration that governs behaviour is versioned with the release and hashed into the sign-off where the tier demands it; environment-specific values (endpoints, project ids) are separate and not behaviour-setting.
  • Migrations are backward compatible across one release so rollback works: expand, migrate, contract.

30.8What your builds' pipelines show

Your builds ARB builds two images from one Dockerfile: a runtime image with the CLI and runtime dependencies, and a demo image with the whole repository, because the demo replays the red-team corpus and portability suites and runs the framework hosts' environments. A Compose file runs the demo, including a portability run across bindings (make demo-portability-compose). pm-agent has its own Dockerfile and a Compose file for its Postgres-backed memory. Neither build deploys to a production environment yet; that is ARB's E6 and pm-agent's hosted release (Appendix H).

30.11In the room

In the room
  • "Who can change what the agent says?" "Its prompts, model choice and policies ship like code: reviewed, tested, gated and signed. A change nobody approved cannot reach production, because the gate and the admission check both refuse it."
  • "How fast can you undo a bad release?" "Minutes. The previous version stays deployed beside the new one and traffic moves back; data changes are written so the old version still works with them."
