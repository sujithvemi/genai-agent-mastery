PART II · CHAPTER 9

Inference and serving

Whether you call a hosted model or run one yourself, the same physics sets latency, throughput and cost. This chapter explains that physics (prefill and decode, the KV cache, batching, caching, speculative decoding and quantisation) and then the commercial layer on top of it: the quotas, tiers and reservations that decide whether an agent gets an answer or a 429.

9.1Two phases: prefill and decode

Generic Every request runs in two phases with different bottlenecks.

  • Prefill processes the whole prompt in one parallel forward pass, computing the keys and values for every prompt token. It is compute-bound: lots of matrix multiplication done in parallel. Its cost grows with prompt length (linearly for the weights, quadratically for attention). It sets the time to the first token.
  • Decode then produces output one token per forward pass, each pass reading the model weights and the KV cache. It is memory-bandwidth-bound: little arithmetic per byte moved. It sets the time between tokens, and output length multiplies it.

So the answer to the first prediction question is time to first token. A rough rule for dense models is about 2 × parameters floating-point operations per token processed: prefilling a 4,000-token prompt on a 7.6-billion-parameter model is about 6 × 1013 operations, well under a second on a data-centre GPU and closer to a minute on a laptop CPU. That difference is why local evaluation runs are slow when prompts are long. pm-agent's full live evaluation on a local 7B model took about eleven hours (ADR-0006).

9.3Why decode is memory-bound

Generic At batch size one, every decode step reads every weight once to produce one token. So an upper bound on single-stream speed is memory bandwidth divided by model size in bytes. Your knowledge advisor's pinned weights file is 4.68 GB (Qwen2.5-7B-Instruct, Q4_K_M):

Hardware (memory bandwidth, approximate)Upper bound, batch 1
Laptop CPU, dual-channel DDR5 (~80–100 GB/s)≈ 17–21 tokens/s
High-end consumer GPU (~1,000 GB/s)≈ 210 tokens/s
Data-centre GPU, HBM3 (~3,350 GB/s)≈ 700 tokens/s

Upper bounds only: KV-cache reads, kernel overheads and sampling all reduce them. Assumption bandwidth figures are typical, not measured on your hardware.

Batching changes the arithmetic. Sixteen sequences decoded together share one read of the weights, so aggregate throughput rises almost sixteen-fold while each user's speed drops only a little, until the step becomes compute-bound or KV memory runs out. That answers the second prediction question: each of the 16 users sees somewhat less than 40 tokens per second, not 2.5. This is why providers batch aggressively, why your request's speed depends on other customers' traffic, and why a reserved capacity product exists.

9.4The KV cache, sized

Generic The KV cache stores keys and values for every past token, in every layer, for every key-value head:

KV bytes per token = 2 (K and V) × layers × kv_heads × head_dim × bytes per value

Worked from the published configuration files (read 2026-10-21):

ModelLayers · KV heads · head dimKV per token (16-bit)One 32k-token sequence
Qwen2.5-7B-Instruct (your local pin)28 · 4 · 12857,344 B (56 KiB)≈ 1.75 GiB
Qwen2.5-72B-Instruct80 · 8 · 128327,680 B (320 KiB)≈ 10 GiB

Without grouped-query attention the 7B model would need 28 KV heads instead of 4, seven times as much cache. The cache, not the weights, usually limits how many conversations a server can hold at once.

Worked example · concurrency is a memory budget

Serve Qwen2.5-72B in 8-bit weights (about 73 GB) on two 80 GB GPUs. Roughly 80 GB remains for the cache. At 320 KiB per token that is about 244,000 tokens: about 30 concurrent conversations at 8,000 tokens each, or 7 at 32,000. Store the cache in 8 bits and both figures double. Assumption activations, fragmentation and framework overhead are ignored; real headroom is lower.

9.5Batching and paged attention

Generic Three ideas turned LLM serving from wasteful to efficient:

  • Continuous batching. Static batching waits for the longest sequence in a batch to finish. Iteration-level scheduling (Orca, Yu et al., OSDI 2022) adds and removes sequences at every decode step, so short requests leave early and new ones join immediately.
  • Paged attention. Allocating each sequence a contiguous cache for its maximum length wastes most of the memory. PagedAttention (Kwon et al., 2023, the paper behind vLLM) stores the cache in fixed-size blocks mapped through a table, as an operating system pages memory. The authors measured 60–80% of KV memory wasted in earlier systems and under 4% with paging, and reported 2–4× throughput at the same latency.
  • Chunked prefill. A long prefill stalls every decode in the batch. Splitting prefills into chunks and interleaving them with decode steps (Sarathi-Serve, Agrawal et al., 2024) keeps inter-token latency smooth.

9.6Prefix and prompt caching

Generic Agents resend the same long prefix on every call: system instructions, tool declarations, policies, earlier turns. If the server keeps the KV cache for a prefix it has seen, the next request skips that part of prefill. Self-hosted engines do this automatically (vLLM's prefix caching; SGLang's RadixAttention, Zheng et al., 2023). Hosted APIs sell it as prompt or context caching, with cached input tokens billed at a large discount and a shorter TTFT; some providers apply it implicitly, others require marking cacheable blocks.

  • Design for it. Put stable content first (system prompt, tool schemas, policy text) and variable content last. A timestamp or request id at the top of the prompt defeats every cache.
  • Count it. Cached tokens may still count towards throughput limits. AWS's documentation, for example, says Reserved-tier sizing must include cache-write input tokens.
  • Isolate it. A shared prefix cache can leak through timing: a cache hit is measurably faster, which reveals that someone else sent the same prefix. Gu et al. ("Auditing Prompt Caching in Language Model APIs", 2025) detected cross-user cache sharing at several API providers this way. Ask a hosted provider how its caches are scoped (to an organisation, a project or a key) and get the answer in writing; in a self-hosted multi-tenant deployment, scope prefix caches per tenant (Chapter 32).

Prompt caching should not be confused with response caching, which returns a stored answer and needs permission scoping to be safe (Chapter 10).

9.7Speculative decoding

Generic Decode is memory-bound, so a forward pass that checks several tokens costs little more than one that produces one. Speculative decoding (Leviathan et al., 2022; Chen et al., 2023) uses a small draft model to propose k tokens, then has the large model verify them in one pass, accepting the longest correct prefix. A rejection-sampling rule makes the output distribution identical to the large model's. Speedups of 2–3× are typical where the draft guesses well (code, boilerplate, structured output). Variants replace the draft model with extra prediction heads (Medusa) or feature-level drafting (EAGLE). For a buyer it is invisible, except as lower TPOT.

9.8Quantisation

Generic Storing weights in fewer bits shrinks memory and, because decode is bandwidth-bound, speeds it up almost proportionally. Common schemes are 8-bit (LLM.int8(), FP8 on recent GPUs) and 4-bit (GPTQ, AWQ, and llama.cpp's "k-quants" in the GGUF format). Q4_K_M, your local pin, mixes 4- and 6-bit blocks: 4.68 GB for about 7.6 billion parameters is roughly 4.9 bits per weight, against 16 for the original. The KV cache can be quantised too. Quality loss is usually small at 8 bits and noticeable at 4 bits on harder tasks, so measure on your own evaluation set.

Governance consequence · quantisation changes identity

Two files called "Qwen2.5-7B-Instruct" at different quantisations are different models with different behaviour. ARB's pin for the knowledge advisor records the weights file, the quantisation and a SHA-256 of the exact file, and a live preflight re-hashes it before a run (D57). A model id alone is not an identity (Chapter 10).

9.9Parallelism and disaggregation

Generic Models too large for one accelerator are split: tensor parallelism splits each layer's matrices across devices (fast interconnect needed), pipeline parallelism places different layers on different devices, and expert parallelism spreads a mixture-of-experts model's experts. The newest step is disaggregated serving: run prefill and decode on separate pools, because one is compute-bound and the other bandwidth-bound, and move the KV cache between them (DistServe and Splitwise, 2024). Open projects such as NVIDIA Dynamo and llm-d, and Kubernetes-level routing such as GKE Inference Gateway, package these ideas Verify. You need this depth when a client wants to self-host at scale or argues about cost per token; most enterprise agents consume a hosted endpoint.

Three consequences for design:

  1. Tokens per minute is the binding constraint for agents. One user request becomes many model calls, each resending a long context. Capacity planning starts from tokens per task × tasks per minute, not from users (Chapter 33).
  2. On shared capacity, a 429 is weather, not a bug. Google's guidance is exponential backoff with jitter, not an immediate retry, plus the global endpoint to spread load. For guaranteed real-time capacity, reserve it.
  3. Residency is a deployment choice. "Global" options may process data in any region. A client with residency obligations needs data-zone or regional options, at some cost in quota and price (Chapter 21).
Retries that respect effects · ARB D71

The third prediction question has a governed answer. When the CRITICAL agent met 429s on live Vertex, D71 ruled a bounded whole-turn retry: only on 429 or RESOURCE_EXHAUSTED, only if no effectful tool call completed in that attempt, each retry on a fresh enforcement plane, at most three attempts with 120, 240 and 480 second backoff, at most ten retries per measurement, and the full error body recorded. A 429 after an effectful call aborts, because repeating the turn could repeat the refund. Where a fixed daily or per-minute limit is listed instead, there is no retry: raising a limit is a human act. The retry is keyed on the error class, never on the outcome, so it cannot be used to shop for a different decision (Chapter 29).

9.12What this means for agents

Generic An agent turn is a chain of requests. Assumption With five model calls, each 0.8 s TTFT and 300 output tokens at 25 ms per token, the model time alone is about 5 × 8.3 ≈ 42 seconds before any tool runs. That single estimate explains several architectural choices made elsewhere in this book:

  • Long-running turns need an asynchronous run API (accept, return a run id, stream or poll), not a request held open (Chapter 25).
  • Output ceilings and bounded loops are latency and cost controls as much as safety controls.
  • Stable prefixes make prompt caching pay on every call after the first.
  • Small, fast models for routing and extraction, large ones for planning, cut both latency and cost (Chapter 10).
  • Thinking tokens are output tokens: a reasoning budget is a latency budget too (D71's explicit thinking_budget).

9.13Build it

Build it · T10, about four hours
  1. With the knowledge advisor's local model in LM Studio, measure TTFT and tokens per second for prompts of 500, 2,000 and 8,000 tokens and outputs of 50 and 500 tokens. Plot TTFT against prompt length and explain the shape.
  2. Compare measured single-stream speed with the bandwidth bound for your machine.
  3. Optional, on a rented GPU: run vLLM with the same model, load it with 1, 8 and 32 concurrent clients, and record per-user and aggregate tokens per second.
  4. Turn on prefix caching (or a hosted provider's prompt caching) with a stable 3,000-token system prefix and measure the TTFT change.
  5. Read Ramchandani's AI System Design Playbook cases 2 (vLLM), 5 (prompt caching) and 10 (KV cache), and check each against this chapter.
