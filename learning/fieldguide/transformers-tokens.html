PART II · CHAPTER 8

Transformers and tokens for architects

You do not need to train a model to design around one, but you do need to know why it behaves as it does. Nearly every limit that shapes an agent system (context budgets, latency, cost, nondeterminism, prompt injection, unreliable explanations) follows from a handful of mechanics. This chapter covers those mechanics at the depth where they start to change design decisions.

8.1Why an architect needs the mechanics

Generic Your builds treat the model as a component behind a seam (Chapter 7), which is right. But a seam hides an implementation, not its physics. Four design questions cannot be answered well without the mechanics:

  • Capacity and cost. Everything is metered in tokens of a particular tokenizer, and the work grows with sequence length. A budget control (ARB CTL-0020) has to count something before the call; what it can safely count depends on how tokenizers work.
  • Latency. Generation is sequential, one token at a time, so output length dominates response time. Agents multiply this by the number of loop turns.
  • Reliability. Outputs are samples from a probability distribution and not fully reproducible, so evidence must record what was produced; it cannot be regenerated later.
  • Security. Instructions and data arrive in one token stream, so no prompt can fully separate them. That one fact is why the controls in Part IV sit outside the model.

8.2One token's path

8.3Tokens

Generic Models read integers, not characters. A tokenizer maps text to ids from a fixed vocabulary, almost always learned by byte-pair encoding (BPE; Sennrich et al., 2016) or the related unigram method in SentencePiece. BPE starts from bytes or characters and repeatedly merges the most frequent adjacent pair into a new vocabulary entry until it reaches the target size. The consequences matter more than the algorithm:

  • Tokens are not words. Common English words are one token; rare words, identifiers, numbers and code split into several. A UUID or a base64 blob is expensive.
  • Languages are not equal. Vocabularies are learned mostly from English-heavy data, so many other languages and scripts need more tokens for the same meaning. The same request costs more, uses more context and takes longer to generate. Measure with the actual tokenizer for a multilingual client; do not assume English ratios.
  • Each vendor counts differently. Limits, prices and quotas are in the provider's own tokens. A budget computed with one tokenizer is an estimate for another.
  • Numbers and spelling are awkward. Digits may be grouped unpredictably, which is part of why models make arithmetic and character-counting errors. Do arithmetic in tools.
  • Odd tokens exist. Vocabulary entries that were rare in training ("glitch tokens") can produce strange behaviour. This is a reason to screen and bound inputs, not a design centrepiece.

Reference build ARB's model budget (CTL-0020) must project a call's size before the call, without the provider's tokenizer. D58's answer is an upper bound: the UTF-8 byte length of the serialised request, because with byte-level BPE each token covers at least one byte, so the bytes cannot under-count the text. Two residuals are named rather than hidden: chat-template special tokens are not counted, and a provider that ignores max_output_tokens can exceed the projection (that usage is still charged, so the next call is refused).

Verify it yourself

Is "tokens ≤ bytes" always true? SentencePiece tokenizers often add a dummy prefix space, so a one-character input can become two tokens (a word-boundary marker and the character). Work out why ARB's bound still holds in practice (hint: what else is in the serialised request besides the user's text?), and what you would change if the bound were applied to raw message text instead.

8.4Embeddings and position

Generic Each token id selects a row of an embedding table: a learned vector of a few thousand numbers. Attention by itself has no notion of order, so position must be added. Most current open models use rotary position embeddings (RoPE; Su et al., 2021), which rotate the query and key vectors by an angle that depends on position, so attention scores depend on relative distance. Context-extension methods stretch these rotations to longer sequences than the model was mainly trained on, which is one reason a model's effective context can be shorter than its advertised window (8.10).

The same idea, a learned vector per piece of text, underlies embedding models used for retrieval. Those are separate models trained so that similar meanings land close together (Chapter 4).

8.5Attention

Generic Self-attention (Vaswani et al., 2017) lets each position gather information from others. Each token's vector is projected into a query, a key and a value. A token's query is compared with every earlier token's key; the scores are scaled by √dk, normalised by softmax, and used to take a weighted sum of the values:

Attention(Q, K, V) = softmax( Q·Kᵀ / √d_k  +  mask ) · V
# mask = −∞ above the diagonal: a token may not attend to later tokens (causal)

Several heads do this in parallel with different projections, so different heads can track different relationships. Four consequences matter to an architect:

  1. Quadratic cost in prompt length. Processing a prompt of n tokens compares every token with every earlier one: work grows with n². Long prompts are disproportionately expensive to process. FlashAttention (Dao et al., 2022) makes exact attention much faster by reorganising memory traffic, but does not change the quadratic count.
  2. The KV cache. During generation, earlier tokens' keys and values do not change, so they are stored and reused. The cache grows linearly with sequence length and is the main memory cost of serving long contexts (Chapter 9).
  3. Grouped-query attention. Many heads can share one set of keys and values (multi-query attention, Shazeer 2019; grouped-query attention, Ainslie et al. 2023). Most current open models do this to shrink the KV cache several-fold.
  4. Everything can influence everything. There is no channel separation: any token in the context can affect how any later token is produced. This is the root of prompt injection (8.9).

8.6The decoder stack

Generic A block is attention followed by a feed-forward network, each wrapped with normalisation and added back into a residual stream that carries each token's representation up through the layers. The feed-forward networks hold most of the parameters. A mixture-of-experts (MoE) model replaces each feed-forward network with many expert networks and a router that sends each token to a few of them (Shazeer et al., 2017; Fedus et al., 2021). MoE explains the distinction between total parameters (memory to hold the model) and active parameters per token (compute per token): an MoE model can be large to host and comparatively cheap to run.

The final layer projects to one score (a logit) per vocabulary entry. That is the whole output: a distribution over the next token.

8.7Generation and sampling

Generic Softmax turns logits into probabilities; a decoding strategy picks a token. Greedy takes the most likely. Temperature sharpens (below 1) or flattens (above 1) the distribution before sampling. Top-k and top-p (nucleus) sampling restrict choice to the most likely candidates. The chosen token is appended and the model runs again.

The first prediction question has a precise answer: temperature 0 is not a guarantee of identical output. Floating-point addition is not associative, and a serving system's results can depend on how requests were batched together, which changes the order of reductions. Thinking Machines Lab's "Defeating Nondeterminism in LLM Inference" (Horace He, September 2025) traced this to kernels that are not batch-invariant and showed it can be fixed at a throughput cost; hosted APIs generally do not promise it. Mixture-of-experts routing and provider-side model updates add further variation.

Design consequence

Evidence must store what the model produced; you cannot rely on regenerating it. Tests must not assert exact model text: use typed outputs and property checks (Chapter 2), and measure rates over repeated runs (pass^k) rather than single passes (Chapter 23). Your builds already do both, and CI runs on deterministic fakes for exactly this reason.

8.8How the behaviour got there

Generic A chat model is built in stages, and each stage explains a behaviour you will design around:

StageWhat it doesBehaviour it explains
Pre-trainingNext-token prediction on trillions of tokensBroad knowledge, fluent continuation, a knowledge cut-off, confident errors where data was thin
Supervised fine-tuningImitation of example dialogues, including tool callsChat format, following instructions, emitting tool-call syntax
Preference tuningRLHF (Ouyang et al., 2022), DPO (Rafailov et al., 2023), constitutional methodsHelpfulness and refusals, learned tendencies (not rules); sycophancy as a side effect
Reinforcement learning on verifiable tasksRewards for correct maths, code, tool use (for example DeepSeek-R1, 2025)Long reasoning traces, better multi-step tool use, sometimes reward-hacking behaviour

The governance point is that all of these produce tendencies. Instruction-following and refusals are learned dispositions, strengthened by training such as OpenAI's instruction hierarchy work (Wallace et al., 2024), but never guarantees. A model that follows the system prompt 99% of the time is a model that does not, one time in a hundred.

pm-agent The live record shows the other side of the same coin. In pm-agent's live injection harness the local 7B model obeyed only about 5% of the hostile "steers" planted in Jira content, so, in ADR-0006's words, it "barely exercises the guard". A low obey rate on a weak model is not evidence of safety. Assumption A stronger instruction-follower may obey more injected instructions as well as more legitimate ones, so the injection rate has to be re-measured on every model you adopt, not carried over. This is one reason model choice is a governed decision (Chapter 10).

8.9Why injection is structural

Generic Classic injection attacks (SQL, shell) were fixed by separating code from data at the interface: parameterised queries, argument arrays. A transformer has no such interface. System prompt, user message, retrieved documents and tool results become one sequence of tokens, and attention lets any of them influence the next token. Role markers in the chat template are just more tokens, whose influence was learned in training. So the third prediction question has a structural answer: a sentence telling the model to ignore instructions in documents is itself just text competing with other text.

This is why the architectural defences work and the prompt-level ones only help: decide every effect outside the model on trusted facts (Chapter 16), keep untrusted content away from the component that plans (CaMeL's dual-LLM split), and treat screening as a filter, never as the control (Chapter 20).

8.10Long context, advertised and effective

Generic Context windows have grown to hundreds of thousands or millions of tokens, but three effects limit what a window is worth:

  • Position effects. Liu et al. ("Lost in the Middle", 2023) found accuracy highest when the relevant passage is at the start or end of a long context and lowest in the middle.
  • Effective length. Needle-in-a-haystack retrieval is easy; benchmarks with harder tasks such as RULER (Hsieh et al., 2024) found that many models' usable context was well below the advertised window.
  • Cost and latency. Long prompts cost more per call, take longer to prefill and consume KV memory.

The design response is the one Chapter 3 builds out: assemble the minimum context deliberately, put what matters at the edges, retrieve rather than stuff, and measure quality at the context sizes you actually use.

8.11Reasoning models

Generic Reasoning models spend extra generated tokens "thinking" before answering. Chain-of-thought prompting (Wei et al., 2022) showed the effect; reinforcement learning made it native, and work on test-time compute (Snell et al., 2024) showed that spending more inference compute can substitute for model size on some tasks. For an architect, thinking tokens are output tokens: they are billed, they add latency, and they count against output limits.

Reference build D71 made the thinking budget an explicit, recorded part of the CRITICAL agent's model pin (thinking_budget: 512 inside a 1,024-token output ceiling) so that token use is a configured fact rather than a provider default, and added it to the inputs of the fairness digest because changing it could change outcomes.

Gotcha · reasoning is not an explanation

A model's stated reasoning is not a reliable account of why it produced an answer. Turpin et al. (2023) showed chain-of-thought explanations that omitted the biasing feature that actually drove the answer, and later studies of reasoning models found similar unfaithfulness. Do not offer reasoning traces to a regulator as the explanation of a decision. Explain decisions through the deterministic parts: the facts the PIP read, the rule the PDP applied and the evidence record (Chapter 22).

8.13Build it

Build it · about six hours over two weeks
  1. Work through Sebastian Raschka's Build a Large Language Model (From Scratch) chapters 2–4 (tokenisation and data, attention, the GPT model) with its companion videos. Write the causal attention module yourself before reading the solution.
  2. Tokenise the same 200-word policy paragraph in English and in Telugu or Hindi with two tokenizers (for example tiktoken and a SentencePiece model from Hugging Face). Record the token counts and the ratio.
  3. Compute the KV cache size per token for the local model your reference build pins, from its configuration file (Chapter 9 gives the formula).
  4. Run the same prompt twenty times at temperature 0 against your local model and against a hosted one. Count distinct outputs.
