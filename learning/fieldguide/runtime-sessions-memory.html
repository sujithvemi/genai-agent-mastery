PART VI · CHAPTER 37

Runtimes, sessions and memory services

An agent run can last two seconds or seven days, pause for a human, stream as it works and run code it wrote. Ordinary web hosting assumes none of that. Every major platform now sells a managed agent runtime with sessions and memory attached. This chapter explains what agents need from a runtime, how the managed runtimes compare with containers and Kubernetes, how session and memory services work, and the line between what a managed runtime governs and what remains yours.

37.1What agents need from a runtime

Generic Compared with a typical stateless web service, an agent needs:

  • Long and variable run times, from seconds to days, without holding a request open.
  • Durable state across turns, crashes, deployments and approval waits (Chapter 26).
  • Streaming of progress and partial output (server-sent events or WebSockets).
  • Per-session isolation when the agent runs code or browses.
  • Identity per agent, not a shared service account (Chapter 18).
  • Egress control: which models, tools and hosts the agent may reach.
  • Versions and traffic splitting for safe release (Chapter 38).
  • Scheduling and events for background agents triggered by time, queues or data changes.

37.4Sessions

Generic A session is the record of one conversation or run: the event log (messages, tool calls, results) plus working state. Every framework has a session abstraction (ADK's session service, LangGraph's checkpointer, the OpenAI Agents SDK's sessions), and the managed runtimes offer hosted versions. Design decisions:

  • Session identity. Map sessions to business records (a case number, a ticket) so they can be found, audited and deleted. GEAP Sessions accepts your own session ids for this reason.
  • Where state lives. In a store the runtime can lose without losing the run: pm-agent checkpoints its planning graph in Postgres (P4-S0), so an approval wait survives restarts. The first prediction question's answer is a database, never a held request or a live process.
  • Size and lifetime. Sessions grow with every turn; compaction and summarisation are context engineering (Chapter 3), and a time-to-live is a data-retention decision (Chapter 21).
  • Who can read a session. A session contains everything the user and the tools said. Its access control is the user's, not the developer's.

37.5Memory services

Generic Long-term memory services extract durable facts from sessions and retrieve them later: user preferences, facts about entities, summaries of past work, and sometimes procedures. GEAP Memory Bank (generation from streamed events, revision history, memory profiles), AgentCore Memory (strategies including episodic memory, namespaces, time-to-live) and Foundry's memory (procedural, user and session) all follow this pattern, as do open-source options such as Mem0, Zep and Graphiti Verify.

The second prediction question shows the central risk. Memory is written by a model from conversations that may include injected or mistaken content. A remembered "approved up to $5,000" is a claim, not a fact. Four rules follow, and your builds implement them (Chapter 3):

  1. Memory is a hint unless verified. No policy decision reads memory; the PIP re-reads trusted systems.
  2. Scope it. Per user and per tenant by default; shared agent memory is a deliberate, reviewed exception.
  3. Protect its integrity. pm-agent's governed memory is redacted, scoped, expiring and MAC-verified, so a tampered entry is detected.
  4. Make it erasable. Every memory traces to its source session and subject, so a deletion request can find it.

37.6Scaling and isolation behaviour

  • Concurrency is bounded by model quota before compute. An instance can hold hundreds of waiting agent turns; the provider's tokens per minute run out first (Chapter 9).
  • Timeouts. Serverless request limits (Cloud Run allows up to 60 minutes per request) suit turns of seconds to minutes. Anything longer is asynchronous: accept, checkpoint, resume on an event.
  • Cold starts matter for interactive agents; managed runtimes advertise sub-second starts, containers can keep a minimum number of warm instances.
  • Idempotent resumption. A resumed run must not repeat an effect it already made. Effects carry idempotency keys, and evidence records which step completed (Chapter 29).
  • Cost models differ: per vCPU-second (containers), per session-hour (Claude Managed Agents), per request and memory (functions), plus tokens everywhere. Long waits are cheap only if nothing is running during them.

The third prediction question: a platform identity replaces none of your controls. It makes CTL-0008-style subject resolution easier and makes per-agent least privilege possible, but deciding what an action may do on whose behalf is still the PDP's job. "Platforms supply enforcement points; the rulebook is yours."

37.8Worked example: hosting pm-agent

pm-agent The design scenario in design/pm-agent-at-scale.md assumes about 5,000 users in 20 tenants, a peak of about 50 concurrent planning runs, each 20 seconds to 2 minutes with 5–30 model and tool calls, and Jira writes that need a distinct human approver. pm-agent's own deployment notes start on Cloud Run with Cloud SQL Postgres and defer GKE until sandboxed executors need node-level isolation. Assumption A defensible plan:

  1. Run API on Cloud Run: accept a run, return its id, stream progress by server-sent events (Chapter 25). Runs of two minutes fit comfortably inside request limits.
  2. State in Postgres: the existing checkpointer; an approval wait is a checkpoint plus an event, resumed by a worker when the approver signs.
  3. Identity: workload identity for the service, and per-tenant, on-behalf-of Jira credentials held outside the agent.
  4. Executors (coding agents and other harnesses) in isolated sandboxes, which is the point at which GKE or a managed sandbox earns its cost (Chapter 6).
  5. Alternative: GEAP Agent Runtime would supply sessions, memory and per-agent identity, at the cost of fitting pm-agent's LangGraph runtime and Postgres checkpoints to the platform's model. Record the choice and the rejected alternative in the design log.

37.10In the room

In the room
  • "Should we use the cloud's agent runtime or our Kubernetes platform?" "The managed runtime buys sessions, memory, identity and sandboxes on day one. Kubernetes buys control. Most clients should start managed and keep the agent portable behind their own gateways and seams."
  • "Can we turn on long-term memory?" "Yes, scoped per user, erasable, and never read by a policy decision. Memory makes the agent more helpful; it must never make it more authorised."
