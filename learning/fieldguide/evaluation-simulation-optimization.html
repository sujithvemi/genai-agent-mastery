PART VI · CHAPTER 39

Evaluation, simulation and optimization

Chapter 23 treated evaluations as gates: pass or hold before release. This chapter treats them as the engine of improvement. Quality comes from a loop: find failures in production, turn them into cases, change something, measure the change offline and in simulation, release it carefully and watch it online. Every platform now sells parts of this loop, including optimizers that propose changes themselves. The architect's job is to keep the loop honest.

39.2What to evaluate

LayerQuestionTypical measure
OutcomeDid the task get done correctly?Task success against the end state (check the system, not the transcript)
TrajectoryDid it take a sensible path?Tool selection and argument accuracy, order, step count, redundant calls
ComponentsDid each part work?Retrieval recall and precision, extraction accuracy, routing accuracy
Safety and policyDid it stay inside its limits?Refusal correctness, injection obey rate, control decisions, groundedness
EfficiencyAt what cost?Tokens, latency, cost per successful task
ExperienceWould a user be satisfied?Rubric scores, human ratings, escalation and abandonment rates

Reliability over repeated trials. The first prediction question: if each attempt succeeds independently with probability 0.8, all four succeed with probability 0.84 ≈ 0.41. τ-bench (Yao et al., 2024) introduced pass^k, the chance that all k trials of a task succeed, because agents that look good on a single pass often fail this. Customers meet your agent many times; pass^k is closer to their experience than pass@1.

39.3Evaluators and their calibration

  • Code-based checks are cheapest and most trustworthy: schema validity, exact values, state of the system after the run (was the refund the right amount, on the right order?), policy decisions in evidence. Use them wherever the answer is checkable.
  • LLM judges score what code cannot: helpfulness, faithfulness, tone, adherence to a rubric. Zheng et al. ("Judging LLM-as-a-Judge", 2023) documented their biases: position, verbosity and self-preference. Mitigate with rubrics that ask narrow, binary questions, swapped positions in pairwise comparisons, and a judge from a different model family than the agent.
  • Human review creates the labels everything else is calibrated against, and catches what nothing else does.

The second prediction question: 92% agreement may be poor. If 90% of cases are passes, a judge that always says "pass" agrees 90% of the time. Calibrate judges like classifiers: measure agreement per class, use a chance-corrected statistic such as Cohen's kappa, and look at the disagreements. In your build, classifier accuracy is "reported, never gated" (D54), and a model-based check on the enforcement path may only restrict (D52); a judge used for quality measurement needs the same humility about what its score means.

39.4Datasets and baselines

  • Golden sets: hand-written, representative, with the definition of correct agreed by the product owner (Chapter 34).
  • Regression cases: every production failure that was fixed becomes a case, so it cannot return unnoticed.
  • Adversarial sets: red-team corpora for injection, misuse and policy edges (ARB's red-team corpus has hundreds of cases; Chapter 24).
  • Production samples: real conversations, with consent, minimisation and PII handling decided in advance (Chapter 21).
  • Synthetic expansions: model-generated variants of real cases to widen coverage; label a sample by hand.

pm-agent pm-agent's evaluation baseline is a committed file that pins, for the deterministic offline eval, each golden case's verdict and plan-quality rubric score and the injection eval's per-class rates. Any regression fails the build. Two rules make it trustworthy: a changed corpus means the baseline "must be rewritten in its own reviewed commit, so a rate can never be re-based silently", and a deliberate-regression test weakens the guard to prove the check bites.

39.5Simulation

Generic Multi-turn agents cannot be evaluated with single prompts. Simulation pairs the agent with a simulated user (a model playing a persona with a goal and hidden information) and virtual tools (deterministic stand-ins for real systems), then scores the end state. τ-bench established the pattern for customer-service agents; the platforms now offer it as a service: GEAP Agent Simulation (synthetic users and virtualised tools, scoring task success and safety), AgentCore's agent performance loop with user simulation, and Salesforce's conversation testing with simulated customer personas Verify.

Three cautions. A simulator is a model, so it has blind spots and can be too cooperative; check a sample of simulated conversations against real ones. Do not let the simulator and the agent be the same model family if you can avoid it. And keep virtual tools faithful to the real ones, for the same reasons fakes need conformance (Chapter 7).

39.6Online evaluation and drift

Generic Offline sets go stale; production keeps changing. Online evaluation samples live traffic and scores it continuously: GEAP Online Monitors, AgentCore Evaluations, Foundry Control Plane's continuous evaluation (task adherence, groundedness, sensitive data leakage), Agentforce Custom Scorers and Health Monitoring. Add implicit signals: escalations to humans, user edits of the agent's output, retries, abandonment.

pm-agent make eval-drift compares a recent window of runs with the window before it, per class, over the evidence log (each run's rubric criteria and its grounding-control actions), with thresholds in params.yaml. Drift is how you notice a provider's silent model update, a change in user requests or a decaying knowledge source, none of which shows up in an unchanged offline set. ARB's CTL-0021 names the same need: behavioural drift under an unchanged model id is "measured only (evals on schedule)" (Chapter 10).

39.7Replay

pm-agent A technique worth stealing: replay retained live runs through the current guard, with no new model calls. pm-agent's replay (ruling D-PM-P5-t) rebuilds each run's inputs from evidence, re-runs only the plan screen over the stored model output, and writes the result to a new file labelled "replay". Before reading anything, every retained file must match the hash its committed summary recorded and every evidence chain must verify. Values that were minimised to salted digests are restored only when a candidate text re-digests to the stored value; anything else stays an opaque token, so a person's name is never guessed back. And fidelity is checked: replayed with the guard the run was measured under, every outcome must reproduce its recorded verdict. The result is a way to measure a guard change on real model behaviour, cheaply and privately.

39.8Optimizing prompts and agents

Generic Three generations of prompt optimization coexist:

  1. Error analysis by hand. Read failing traces, name the failure modes, fix the biggest. Still the highest-value activity.
  2. Programmatic optimizers. DSPy (Khattab et al., 2023) treats prompts and few-shot examples as parameters tuned against a metric; GEPA (Agrawal et al., 2025) evolves prompts using a model's reflection on failures and reported results competitive with reinforcement learning at far lower cost; TextGrad (Yuksekgonul et al., 2024) propagates textual "gradients".
  3. Platform optimizers. GEAP's Agent Optimizer "automatically clusters real-world failures and suggests refined system instructions" and tool descriptions; AgentCore Optimization offers recommendations, versioned configuration bundles and A/B testing; Salesforce's Agent Optimizer ranks failure patterns by impact; Microsoft's Agent Optimizer was announced for preview Verify.

The third prediction question: an optimizer that maximises your eval score will find the eval's weaknesses. Risks are overfitting to the set (Goodhart's law), regressions on cases outside it, safety instructions trimmed because they cost points, and prompts no human understands. Treat optimizer output as a candidate change: it goes through held-out evaluation, red-team cases and the normal release path, and at CRITICAL it re-signs, because a new system prompt is a new configuration (Chapter 38).

39.9Optimizing the model

Generic When prompts plateau, change the model:

TechniqueWhat it doesWhen it pays
Supervised fine-tuning (often with LoRA or QLoRA adapters)Teaches format, style, domain vocabulary, tool-call conventionsStable task, hundreds to thousands of good examples
DistillationTrains a small model on a large model's outputsHigh volume where a small model's latency and cost matter
Reinforcement fine-tuningOptimises against a grader's reward (for example GRPO, from DeepSeekMath, 2024)Verifiable tasks with a reliable grader

All three clouds and the main model providers offer managed tuning Verify. The governance consequences: a tuned model is a new model identity (pin it, price it, re-gate it); training data needs rights and minimisation; and the injection obey rate and refusal behaviour must be re-measured, because tuning can erode safety training.

39.10Optimizing cost and latency

Target cost per successful task, not cost per call. The levers, roughly in order of effort: shorter and stable prompts (cache hits); output ceilings; fewer, better tools; parallel tool calls where safe; smaller models for routing and extraction; caching of reads; early termination when the answer is known; and finally tuning or distillation (Chapter 9, Chapter 10).

39.13In the room

In the room
  • "Our agent scores 95% on our test set." "On how many cases, over how many runs per case, and how many of them came from last month's failures? Reliability is pass^k on cases that keep up with production."
  • "Can the platform optimize our agent automatically?" "It can propose changes quickly. Each proposal still has to beat a held-out set, pass the red team and go through release, because the optimizer is graded by the same tests it is optimizing."
