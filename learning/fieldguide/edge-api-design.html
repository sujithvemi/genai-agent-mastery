PART V · CHAPTER 25

Edge, request path and API design

Agents are reached through ordinary infrastructure: DNS, load balancers, gateways and HTTP APIs. What is not ordinary is the shape of the work behind them: long, streaming, interruptible runs that may pause for a human and must never repeat an effect. This chapter walks the request path, then designs the run API an agent needs, using pm-agent's API as the worked example.

25.1The request path

Generic Each hop does one job. DNS (often anycast) finds the nearest entry; a global load balancer terminates TLS, applies a web application firewall and spreads load; an API gateway authenticates, enforces quotas and routes; the service does the work. Two rules matter for agents: timeouts shrink inwards (each hop's timeout is shorter than its caller's, or callers give up while work continues unseen), and long work leaves the synchronous path as early as possible. On Google Cloud this is typically Cloud DNS, the global external Application Load Balancer with Cloud Armor, API Gateway or Apigee, and Cloud Run (lab T11).

25.2Run APIs for agents

Generic Model the work as a run resource with a lifecycle, not as a request that returns an answer:

OperationResponseNotes
POST /runs202 Accepted with the run and a Location headerCarries an idempotency key; returns immediately
GET /runs/{id}Run stateStatus, progress, result when done
GET /runs/{id}/eventsEvent streamResumable from the last event id
POST /runs/{id}/cancelRun stateSafe interruption at a step boundary
POST /runs/{id}/approve, /rejectRun state, or 403 or 409Only for a parked run; the approver is a resolved, entitled, distinct subject
POST /runs/{id}/clarifyRun stateThe agent asked the user a question

The second prediction question: 202 says "accepted for processing, not done", which is the truth for work lasting minutes. It must come with the run's identifier and a way to follow it: a status URL, an event stream, or a webhook.

25.3pm-agent's run API, read closely

pm-agent src/pm_agent/api/app.py implements exactly this shape in FastAPI, and its comments show the governance threaded through it:

  • POST /runs returns 202; the run executes in the background and writes a per-run evidence log.
  • GET /runs/{id}/events is server-sent events that tail the evidence log, "so a client sees the same node/tool_call/run events an auditor would, live". The user's view and the auditor's are the same records.
  • A run with publish: true proposes a governed write and parks as pending_approval. /approve resolves the approver through the approval gate; a self-approval (compared as directory subjects, so an alias of the agent counts as self), an unentitled or an unknown approver gets 403 and the run stays parked; a distinct entitled human resumes it and the write goes through the PEP.
  • /reject resumes with no grant, so the PEP denies the write; /cancel stops the graph at the next node boundary with a terminal evidence event, and a parked run can never resume into its write.
  • Calling /approve on a run that is not parked returns 409 Conflict.

Its docstring is candid about scope: "State is in-memory and per-process — fine for a dev API; durable run state is a later concern." That is the starting point for the design exercise in 25.9.

25.4Streaming: SSE, WebSockets, webhooks

MechanismDirectionStrengthWeakness
Server-sent eventsServer to clientPlain HTTP, proxy-friendly, built-in resume with Last-Event-IDOne direction; some proxies buffer
WebSocketsBothInteractive (voice, live steering)Stateful connections; harder to load-balance and secure
WebhooksServer to client's endpointNo open connection; good for system integrationsClient must expose and secure an endpoint; signatures and retries needed
PollingClient pullsSimplest, works everywhereLatency and wasted requests

The third prediction question: give every event a monotonically increasing id, have the client reconnect with Last-Event-ID, and serve the stream from a durable event store rather than from a process's memory. pm-agent already has the durable source (the evidence log); at scale the stream should be served from it through a pub/sub layer rather than by polling a file. Agent UI protocols such as AG-UI standardise these event types for front ends (Chapter 36).

25.5Idempotency

Generic The first prediction question: without protection, two runs exist, and if both reach a write, the effect may happen twice. The standard fix, popularised by payment APIs and being standardised as an Idempotency-Key HTTP header, is:

  1. The client sends a unique key with every non-idempotent request.
  2. The server stores the key with a hash of the request and the response, atomically with creating the resource.
  3. A repeat with the same key and the same request returns the stored response; the same key with a different request is rejected (422 or 409).
  4. Keys expire after a stated window.

Apply it at every layer that can repeat: POST /runs, /approve, and above all each tool write, which needs its own key derived from the run and step (ARB's CTL-0006, idempotency on writes; Chapter 29).

25.6Errors, versioning, pagination

  • Errors: use a consistent machine-readable body, such as RFC 9457 Problem Details (type, title, status, detail, instance), and include the control id when a governance control refused (403 with CTL-0005 tells the caller something actionable; a bare 403 does not).
  • Status codes: 202 accepted; 403 refused by policy; 409 wrong state (approve a run that is not parked); 422 invalid input; 429 with Retry-After when rate limited.
  • Versioning: version the API contract (path or header) and, separately, record the agent's release digest on every run (Chapter 38).
  • Pagination: cursor-based for run lists and event histories.

25.7Three gateways on the path

Generic "API gateway" now names three different things, and an agent system usually needs all three. Mixing them up is the commonest edge-design mistake in agent proposals.

GatewayProtectsTypical controlsWhat it cannot decide
Edge and API gatewayThe agent's API from its callersTLS, WAF, DDoS, token validation (Chapter 27), per-tenant quotas, routing, API versionsAnything about what the agent does next
AI or model gatewayModel budgets, providers and data sent to themToken-based limits per tenant or agent, token metrics for showback, semantic caching, backend pools with priority and circuit breaking (reserved capacity first, spill to pay-as-you-go), content screening, a unified model API, model pinningWhether a tool call is allowed; it sees prompts, not effects
Agent or tool gatewayTools, business systems and other agents from the agentAgent identity and mTLS, MCP and A2A routing, destination allow-lists, tool-level policy, egress control, tool-description pinningBusiness limits that need trusted facts, unless it calls your PDP (Chapter 16)

Generic Two design rules follow. Token limits belong at the AI gateway, because a request counter cannot see that one request is 200 tokens and the next is 200,000 (Chapter 33). And a cache at the AI gateway is a data store: semantic caching returns an earlier answer to a similar question, so its key must include the tenant and the caller's permission scope, and nothing that authorises an effect may be served from it (Chapter 21).

25.8When the caller is another agent

Generic Other agents will call your agent through A2A (an agent card describing skills and authentication, tasks with lifecycle states, streaming) or through tools exposed over MCP. The same API rules apply, with two additions: the caller's identity must be a resolved subject with a channel authorisation (CTL-0017), and nothing the calling agent says carries authority (CTL-0016; Chapter 5).

25.9What changes at scale

Assumption For pm-agent at the scale in its design document (about 50 concurrent runs, 20 seconds to 2 minutes each):

  1. Identity from the token, not the body. The dev API accepts a principal field in the request; at scale the principal comes from the verified token at the gateway (Chapter 27).
  2. Durable run state in Postgres with the checkpointer; any instance can serve any run.
  3. Events from a durable store, fanned out through pub/sub, resumable with Last-Event-ID.
  4. Idempotency keys on POST /runs and the approval endpoints.
  5. Per-tenant quotas at the gateway, sized from tokens per run, not requests (Chapter 33).

25.12In the room

In the room
  • "We already have an API gateway, so we're covered." "Your API gateway protects your services from callers. Agents also need a gateway on the way out: one that counts tokens rather than requests for model traffic, and one that decides which tools and agents each agent may reach. Those are different jobs, and the second is where your policies bite."
  • "Why can't the agent just answer the request?" "Because agent work takes minutes and may pause for a person. We return a run you can follow, stream progress you can resume after a disconnect, and make every retry safe with an idempotency key."
