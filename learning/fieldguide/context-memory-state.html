PART I · CHAPTER 3

Context, memory and state

An agent keeps state in four places with four lifetimes: the context of one call, the state of one run, memory that outlives runs, and the counters and ledgers its controls decide on. Each needs its own design, and the last one is the one most systems forget until a restart quietly resets a rate limit.

3.1Four kinds of state

3.2Context is a budget

Generic Everything the model knows on a given call is in its context: the system prompt, tool definitions, the conversation, tool results, retrieved text. Large windows make it tempting to put everything in. Three costs stop you:

  • Money and latency. Every input token is processed on every call (the "prefill" of Chapter 9). A loop of ten calls over a 200,000-token context processes two million tokens. Prompt caching helps only for a stable prefix.
  • Accuracy. Models use long contexts unevenly. Liu and colleagues showed in 2023 that information in the middle of a long context is used less reliably than information at the ends ("lost in the middle"); Anthropic's context-engineering guidance (2025) calls the broader degradation "context rot". More context is not more knowledge.
  • Attack surface. Every token of untrusted content in the context is a chance to steer the model (Chapter 20). Context minimisation is a security pattern, not only a cost one.

Context engineering is the discipline of putting the right tokens in: retrieval just in time rather than everything up front, compaction of long histories into summaries, tool results trimmed to what the next step needs, and stable content first so caches hit. The harness study found the production coding agents rely on deterministic, just-in-time retrieval (search, syntax trees, file globs, auto-discovered context files) rather than embeddings over code.

3.3Run state and checkpoints

Your build The two builds sit at opposite ends here, deliberately.

  • ARB runs each turn in a fresh session. AdkRuntimeAdapter drives ADK through an in-memory runner and a new session, then collapses the event stream into one result. A turn is self-contained; anything that must outlive it (approvals, counters, evidence) lives in purpose-built stores, never in the framework's session.
  • pm-agent checkpoints its graph. A run is a LangGraph state graph whose state is saved at every step by a checkpointer: in memory in CI, Postgres behind the same seam, exercised against a real database (D-PM-P4-f). That is what lets a run park for a human approval for hours and resume exactly where it stopped, or end cleanly when cancelled.

Generic The choice follows from the work. Request-response agents with short turns are simplest stateless, which also makes them easy to scale horizontally (Chapter 28). Agents whose runs include waits (approvals, long tool calls, external events) need durable run state: a checkpointer or a durable-execution engine (Chapter 26). Do not use conversation history as run state; it is unstructured, unbounded and hard to resume deterministically.

3.4Durable memory

Generic Memory is what an agent keeps across runs so it does not start from zero each time. Useful distinctions, borrowed from cognitive science and common in the agent literature:

KindHoldsExampleMain risk
EpisodicWhat happened in past runs"Last sprint's plan for PLAT was approved with two changes"Stale or poisoned history steering today
SemanticFacts learned"Team PLAT uses Story points; MOBI doesn't"Wrong facts persisting; personal data accumulating
ProceduralHow to do thingsSkills, playbooks, learned preferencesAgent-authored instructions that become standing commands

Memory needs two policies: a write policy (what is worth remembering, by whom, with what redaction, for how long) and a read policy (when to recall, how much, and how far to trust it). Managed memory services (Vertex AI Memory Bank, Mem0, Zep, graph memories such as Graphiti on Neo4j) differ mostly in how they extract and retrieve; the governance questions are the same for all of them.

pm-agent pm-agent's governed memory answers those questions concretely: every record is scoped by principal, project and kind; PII is redacted before write with check-digit validation; time-to-live is bounded to 30 days; records are MAC-signed with a key that has no development fallback; and without a key, memory is retrieval hints only, never planner notes (D-PM-P5-i, -l, -p). Chapter 21 covers the design in detail. The principle to carry: memory is untrusted input that arrives later. Text an attacker got into memory last week is as dangerous as a poisoned document today, unless its integrity and provenance can be verified.

3.5Control state

Your build The fourth kind of state is the one GAP-20 found. ARB's rate and value budgets (CTL-0007), its idempotency dedup window (CTL-0006), its approval-fatigue ledger and its approval-redemption ledger (RT-01) all lived in process memory. D38 put the consequence in one sentence: a rate limit a restart clears is a rate limit an attacker who can cause a restart can reset. In a multi-replica deployment it is worse: each replica has its own counter, so the limit multiplies by the replica count.

D42's fix is one seam for all four ledgers, StateStore, with three operations: read, keys and transact. All four ledgers reduce to the same shape (a small document keyed by an identifier, changed by a pure function of its current value), and transact runs that change inside the backing store's own transaction (a Firestore transaction in the shipped binding; a Redis WATCH/MULTI/EXEC loop or a SQL row lock would do the same). Two replicas racing on the same key can no longer both read the old value and both win. The Firestore binding has been exercised against a real project, and a contended transaction refuses with a named error rather than proceeding.

Honest limit, stated in the seam

transact closes lost updates. It does not make a rate limit exact under a race between two replicas deciding at the same instant, because the policy decision reads the counter and the increment runs after the decision allows: two steps, as in every optimistic rate limiter. The seam's docstring says so. For a limit that must be exact, reserve before deciding (decrement a token bucket atomically, then decide) and release on refusal.

Two further details are worth copying. Stores are per agent by default, because the point is one agent's ledger surviving restarts and being shared by its replicas, not agents sharing ledgers. And the general principle from D38 applies beyond counters: a stateful control is only as trustworthy as the durability and tamper-resistance of its state, the same lesson as an evidence anchor kept in a file the attacker can also truncate.

3.6Alternatives

DecisionOptionsTrade-off
Context assemblyLoad everything · retrieve up front · retrieve just in time · compactionJust-in-time keeps context small and fresh at the cost of more calls; compaction trades fidelity for length
Run stateStateless turns · framework session · checkpointer · durable-execution engineStateless scales simply; checkpoints enable waits and resume; durable execution adds retries and timers at more operational cost
MemoryNone · per-session · durable vector · durable graph · managed serviceDurable memory adds value and risk together; add it with scope, redaction, expiry and integrity, or not at all
Control stateIn process · shared cache · transactional storeOnly a transactional, durable store is safe for security-relevant counters

3.8In the room

In the room
  • "Where do your agent's limits live?" If the answer is the application process, ask what happens on restart and with two replicas.
  • "Should our agents remember users?" "Only with a scope, an expiry, redaction before write and a way to verify a memory wasn't planted. Otherwise memory is a privacy store and an injection channel."
