PART V · CHAPTER 27

AuthN and AuthZ end to end

Every agent request involves at least three identities: the human who asked, the agent acting, and the systems it calls. Getting authentication and authorisation right end to end is ordinary security engineering, done carefully, plus one agent-specific problem: carrying the human's authority through the agent without either losing it or inflating it. Chapter 18 treated this as governance; this chapter treats it as system design.

27.1AuthN, AuthZ and the agent in between

Generic Authentication establishes who is calling; authorisation decides what they may do. In an agent system both happen at several boundaries: the user to the agent's API, the agent to the model and tool gateways, the gateways to business systems, and agents to each other. At each boundary there is a caller (often the agent's workload identity) and, usually, a subject on whose behalf the call is made (the user). Confusing the two is the root of most agent authorisation bugs.

OpenID Connect adds an ID token that says who the user is; OAuth access tokens say what the bearer may call. Do not use ID tokens to call APIs.

27.3Validating a token properly

Generic The first prediction question: a valid signature is the start, not the end. Check:

  • Algorithm pinned to what you expect (reject none and unexpected algorithms; never let the token choose).
  • Key from the issuer's published key set, selected by kid, cached with rotation.
  • Issuer (iss) and audience (aud): the token was issued by the expected authority for this service. A token minted for another API must not work here.
  • Time: exp, nbf, iat, with small clock skew.
  • Scopes and claims needed for this operation.
  • Binding where used (DPoP or mTLS-bound tokens).

Then resolve the subject: map the token's identity to one directory subject, so that aliases, emails and object ids are the same person. ARB's D33 does this because its red team found that "many spellings" of one principal could split budgets and separation-of-duties checks; pm-agent compares approvers and executors as directory subjects for the same reason.

27.4Sessions or tokens

Generic Browser front ends are safest with a server-side session (an HTTP-only, secure cookie) and a back end that holds the tokens: the back-end-for-front-end pattern. Tokens in browser storage are exposed to script injection. Machine clients and agents use short-lived tokens. Either way, the agent's API should receive an authenticated identity from the gateway or session layer, never from a field the client fills in; pm-agent's dev API takes principal in the request body, which is acceptable only because it is a development server (Chapter 25).

27.5Service and workload identity

  • No long-lived keys. Workloads get short-lived credentials from the platform: GCP service accounts with attached identity, Workload Identity Federation for external workloads and CI (your M0 pipeline), AWS IAM roles, Azure managed identities.
  • Per-agent identity where the platform offers it (GEAP Agent Identity, Entra Agent ID, AgentCore Identity), so each agent has its own least-privilege grants and audit trail (Chapter 37).
  • SPIFFE provides a standard workload identity format and X.509 or JWT credentials across platforms; GEAP's agent identities are SPIFFE ids.
  • mTLS between services authenticates both ends; in a service mesh it is automatic.

Agent systems need all three: roles for coarse access, attributes for business limits (refund amounts, tiers), relationships for data permissions (which projects a user can see in Jira). Lab T08 implements one rule in OPA, Cedar, AGT and OpenFGA.

27.7Where decisions belong

The third prediction question:

  • At the gateway: coarse checks that need only the token (authenticated, right audience, scope present, tenant quota).
  • In a PDP: anything that needs business facts, such as whether this user may approve this refund (an entitlement, a limit, separation from the requester). The PDP reads trusted facts through a PIP and records the decision (Chapter 16).
  • In the data store: row-level permissions that the store enforces itself, as a backstop.

Decide once, enforce at every hop that matters, and never let a downstream system assume an upstream check happened.

27.8Delegation chains

Generic The second prediction question: a new token, obtained by token exchange, that represents "this agent acting for this user", scoped to the operation and short-lived. Passing the user's own token onward gives every downstream system the user's full authority and loses the fact that an agent was involved; using the agent's own broad token inflates the user's authority to the agent's. The rules from Chapter 18 in system-design form:

  1. Authority only narrows along the chain.
  2. Every hop records both the actor and the subject.
  3. Credentials for downstream systems are held by a vault or gateway, not by the agent's code.
  4. High-risk actions require step-up: fresh authentication or a distinct approver.
  5. An approval is bound to the exact action (pm-agent's approval gate issues a signed grant scoped to the exact write, and the PEP re-verifies it before executing).

27.9Managed services across clouds

Generic "Agent identity" means three different things across vendors, and a design should say which it relies on: a workload identity with agent metadata (a SPIFFE id or a service principal the agent runs as); a directory object with an owner, a sponsor and a lifecycle, so agents can be governed like accounts; and a credential broker that holds users' OAuth tokens for tools and hands out short-lived access on their behalf. Most enterprises will need all three, from more than one vendor.

Generic Two consequences for design. A cloud's agent identity is strongest inside that cloud: its grants are that cloud's IAM, so an agent on Agent Runtime calling Salesforce still needs a broker for the user's Salesforce token. And none of these services knows your business facts; the decision whether this user may approve this refund still needs your PDP (Chapter 16).

Check before quoting

Agent identity is the least settled area in this book's platform coverage: products were announced in 2025 and several features are preview or licensed separately. Before naming one, check its current status, which licence it needs, and whether it covers agents built on other platforms.

27.11In the room

In the room
  • "Will the agent log in as me?" "No. It acts for you with a narrower, short-lived permission that names both you and the agent, so every record shows who asked and what acted."
  • "Does the agent have admin rights to Jira?" "It has nothing of its own in Jira. Each write uses your permission, cut down to the one project and action, and anything risky also needs an approval tied to that exact change."
  • "We use Entra (or Okta). Does that cover agents?" "It covers who the agent is and who you are. It does not decide whether this approval is within your limit; that check lives in our policy layer and reads your HR and finance data."
