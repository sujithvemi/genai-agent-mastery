PART V · CHAPTER 33

Capacity, cost, regions and disaster recovery

The last system-design chapter answers the questions a platform owner and a finance partner ask before an agent goes wide: how much will it carry, what will it cost per run, what should we buy, where does the data go, and what happens when a region fails mid-run. The answers are arithmetic plus a few agent-specific traps.

33.1Capacity is a chain

Generic An agent's throughput is the minimum over a chain of limits, and the model is only one link:

  • Model quota: tokens and requests per minute, per model, per region or endpoint, per project. Input and output tokens are often limited separately.
  • Provider tier: shared on-demand capacity can throttle under load; reserved and priority tiers change that (Chapter 9).
  • Your gateway and workers: concurrency limits, connection pools, memory per in-flight run.
  • Tools and business systems: the order system's API limit is frequently the real ceiling, and it is shared with human users.
  • State and evidence stores: write rates on checkpoints and evidence records, and hot keys (Chapter 28).

Find the narrowest link first. Agents make the chain longer and multiply load on each link by the number of steps per run.

33.2A worked estimate

Assumption Every number below is an assumption for pm-agent at scale, to be replaced by measurements from traces. The structure is what carries over.

# estimate.py — rerun with your own numbers
PEAK_RUNS_PER_MIN = 50        # arrivals in the busiest minute
RUN_SECONDS       = 60
RUNS_PER_DAY      = 20_000
CALLS_PER_RUN     = 15
IN_TOK, OUT_TOK   = 6_000, 400   # per model call
LARGE_SHARE       = 1/3          # calls routed to the large model
PRICE = {"large": (3.00, 15.00), "small": (1.00, 5.00)}  # $ per 1M tokens, illustrative
CACHED_SHARE, CACHE_READ = 0.70, 0.10   # input served from cache; read price vs input price

in_run, out_run = CALLS_PER_RUN * IN_TOK, CALLS_PER_RUN * OUT_TOK
concurrency = PEAK_RUNS_PER_MIN * RUN_SECONDS / 60    # Little's law: L = λW
peak_in_tpm = PEAK_RUNS_PER_MIN * in_run
avg_in_tpm  = RUNS_PER_DAY * in_run / 1440

The first prediction question: 15 × 6,000 × 50 = 4.5 million input tokens a minute. Two cautions on the cost rows: cache writes can carry a premium (on some providers, writing a prefix costs more than reading it), and every lever that changes which model answers is a behaviour change that needs an evaluation (Chapter 39).

33.3Demand shape and what to buy

Generic The second prediction question: almost never. Reserved capacity is cheaper per token only when you use most of it. Break-even utilisation is the reserved price divided by what the same capacity would cost on demand at full use; if your average use of the reservation is below that, on demand is cheaper. With the profile above, a reservation sized at the peak averages 28% utilisation; one at 1.5M TPM averages about 50%, because demand falls to near zero overnight. Two moves raise that: spill the peak to on-demand capacity (which the providers support directly), and fill the trough with deferrable work you control (evaluation suites, replays, nightly digests). Reserve for latency guarantees and for the steady base, not for the peak.

33.4Unit cost and its levers

Track cost per successful run (not per call, not per token), split by agent, tenant and model, and treat the levers as design changes with evaluation gates:

33.5Budgets, quotas and showback

  • Attribute every call. Tag model and tool calls with tenant, agent, version and run so cost can be shown back per tenant and per agent (labels on GCP, cost allocation tags on AWS, tags on Azure, plus your own trace attributes).
  • Enforce at the run, not the invoice. Your builds ARB's CTL-0020 projects every model call at its max_output_tokens ceiling and refuses a request that carries none; pm-agent's CTL-0007 caps fan-out and cost per run. Budgets that only alert after the month ends are reports, not controls.
  • Per-tenant quotas on runs, tokens and tool calls, so one tenant cannot starve the rest (Chapter 29).
  • Alert on cost per run, not only total spend: a prompt change that doubles steps shows up there first (Chapter 31).

33.6Everything that is not the model

  • Workers. Agent workers spend most of their time waiting on models and tools, so CPU-based autoscaling under-scales them. Scale on in-flight runs or queue depth (request concurrency on Cloud Run, KEDA on queue length, target tracking on a custom metric).
  • Telemetry. Full prompt capture is large: 90,000 input tokens a run is roughly 360 KB of text, so 20,000 runs is about 7 GB a day before compression. Store prefix hashes plus the per-step deltas, keep full content in cheaper object storage under a retention policy, and sample what goes to the observability tool.
  • Evidence. Append-only, retained for years; budget for storage and for the verification jobs that read it (Chapter 22).
  • Vector indexes, state stores and egress are usually small next to model spend, but per-tenant indexes multiply fixed costs.

33.7Regions and residency

Generic Separate three questions, because providers answer them separately: where inference runs, where data rests (prompts, sessions, memories, files), and where your telemetry and evidence live.

Two design rules follow. Put the inference location in the approved configuration, because it decides where regulated data is processed; and record where each call actually ran in the evidence record whenever the provider reports it. Your builds ARB's Vertex binding defaults its location to global in src/aicoe/platform/model/settings.py, set from the environment; the manifest's model pin (provider, model, version, thinking budget) does not include it, so neither does the sign-off digest. That is a reasonable default for a reference build and a gap for a residency-bound client: finding F-08 (Appendix G).

33.8Failover for agents

Generic Ordinary DR planning applies: an RPO and RTO per store, replication to match, and drills. Agents add state that ordinary services do not have. The third prediction question in one table:

StateWhat must hold in the other region
In-flight runsCheckpoints replicated within the RPO, so durable runs resume (Chapter 26); runs without checkpoints are failed visibly and re-driven, never silently dropped
Effects already sentIdempotency keys derived from the run and step, not from anything region-local, so a re-driven step cannot refund twice (CTL-0006)
Pending approvalsThe approval request, its bound facts and the approver's grant are readable there, and the keys that sign and verify grants are available there (multi-region or replicated KMS keys)
Evidence chainA hash chain has one writer. Either one region writes and the other takes over from the last anchored head, or each region writes its own chain and both are anchored. The unanchored tail at failover is the detection gap; size it (Chapter 22)
ModelThe pinned model and version are offered there. A fallback model is a different model: it must be evaluated and inside the signed-off configuration, or failover becomes an unapproved change (CTL-0021, CTL-0022; Chapter 38)
Quota and capacityQuota and any reservations exist in the standby region before you need them; a capacity plan that exists in one region is not a DR plan
Policy, registry and memoryPolicy bundles, the agent and tool registry, and memory stores replicated, with their versions recorded so the evidence shows which applied

Active-passive is the usual answer for the stateful core (run state, evidence, approvals), with an active-active stateless edge. Active-active for the core means multi-writer evidence, memory conflicts and shared rate limits across regions; take it on only when the RTO demands it.

33.11In the room

In the room
  • "What will it cost?" "Per successful task, not per call: here is the estimate from traced runs, the narrowest capacity link, and the budget each tenant gets. The run refuses to overspend; it does not wait for the invoice."
  • "Should we buy reserved capacity?" "Only for the steady part of demand, sized to what we will actually use; the peaks go to pay-as-you-go and anything nobody waits on goes to batch at about half price."
  • "If a region goes down, do approvals still work?" "Yes, if we plan it: the pending approval, its facts and the signing keys must be available in the second region, and the model we fail over to must be one you approved."
