Policy as code

The decision point is where a control's trigger becomes executable. Which language you write it in matters less than three disciplines: the rules must fail closed on missing data, they must be testable against a second implementation, and every rule must be reachable by a real request.

17.1What policy as code buys

Generic Writing authorisation rules in a dedicated policy language, evaluated by a decision engine separate from the application, buys five things that matter for governance specifically:

  • Separation of decision from enforcement. The PEP asks; the PDP answers. The same rules can serve an in-process chokepoint, a gateway and a batch audit.
  • Reviewability. A rule a risk owner can read beside the control it implements, in one place, versioned.
  • Testability in isolation. Rules can be unit-tested with fixtures, without running an agent or a model.
  • Engine independence, if you prove it. The control's meaning lives in the catalog, and the engine is a binding, but only a second engine on the same cases can show that.
  • Decision records. Every evaluation can be logged with its inputs and the policy version, which is most of an audit trail.

What it does not buy: correctness. A policy language makes rules explicit; it does not make them right, complete or reachable. The rest of the chapter is about the disciplines that do.

17.3One control, three ways

Your build CTL-0002, "a refund may not exceed the order total", is the clearest comparison, because it is the simplest rule that compares two fields.

Rego

violations contains v if {
	is_write
	amount_minor > resource_total_minor
	v := {
		"control_id": "CTL-0002",
		"reason": sprintf("refund %v exceeds the order total %v",
			[minor_to_text(amount_minor), minor_to_text(resource_total_minor)]),
	}
}

Rules add to a violations set; allow is true only when the set is empty; every fact (amount_minor, resource_total_minor, is_write) is defined earlier through object.get with a conservative default.

Cedar

@id("CTL-0002")
@control("CTL-0002")
forbid (
  principal,
  action == Action::"issue_refund",
  resource
)
when { context.amount_minor > resource.total_minor };

A forbid that overrides the baseline permit. The control id is an annotation, read back from the engine's JSON, so reordering the file cannot mislabel a denial (D22).

AGT at 5.0.0

Not expressible. AGT's conditions need a literal on the right of a comparison, so "field greater than field" never matches. Written as a deny it fails open; written as an allow it denies everything. This is gap G1 in docs/architecture/AGT_INTEROP.md, and it is why the spike expressed 2 of 4 tested refund controls (CTL-0001 and CTL-0003), with full parity on those two. Chapter 47 covers the rest of the spike and the rule for talking about it.

Gotcha

Both Rego and Cedar evaluate JSON numbers as IEEE-754 doubles. In floating point, 34.95 * 100 is 3494.9999999999995, so a rule comparing a refund to an order total in decimal currency will occasionally decide wrongly at the boundary. ARB converts money once, from its decimal string, to integer minor units in the PIP (D17), and both engines compare integers. Do the same for any quantity where equality at the boundary matters.

17.4Writing fail-closed policy

Your build D18 is the rule, and the header of tool_call.rego explains it. default allow := false is necessary and not sufficient, because Rego's undefined semantics make a deny rule that reads a missing field disappear. A bundle written the obvious way therefore fails open on precisely the malformed request you most want refused. The discipline that fixes it:

  1. Read every fact through object.get with a conservative default. Not registered, not verified, no capability, an unrefundable resource, a principal already at quota, the tightest authored cap. If the PIP did not say, assume the worst.
  2. One object entrypoint. data.aicoe.toolcall.decision returns {allow, violations[]}; callers never query partial rules (which can also fault the embedded engine, D17).
  3. Every violation names its control. A refusal without a control id cannot be attributed, counted or audited.
  4. An authored refusal ladder. When several controls refuse one call, all go into evidence, and violation_precedence in params.yaml decides the headline: can you call at all, are you who you say, is the action approved, is the input sane, does the resource permit it, is the money right, are you within quota. Both engines report the same headline (D24).
  5. Portable reason strings. The embedded engine is rego-cpp, a second implementation of Rego; sprintf's %q verb is not portable between it and OPA, so every reason uses %v (D17).
  6. A test for the empty request. It must deny.

The same discipline applies in the Cedar marshaller: every attribute a policy reads is supplied with the same conservative default the Rego bundle uses, because Cedar errors on a missing attribute and an error must also deny.

17.5Testing policy

Policy tests come in five kinds, and a governance-grade suite has all five.

KindAsksIn ARB
UnitDoes each rule refuse its case and allow its counter-case?Policy tests over fixtures; opa test in BT06
Boundary sweepDoes the rule hold at the edges, for every real resource?Ten boundary cases plus one refund at each order's own total, for every order in the fixtures
ParityWould a second engine decide the same?tests/test_policy_parity.py: OPA vs Cedar on the golden set, the boundaries and the sweep
ReachabilityCan every rule actually fire?tests/test_no_dead_policy.py: every fact read has a producer
FalsifierIf the rule were removed, would a test fail?Conformance checks re-block the gate when a binding is removed (demo-gate-flip)

D22 is the reason the parity test exists: not redundancy, falsifiability. The build claims that control semantics live in the catalog and the engine is a binding. If swapping the engine changed an answer, the rules would really be in the engine and the catalog would be decoration. A parity test is how that claim gets the chance to fail. Two details make it honest. The comparison is projected onto Cedar's declared scope, so OPA-only controls are not silently ignored. And a test asserts that CedarPolicyEngine.covers equals what the .cedar file actually annotates, so adding a fifth Cedar rule without widening the comparison cannot quietly escape it.

D22 also explains why only four controls are in Cedar, and the reasoning is a good design rule: a rate budget needs accumulated counters, an approval needs a signature check, and idempotency, minimisation, contracts, chaining and guardrails are not authorisation decisions. "A PDP that pretended to answer those would be the wrong shape." Put in the policy engine what is a decision over facts; put elsewhere what needs state, cryptography or content analysis, and feed the policy the result as a fact.

17.6Policy, data and facts

Generic Three kinds of input meet in a decision, and putting each in the right place is most of policy design:

InputChangesOwned byLives inARB example
RulesRarely, by authored changeControl ownerPolicy source"refund ≤ order total"
ParametersOccasionally, by authored changeControl owner, ratifiedAuthored dataTier refund caps, rate windows, budgets in params.yaml
FactsEvery requestThe PIP, from trusted stateThe input documentOrder total, principal verified, approval verdict

Keeping parameters out of rules means a threshold change is a reviewed data change that cannot alter logic, and it means both engines read the same numbers (the Cedar caps are resolved by the PIP from the same params.yaml the Rego bundle reads). Keeping facts out of both means the policy cannot be fed a convenient world.

pm-agent pm-agent extended the idea to heuristics. Its output guard's vocabulary (verb families, object classes, thresholds) was moved from code into params.yaml as authored data (D-PM-P5-a, ratified), and then the params schema was given floors with ratified samples, so that an edit which weakens the guard fails gov-validate rather than passing quietly (D-PM-P5-e). That is a useful pattern for any tunable control: authored, reviewable, and with a schema that refuses to let it be tuned into uselessness.

17.7Eligibility policy for typed actions

pm-agent The most interesting use of policy as code in either build is pm-agent's ADR-0005, "containment by construction". After a dozen rounds of trying to detect injected steers in free text, held-out acceptance stayed at 56%. The ADR's conclusion is that a detector cannot win that race by design, and it moves the defence into structure:

  • The model may propose effects only as typed actions from a closed union (create_issue, transition, assign, link, label, set_field, comment), each targeting only keys that were actually retrieved.
  • A deterministic, per-project eligibility policy in Rego decides whether the structured state permits each action: a transition to Done needs all subtasks Done; assign only to a directory member with project access, never to a name found in text; link only between retrieved issues; at most N per run.

Policy as code here is not authorising a principal; it is constraining what a possibly-steered model can make happen, using facts the attacker cannot write. The residual is stated honestly: an attacker can still influence which eligible action is suggested, which human approval with provenance then covers. Chapter 20 develops the argument; this chapter's point is that the policy engine is the natural home for that kind of rule.

Waiting on the builds

At R1-S0 the eligibility module is a seam that denies every action (governance/policies/eligibility/eligibility.rego), with the Python boundary failing closed on any error or timeout. When R1-S3 authors the per-action rules and T1 decides which control id an eligibility deny is attributed to (D-PM-R1-15), add the real rules as a fourth worked example beside CTL-0002, with their tests.

Generic At one team, policy is a file in a repository. At an estate, it is a distributed system with its own lifecycle. The questions to answer:

17.11In the room

In the room
  • "Why not just use Microsoft's toolkit?" Say it the D63 way: "At agent-governance-toolkit-core 5.0.0, its policy language expressed 2 of our 4 tested refund controls, with full parity on those 2; make agt-parity reproduces it." Then: it is a strong benchmark and a likely partner; the question is expressiveness against your triggers, which is measurable.
  • "Which policy engine should we standardise on?" "The one your platform team can run reliably. The catalog is the standard; the engine is a binding. If you want proof of that, run a second engine on your top controls for a quarter."
