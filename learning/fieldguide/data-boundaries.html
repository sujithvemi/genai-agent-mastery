PART IV · CHAPTER 21

Data boundaries: what agents may see, keep and move

An agent is a new kind of data path: it reads across systems on behalf of people with different rights, remembers across sessions, writes text into other systems, and leaves records of all of it. Each of those is a boundary, and each needs its own mechanism, because a label policy on documents does nothing about a cache, a memory store, a trace or a ticket comment.

21.1Four questions

Generic Data governance for agents reduces to four questions, each answered by a different mechanism:

QuestionBoundaryMechanisms
What may it see?Retrieval and tool readsLabels and classification; permission-aware retrieval; on-behalf-of entitlements; permission-scoped caches
What may it keep?Context, cache, memory, evidence, tracesScoped memory with redaction and expiry; minimised evidence; traces without payloads; retention
What may it move?Writes, messages, answers, calls to other agents and toolsOutput contracts; display-only free text; DLP at exits; egress allowlists; digests instead of text across agent boundaries
Where may data live?Model endpoints, stores, logs, anchorsRegion pinning; regional endpoints; residency-aware routing; key location

The tiering axis data_sensitivity (none, internal, PII, sensitive/regulated) decides which of these become required controls for a given agent; in ARB, evidence minimisation (CTL-0009) attaches from PII upward.

21.2What it may see

Generic The core rule: an agent acting for a user should see only what that user may see, unless it has a reason and an authority of its own (Chapter 18). In retrieval this means permission-aware retrieval, and there are two ways to build it:

  • Pre-filter: pass the user's entitlements into the search, so only permitted documents are candidates. Correct by construction; needs entitlements the index can filter on (document ACLs mirrored into the index, or a relationship-based authorisation service queried for candidate sets).
  • Post-filter: search everything, then drop results the user may not see. Easier to bolt on; leaks through side channels (result counts, ranking, snippets in logs) and can return empty results when the permitted documents ranked below the cut-off.

Prefer pre-filtering; use post-filtering only as a second check. Relationship-based systems (Zanzibar-style: OpenFGA, SpiceDB) fit this well because document access in enterprises is usually inherited from folders, groups and projects.

pm-agent pm-agent has two controls for this boundary that ARB does not, and they are worth knowing by name. (Note: pm-agent's catalog reuses ids that mean different things in ARB; see Appendix G.) pm-agent's on-behalf-of entitlement propagation is a dedicated PEP step that checks the resource is within the calling principal's project scope before the policy call, with the Rego bundle also refusing an out-of-scope read as defence in depth (D-PM-P3-h). Its permission-scoped cache keys cached Jira reads by the principal's scope, so one user's read can never be served to another. The cache case is the one most teams miss: a read-through cache in front of a system of record is a confused deputy unless its key includes the entitlement.

Your build ARB's knowledge_advisor takes the other path: it reads internal policy documents whose worked examples contain customer names and emails, under its own identity, for internal staff only. That is an acceptable design for an internal-only, read-only, advisory agent, and it is exactly why its derived controls include evidence minimisation and the injection boundary: what it sees is sensitive, so what it keeps and says must be controlled.

21.3What it may keep

Generic Agents keep data in five places, and only one of them is usually designed: the context window (per call), caches (per scope), memory (across sessions), evidence (for audit) and traces (for operations). Each is a store with its own retention, access and leakage path.

pm-agent pm-agent's durable memory (P5-4 and P5-5) is the best worked example of governed memory in either build:

  • Scoped. Every record is keyed by principal, project scope and kind; every caller goes through a GovernedMemory wrapper; there is no unscoped read.
  • Redacted before write. A memory-side PII set runs before a put: email, phone (several international forms), national ids, payment cards (Luhn-checked, so order numbers survive), IBANs (mod-97-checked), person names (using the output guard's person detector) and account identifiers (D-PM-P5-j, -m). The check digits are the clever part: they let the redactor remove real card numbers while leaving lookalike ids intact.
  • Bounded in time. TTLs are validated in the constructor and the params schema: finite, positive, at most 30 days.
  • Integrity-checked. Records are MAC-signed with a memory key from the environment, a key file or KMS. There is deliberately no development key (D-PM-P5-l): a published dev secret would let anyone who can write the store forge a "verified" memory.
  • Degrades to hints. Without a key, memory is a hint: records are stored unsigned, every recall is untrusted, and recalled content may only guide retrieval, never feed the planner as notes (D-PM-P5-p).

The last point is the general lesson: memory is an injection surface across time. Text an attacker got into memory last week is untrusted content this week, and it should be treated with the same suspicion as a document, unless its integrity and provenance can be verified.

21.4Evidence is data too

Your build The audit trail is the store most likely to become a honeypot, because it records everything by design. P1's evidence stored tool arguments and results verbatim, including customer names and emails (GAP-09). ARB's fix went through two steps worth copying:

  1. Structural separation over recognition (D23). Rather than an entity recogniser that tries to find names in text, every free-text field (the model's prose, retrieved snippets, any human-typed reason) moves wholesale into an access-controlled detail store, and only its hash stays in the open log. "No free text in the open log" is then an invariant a test asserts by construction.
  2. An allowlist, not a redaction pass (D25). The default was inverted: a string appears verbatim in the open log only if an authored rule in params.yaml names it as transparent. Everything else, including anything nobody classified, goes to the detail store with a salted marker left behind. Unknown fields fail safe.

Reads of the detail store are gated by the same signed capability that gates tool calls (Chapter 18). And traces follow the same rule through the same policy object: a span never carries arguments or results, and the fields it does carry pass the same redaction (D26), so "no raw PII in traces" is the same guarantee as "no raw PII in the open log", not a second one to keep in sync.

21.5What it may move

Generic Everything an agent writes is a potential exfiltration channel: a ticket comment, an email draft, a summary posted to chat, a URL in a plan, a message to another agent, even a tool call's arguments to an external API. Controls at this boundary:

  • Output contracts on writes: the shape and fields of what may be written (ARB CTL-0010).
  • Display-only free text (pm-agent ADR-0005): written text is sanitised, with no URLs, emails, mentions or markup unless they come from the request or a structured field, and bounded in length. After a review found host and path fragments surviving, the sanitiser was changed to remove whole URLs, scheme-less forms included (D-PM-R1-31).
  • Egress allowlists: which hosts and tools an agent may reach at all, enforced at the network or gateway, not in the prompt.
  • DLP at exits: a test that plants a fake secret and confirms every exit blocks it is the cheapest proof this boundary holds.
  • Digests, not text, across agent boundaries. ARB's cross-agent provenance envelope carries the payload's digest and the upstream record's hash, never the payload text (D40, CTL-0019); otherwise the evidence-minimisation gap would reopen at the fleet boundary.

pm-agent A related ruling settles how to decide which lane data is in. A review found that 8 of 15 novel steers became structured-lane actions because the lane decision depended on the injection fence noticing them. D-PM-R1-30 ruled that a lane is decided by source type, never by a detector: system-of-record fields are structured; all text adopted from a repository or a comment is free text, whatever container it sits in. The same principle applies to data classification generally: classify by where data came from, which an attacker cannot change, not by what it looks like, which they can.

21.6Where data may live

Generic Residency is usually framed as "where the database is". For agents it is at least five places: the model endpoint that processes prompts (and anything it logs), the vector index and document stores, memory and caches, evidence and its anchors, and the observability backend. A design that pins storage to a region and calls a global model endpoint has moved personal data across borders on every turn.

Your build ARB's live GCP setup creates its evidence bucket, Firestore database and Model Armor template in one configured region (AICOE_GCP_REGION, default us-central1, in infra/gcp/setup.sh). That is single-region by construction, which is the right starting point; multi-region and residency-aware routing are design topics for Chapter 33.

Check before quoting

Which models are available in which regions, whether a provider's "regional" endpoint keeps processing and logging in region, and what a provider retains for abuse monitoring all differ by provider and change often. Confirm per model and per region before promising residency.

21.7Erasure versus tamper-evidence

Assumption A tamper-evident log cannot have records deleted without breaking its chain, and data-protection law can require personal data to be erased. ARB's split between the open log and the detail store points at the resolution, although the build does not claim it as an erasure mechanism: if personal data lives only in the detail store, and the open log holds only a salted hash of it, then deleting the detail entry (and its salt) removes the personal data while the chain still verifies. The record that an act happened survives; the personal content does not, and the hash left behind cannot be reversed without the salt. Design evidence this way from the start, and test erasure as a scenario, because retrofitting it onto a log that already contains names is not possible without breaking the chain.

Waiting on the builds

Neither build has an erasure workflow yet, and pm-agent carries a named memory-PII residual to a future DLP seam (D-PM-P5-m). When either lands, replace the assumption in this section with the built mechanism and its test, and add the DLP seam's placement to the "what it may move" list.

21.10In the room

In the room
  • "Our data is labelled, so our agents respect it." Ask whether the agent's retrieval filters by the user's entitlements, whether its cache keys include them, and where the agent's memory, logs and traces live and who can read them.
  • "Can the audit log and the right to erasure coexist?" "Yes, if personal content never enters the tamper-evident log: it holds a salted hash, and the content lives in a separate store that can be erased without breaking the chain."
