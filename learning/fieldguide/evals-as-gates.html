PART IV · CHAPTER 23

Evals as gates

An evaluation measures behaviour that is statistical; a gate makes a decision that is binary. Turning one into the other honestly takes a committed baseline, a scorer that has been shown to reject a wrong answer, a record of which model actually answered, retries that cannot change an outcome, and a decision rule that can tell noise from signal. Where that last one is missing, the honest gate is held.

23.1Two kinds of proof

Generic A release gate for an agent asks two different questions, and conflating them is the most common eval mistake in governance:

ConformanceEvaluation
QuestionDoes this control fire when it should?How well does the agent do its job, and how safely?
NatureBinary, deterministic, per controlStatistical, over a dataset, with thresholds
Model in the loop?Usually not: a scripted or hostile model drives the planeYes: the pinned model, offline and live
A 95% result meansThe control is brokenPossibly fine, depending on the baseline and the task
ChapterChapter 24This one

The gate needs both. A refusal control that works 95% of the time is not a control; a planning agent that produces the best plan 95% of the time may be excellent. Keep the two in separate suites, with separate reports, so a number from one is never read as the other.

23.2Anatomy of an eval

Generic Every eval has the same parts, and each part has a way to be wrong:

PartWhat it isHow it goes wrong
DatasetCases: golden (expected outcomes), held-out (never tuned on), adversarial (attack corpus), live (real or seeded systems)Tuned on; too small; drawn from the builder's imagination rather than real requests
RunnerExecutes the agent per case, with a pinned model and recorded configurationModel alias moves; another model answers; retries change outcomes
ScorerDecides per case: exact match, rubric, programmatic check, model-as-judgeNever shown to reject a wrong answer; judge bias
MetricAggregates: pass rate, mean score, pass^k, cost and latency per taskAverages hide the critical failures; one number for many behaviours
Baseline and thresholdWhat "good enough" and "no worse than before" meanChosen after seeing results; never committed
ReportThe artifact the gate readsHand-edited; not tied to the configuration that produced it

For agents, add trajectory evaluation: did the agent use the right tools, in a sensible order, with the right arguments, and stop when it should? An agent can reach the right answer by an unsafe path (reading data it did not need, calling a write tool and having it refused), and an outcome-only score will never show it. Evidence records make trajectory scoring cheap, because every tool call and decision is already recorded with a control id.

23.3Golden sets and rubrics

Your build ARB's golden set (evals/golden/) is a set of customer-service cases with expected outcomes, reported as a pass count at every phase tag. D56 is the cautionary tale every eval owner should know. Applying the rule that every proof must be checked by disabling what it proves, the build made the golden scorer return nothing, and every case still passed: since P1, "golden 25/25" had been reported at every tag, yet no test had ever shown the scorer rejecting a wrong outcome. The number was true; nothing showed it could have been false. The fix is a falsifier test that feeds the scorer known-wrong outcomes and requires it to fail them.

pm-agent pm-agent scores plans with a rubric (evals/rubric.py, D-PM-P5-o): per run, whether the plan is grounded, what share of items cite only retrieved keys, whether the request was resolved, and whether the plan passed the critic; the mean is the score. A rubric of named, checkable sub-scores beats a single "quality" judgement because each sub-score can regress independently and each has an obvious falsifier.

23.4From measurement to gate

pm-agent pm-agent's WS-E (D-PM-P5-o) is the clearest example of turning an eval into a gate. The problem it fixed: the eval measured, but nothing pinned the measurement, so a weakened guard or a drop in plan quality would pass CI. The fix has four parts:

  1. A committed baseline (evals/baseline/): the expected scores per case, in the repository, changed only by a reviewed commit.
  2. A blocking comparison (evals/baseline.py): CI compares each run to the baseline and fails on regression beyond a stated tolerance.
  3. Weakenings pinned (D-PM-P5-r): known ways of weakening the guard are encoded as cases, so a semantic weakening fails CI instead of passing the baseline. A review had shown one such weakening (W2) passing.
  4. Warn-only where the metric is not yet trustworthy: the guard's block rate is reported and warned on, not gated, because blocking on it would penalise legitimate caution.

23.5Live runs, honestly

pm-agent Offline evals use scripted or fake models; live evals use a real one, and that is where pm-agent found that the eval could be measuring the wrong model. A live summary recorded the requested model id, while the local server had just-in-time loaded a different model to answer; the run could not be told apart from a genuine one. The rulings (D-PM-P5-r, -s):

  • Record the model that answered, not the one requested, and exclude any run where they differ.
  • One model at a time: the preflight refuses when the requested model is not listed or more than one chat model is loaded, and records the model listing snapshot with the run.
  • A cause on every block: each quarantine or block in a live run carries its cause, so a rate is explainable.

Your build ARB's live runs on Vertex met rate limits (HTTP 429), and D71 ruled exactly when a retry is allowed, in a way that generalises to any eval against a metered provider:

  • Retry only on the rate-limit error class, and only if no effectful tool call completed in that attempt. A 429 after an effect aborts the case.
  • Each retry runs from a fresh plane; at most three attempts per turn, with backoff of 120, 240 and 480 seconds, and at most ten retries per measurement.
  • Every attempt and the full error body are recorded in the artifact.
  • If the provider shows a fixed per-day or per-minute limit, no retry: request a raise (a human act) and run on a fresh day.

The reasoning is in one line of D71: the retry is keyed on the error class and never on an outcome, and an attempt that failed produced no decision, so the control is no weaker. A retry keyed on outcome ("run again until it passes") is how evals lie.

23.6Non-determinism and statistics

Generic An agent's decision on the same input varies between runs: sampling temperature, provider-side batching and non-deterministic kernels all contribute. Three consequences for gating:

  • One run is an anecdote. Measure each case K times and report the distribution. Distinguish pass@k (at least one of k runs succeeds, a capability measure) from pass^k (all k succeed, a reliability measure). For a governed agent, reliability is usually what matters.
  • Size K for the decision. To tell a 90% agent from an 80% agent with reasonable confidence you need dozens of runs per comparison, not five.
  • Pre-register the decision rule. Write the test, the alpha, the minimum effect size and K before running. Choosing a threshold after seeing the result fits the gate to the outcome.

Your build D74 is a worked example of what happens without these, and of the right response. The fairness criterion as first specified said a matched pair diverges if its two members' sets of decisions over K = 5 runs differ at all, with a threshold of zero divergent pairs. T1 computed what that criterion does to a perfectly fair agent whose decision on a scenario is simply stochastic with per-run probability p:

The first live measurement found divergence in 3 of 8 pairs (0.375). Under that criterion the gate would block, and the block would mean nothing, because it cannot separate sampling noise from a proxy effect. D74 rejected both easy exits (binding the gate, which turns noise into a deployment block; or lowering the threshold after seeing the result, which fits the gate to the outcome) and held the control. It also refused to discard the finding: one pair (FP-08: an English-preference persona escalated to a human in 3 of 5 runs, a Spanish-preference persona in 0 of 4; Fisher two-sided p ≈ 0.17) is not significant at this sample size but concerns exactly the consequential decision the control exists to protect, so it is named as the signal to investigate.

The new decision rule (backlog BL-40) is the textbook answer, and worth memorising as a template: A/A null pairs (identical personas) to measure the noise floor; a per-pair test with a stated alpha and minimum effect size; K sized for power; decisions compared as rates, not sets. A second backlog item (BL-41) records that the noise source is inconsistent decisions on the same case, which is a correctness finding in its own right.

23.7Fairness: measured, held

Your build The fairness control (CTL-0027, authored and held outside the active catalog) measures matched pairs: personas identical except for an attribute proxy (name origin, preferred language), run through the same scenarios, with the artifact signed and bound to a digest of its inputs (model pin, instructions, tools, population, parameters) so a fairness result is current only while those are unchanged. Its state is the important lesson. D74's wording rule for anyone speaking about it: "Fairness is measured, not yet gated: our first live measurement (2026-10-17, synthetic matched pairs) found differences we are investigating, and the gate criterion is being redesigned to separate sampling noise from bias." Never "fair", "bias-free" or "fairness-gated".

Generic That sentence is a model for any measurement-based claim a governance programme makes. State what was measured, when, on what population, what was found, and what is not yet established. A held gate with an honest sentence is more credible to a regulator than a green gate with a criterion nobody can defend.

Waiting on the builds

When the fairness decision rule is ratified and a re-measurement runs, add the A/A noise floor, the per-pair results under the new rule, and whether CTL-0027 was bound or retired. 23.11In the room

In the room
  • "Our agent scores 92% on our eval." Ask: on a held-out set someone else wrote? Against which committed baseline? Has the scorer ever been shown to fail a wrong answer? Which model actually answered?
  • "Is your agent fair?" Use the D74 sentence: what was measured, when, on what, what was found, and what is not yet established.
