PART VI · CHAPTER 36

Tools, integration, sandboxes and computer use

An agent can only do what its tools let it do, so tools are where usefulness and risk are both decided. This chapter covers how to design tools a model uses well, the paths by which enterprise systems become tools, how to run MCP as a managed fleet, how to give an agent a computer (a code sandbox, a browser, a desktop) without giving it your network, and the newer protocols for agent interfaces and agent payments.

36.1Tools are the agent's reach

Generic Classify tools by what they let the agent do, because the class sets both the design and the controls:

ClassExamplesTypical controls
ReadSearch, database queries, CRM and ticket lookups, retrievalCaller's permissions, data classification, result screening
Reversible writeDraft an email, create a ticket, commentPolicy check, idempotency, evidence
Irreversible or financial writeRefunds, payments, deletions, sending external messagesTrusted-fact policy, value limits, approval, evidence before effect
ComputationCode execution, data analysisSandbox isolation, no ambient credentials, egress limits
Environment controlBrowser and computer use, shellIsolated environment, separate identities, human takeover
DelegationCalling another agent (A2A), spawning sub-agentsEdge declaration, provenance, no transitive authority (Chapter 5)

36.2Designing tools for models

Generic A tool is an interface whose user is a model. Anthropic's engineering guidance, "Writing effective tools for agents" (2025), and the experience of both builds agree on a short list:

  • Fewer, larger-grained tools. One schedule_meeting beats list_users, list_events and create_event chained by the model. Each extra tool costs context and adds a decision the model can get wrong.
  • Names and descriptions are prompts. They are read on every call. Say when to use the tool, when not to, and what it returns.
  • Typed, narrow parameters. Enumerations instead of free text; identifiers the system can verify, not names it must guess (Chapter 2).
  • Return what the model needs, not everything. Truncate and paginate; return meaningful identifiers and a short summary; make error messages say what to do next.
  • Separate reads from writes and declare the effect class, so policy and tiering can see it.
  • Make writes idempotent with a key the caller supplies, and offer a dry-run or preview mode for consequential actions.

The first prediction question: with 80 tools the context fills with descriptions, selection accuracy falls, and similar tools get confused. Fix it by consolidating tools, by tool search (retrieve the few relevant tools per task; Microsoft Foundry and others now offer it as a service), or by packaging procedures as skills that are loaded only when needed.

36.3Integration paths

Generic Enterprise systems become tools by one of five paths:

PathHowUse when
Direct API toolA function in the agent's code calls the system's APIOne agent, one system, simple auth; hardest to govern at scale
MCP serverThe system's capabilities are published as an MCP server (vendor-supplied or your own)Reuse across agents and frameworks; the default for new integrations
Gateway-generated MCPAn API gateway turns existing REST APIs or functions into MCP tools: AgentCore Gateway (APIs, Lambda, services), Azure API Management (expose REST as MCP), GEAP Agent Gateway and connectors, ApigeeMany existing APIs; central auth, quotas and logging
Integration platformiPaaS flows (MuleSoft, Boomi, Workato, Google Application Integration) exposed as toolsMulti-step business transactions that already exist as flows
Agent-to-agentAsk another team's or vendor's agent through A2AThe other side owns the logic and data, for example a SaaS agent

Your builds pm-agent reaches Jira through an Atlassian MCP binding for reads and a separate write adapter, each behind a seam (platform/jira/). ARB publishes its tools on a FastMCP server behind the tool gateway, so the same tools serve in-process ADK and out-of-process framework hosts (Chapter 35).

36.4MCP at fleet scale

Generic One MCP server is a convenience; two hundred are an estate. Running MCP at scale needs five things:

  1. A registry with approval. Only registered, reviewed servers are reachable. GEAP's Agent Registry and AWS Agent Registry both register MCP servers alongside agents and skills; Azure API Center does the same for APIM-managed servers Verify.
  2. Authentication per the specification. Remote MCP uses OAuth 2.1; agents acting for users need delegated (on-behalf-of) tokens, ideally held by a vault or gateway rather than the agent (Chapter 18).
  3. Integrity of what the model sees. Tool descriptions are instructions to the model. ARB's CTL-0024 hashes each tool's canonical name, description and schema and withholds any tool whose hash changes after review (a "rug pull"); re-pinning needs a reviewer who is not the requester (make demo-mcp-rugpull, make gov-mcp-repin).
  4. A gateway in the path for rate limits, logging, policy and content screening: platform gateways (GEAP Agent Gateway, AgentCore Gateway, APIM) or data-platform ones (Snowflake Cortex AI Gateway, Databricks Unity AI Gateway, ServiceNow's AI Gateway for MCP).
  5. Selection, not exposure. Give each agent the tools its manifest declares, not the catalogue.

36.5Code-execution sandboxes

Generic Letting a model write and run code is the most powerful tool and the most dangerous. The sandbox must assume the code is hostile, because injected content can make it so. Isolation comes in grades:

IsolationMechanismTrade-off
ProcessSeparate process, restricted user, seccompFast, weak; shared kernel
ContainerNamespaces and cgroups; gVisor adds a user-space kernelCommon; kernel exploits are the risk without gVisor
MicroVMFirecracker-style lightweight virtual machinesStrong isolation, fast start; what several managed services use (AgentCore Harness sessions run in isolated microVMs)
Language isolateWebAssembly or V8 isolatesVery fast, limited language support

Managed options: GEAP Code Execution and Agent Sandbox (shell and computer-use sandboxes GA in September 2026), AgentCore Code Interpreter (Python, JavaScript, TypeScript), Azure Container Apps dynamic sessions, the code-execution tools of OpenAI and Anthropic, and specialists such as E2B, Daytona and Modal Verify. Whatever the isolation, the controls are the same:

  • No ambient credentials. Nothing in the sandbox can reach your cloud with the agent's identity. Anthropic's managed agents keep credentials out of the sandbox entirely and broker tool access through a proxy.
  • Egress allow-lists, or no network at all.
  • Resource limits on CPU, memory, time and disk.
  • Ephemeral by default; files that must persist are copied out deliberately and scanned.
  • Evidence: the code that ran and its outputs are recorded.

36.6Browser and computer use

Generic Browser and computer-use agents operate interfaces built for people: clicking, typing and reading screens. Managed browsers (AgentCore Browser, GEAP computer-use sandboxes) and model-native computer use (Anthropic, OpenAI, Google) make this practical for systems without APIs. They are also the most exposed agents you can build, because every web page is untrusted input and the action space is unbounded.

  • Credentials (the second prediction question) live in a vault or the platform's identity service and are injected into the session for the specific site, never placed in the prompt or visible to the model. Use dedicated accounts with the narrowest rights, not a person's own login.
  • Isolation: a fresh browser profile per session, in a sandbox with egress rules.
  • Constraints: an allow-list of domains, no downloads or uploads unless required, and confirmation before submitting forms that commit to anything.
  • Human takeover for logins, CAPTCHAs and consequential steps.
  • Identification: standards such as Web Bot Auth (supported by AgentCore Browser) let sites recognise a legitimate agent rather than treat it as a scraper.
  • Prefer an API. A browser agent is a bridge to systems without one, not the target architecture.

36.7Agent UI protocols

Generic Agents increasingly drive interfaces rather than return text. Three approaches have emerged Verify:

ApproachWhat it isGovernance note
AG-UIAn open event protocol (from CopilotKit) for streaming agent state, messages and tool activity between an agent back end and a front end; supported by AgentCore Runtime and several frameworksThe event stream can carry approval requests; render them in a trusted component
A2UIGoogle's protocol for agents to return declarative descriptions of UI components that the client renders from its own trusted librarySafer than letting a model emit HTML or script: the client decides what can render
Apps on MCPInteractive components delivered with MCP tool results (for example OpenAI's Apps SDK)Treat embedded UI as third-party content; sandbox it

Whatever the protocol, the approval surface for a consequential action must show the facts the decision rests on, not the model's summary of them (Chapter 19).

36.8Agent payments and commerce

Generic 2025 and 2026 produced a set of protocols for agents that buy, sell and pay Verify:

ProtocolOriginLayerMechanism
AP2, Agent Payments ProtocolGoogle Cloud and partners, September 2025Payment authorisationCryptographically signed mandates (intent, cart, payment) that prove what the user authorised; an extension of A2A
UCP, Universal Commerce ProtocolGoogle and Shopify, January 2026Commerce workflowOne schema for catalogue, cart, checkout, inventory, fulfilment and orders
ACP, Agentic Commerce ProtocolOpenAI and Stripe, September 2025Commerce workflowCheckout within a chat assistant; reportedly narrowed to product discovery in 2026. Not the same ACP as the Agent Client Protocol in Chapter 5.
x402 and MPPx402 from Coinbase; MPP, the Machine Payments ProtocolMachine-to-machine micropaymentsPay per request over HTTP 402; supported by AgentCore Payments with spending limits and managed wallets (GA August 2026)

The third prediction question has a simple answer: a payment is an irreversible financial write, the top of the action scale, whatever its size. Many small autonomous payments add up, so the controls are the ones your build already has for refunds: per-transaction and per-window value limits on trusted counters (CTL-0007), a declared set of payees, evidence before effect, and approval above a threshold. Signed mandates help: they are evidence of what the user authorised, which is exactly what a dispute needs.

36.11In the room

In the room
  • "Should every team build its own MCP servers?" "Build them once per system, register and review them centrally, put a gateway in front, and let agents use the ones their manifests declare."
  • "Can the agent just use the website?" "It can, in an isolated browser with its own narrow account and a person on call for the hard steps. Treat it as a bridge until the system has an API."
  • "Can agents pay for things?" "Yes, with the same controls as any financial write: limits, declared payees, evidence before the payment and approval above a threshold. Signed mandates are your evidence of what the customer authorised."

  2. RecallThe five things MCP needs at fleet scale.
  3. ApplyLab T05: wrap one ARB tool as an MCP server and call it from two frameworks; then change its description and watch CTL-0024 withhold it.

Card candidates: a tool description is a prompt · no ambient credentials in a sandbox · a payment is a financial write at any size.
