Preface

This book exists because a principal architect of agent systems has to hold three jobs at once, and the material for each lives in different places: vendor documentation, papers, system-design books, governance frameworks, and, most usefully, the decisions inside systems you have actually built.

Design it

Choose the harness, the protocols, the enforcement points, the data boundaries and the system around the agent, and know what each choice costs.

Defend it

Answer a CISO, an auditor, a regulator or an interviewer from evidence: which mechanism, which test, which decision, which residual risk.

Build it for someone else

Turn a working reference into a framework and toolkit for a client estate that runs on platforms you don't control.

The two builds behind the book are aicoe-reference-build (ARB), a governed agent fleet with a hand-authored control catalog, an enforcement plane, an evidence plane and live GCP bindings, and pm-agent, a governed product that plans and acts on Jira, forked from ARB's chassis and evolved separately. Both were written mostly by Claude Code under your direction. That is the reason for the book: the decisions are yours, the code is not yet, and a field guide that walks the reasoning, points at the code and asks you to defend it is the shortest path to owning both.

The book is opinionated where the builds took a position, and says so. Where it gives general guidance it is labelled as such; where it states an assumption it is labelled too. Facts about products, versions and law change fast; those carry a Verify tag and a date.

How to read it

The method is consume first, then defend, the same one the Learning OS uses. A chapter is the consume step. Answer its "Predict first" box before reading, read the chapter whole, then answer its "Prove it" questions cold, or do the rep it names, and check with prompts/REP_SESSION.md. Cards come only from what you defend. A chapter explains the design and points at the code; walking the code yourself is still the rep's job.

The book on one page

Fifteen ideas. Every chapter expands at least one, and most come with a decision in your builds you can point to.

  1. An instruction is not a control.A control is a deterministic mechanism on the only path to the effect, plus a test that proves it refuses. The first live agent checked the order and refunded anyway. (Chapter 16)
  2. Mediate completely, then prove the layers agree.Every side effect passes one chokepoint; agents you didn't build go through a gateway that drives the same plane, and an equivalence test shows both paths decide the same way. (Chapter 16, Chapter 45)
  3. Decide on facts, never on the agent's account.The information point re-reads trusted state. An asserted value is named as asserted and nothing decides on it. (Chapter 16, Chapter 18)
  4. Fail-closed takes work.Policy languages fail open on missing data unless every read has a conservative default, and a rule that can never fire is a comment, not a control. (Chapter 17)
  5. Author for the fleet, derive for the agent.Each control states its own lowest tier and the shape it applies to; each agent's control set falls out of its honest scores. (Chapter 13)
  6. Govern nodes by tier and edges by shape.Agents keep their own tiers when they connect; the connection is a governed object, and a message from another agent has no authority. (Chapter 5, Chapter 13)
  7. Evidence before effect, and no unrecorded effect.Record the decision first; reverse an effect whose record fails; derive traces from evidence through one redaction policy. (Chapter 22)
  8. Change is a risk event.Tiers are derived on every gate run and sign-off is bound to a configuration digest, so a new model, tool or policy re-enters the lifecycle by itself. (Chapter 15)
  9. Probabilistic checks may only restrict.A model-based classifier can add a hold, never an allow; composition is max(ALLOW < HOLD < DENY). Structure beats phrase lists. (Chapter 20)
  10. A gate you can't defend is held, not passed.If a criterion cannot separate signal from noise, the honest status is "measured, held". The fairness gate is the worked example. (Chapter 23)
  11. The agent is only as good as the system around it.Edge, auth, state, reliability, deployment and cost decide production value; cleverness does not survive a bad request path. (Part V)
  12. An agent is a product with a lifecycle.Code, prompts, model pin, tools, policy and eval sets version and release together; quality is measured continuously, not once; models get deprecated and frameworks move, so maintenance is planned work; and retirement is a designed event. (Chapter 38, Chapter 40)
  13. Platforms supply enforcement points; the rulebook is yours.Learn the managed services of every major platform, because clients run on all of them. Centralise rules, registry and evidence; federate enforcement to each platform's native controls plus a shared checkpoint in front of the systems that matter. (Chapter 45, Appendix I)
  14. Read every framework through a build.A toolkit, a standard or a law is understood when it is mapped to your components and the overlap is measured; claims about it are versioned and reproducible, and coverage is four numbers, never one. (Chapter 47, Chapter 48)
  15. Start from what is running.Inventory, tiering, approvals and a kill switch on the riskiest agents come before any target-state design; the operating model's job is to make the governed way the fast way. (Chapter 51, Chapter 50)

About this edition

The chapter files live in genai-agent-mastery/learning/fieldguide/ and are published here from that folder. A small build script keeps chapter numbers, cross-references, section and figure numbers, and the living register consistent, so chapters can be reordered without broken links. Facts read from the builds carry the date they were read; when a build module changes, the chapter that cites it is due a refresh, and Appendix H says what each chapter is waiting for. Things found wrong while writing, in the builds or the learning system, are listed in Appendix G.

Four appendices assemble themselves from the chapters at every build, so they cannot drift: the reading map (Appendix E), the card bank (Appendix F), the living register (Appendix H) and the foundation half of the service map (Appendix I). The control catalog (Appendix B) and the decision index (Appendix D) are generated from the builds' own files by the scripts in tools/. A PDF edition (one file, A4, with bookmarks and working internal links) is published beside this page for offline reading and printing; tools/make_pdf.py regenerates it.
