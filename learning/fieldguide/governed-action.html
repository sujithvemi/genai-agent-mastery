The governed action

What happens, in order, between a model deciding to call a tool and that call changing a business system, and which parts of that path make governance a mechanism instead of a hope.

16.1An instruction is not a control

Your build The most useful single observation in ARB came from its first live run (P1). The ungoverned customer-service agent, running on a local model, called get_order to check the order, received the answer, and then issued the refund anyway. It performed the check and ignored the result. The comment that opens pip.py records the lesson in one line: performing the check is not the control; acting on it is.

Generic That is the whole case for this chapter. A system prompt saying "never refund more than was paid" is a request to a probabilistic component. It will be honoured most of the time, and "most of the time" is not a property you can put in front of an auditor or a regulator. A control is a deterministic mechanism on the only path to the effect, which refuses the bad action whatever the model wants, plus a test that proves it refuses. Everything else in Part IV (policy, identity, approval, guardrails, evidence) plugs into the mechanism described here.

16.2Four roles: PEP, PDP, PIP, PAP

Generic The vocabulary comes from attribute-based access control (XACML, and NIST SP 800-162). It is worth using exactly, because vendors, auditors and your own builds all map onto it, and because separating the roles is what lets you change one without touching the others.

RoleJobMust neverIn ARB
PEP · enforcement pointSits on the path; intercepts the call; asks for a decision; enforces it; records itContain business rules; be bypassablechokepoint.py (ToolChokepoint) plus the runtime hooks in enforcement/plane.py
PDP · decision pointEvaluates policy against facts; returns allow/deny with reasonsFetch its own facts; have side effectsgovernance/policies/rego/tool_call.rego via the PolicyEngine seam (OPA/Rego by default; Cedar for parity)
PIP · information pointAssembles the facts the policy reads, from trusted sourcesDecide anything; trust the caller's accountenforcement/pip.py (PolicyInformationPoint)
PAP · administration pointWhere policy is authored, reviewed, versionedLive only in code reviewers can't readRoot governance/: catalog YAML, params, Rego, authored by you (ADR-0001)

16.3Complete mediation

Generic A PEP is only as good as the claim that nothing goes around it. Saltzer and Schroeder named this complete mediation in 1975: every access to every object must be checked. For agents, the practical version is "every side effect passes one chokepoint", and the engineering question is how you make that true rather than intended.

Your build ARB uses four mechanisms, and you should be able to name all four:

  1. The agent only holds governed tools. Tools are constructed through build_toolset(policy=…), so the agent's tool functions are thin calls to chokepoint.call(name, …). The agent has no client object for the payments system to misuse.
  2. An unknown tool is a policy denial, not an exception. If the model invents a tool name, the chokepoint does not raise a Python error that some caller might catch and retry around; it records a denial under GBL-DENY-01.
  3. Vendor code cannot leak past the seams. The import-firewall tests check that framework and vendor SDKs are imported only inside their adapters, so no module can reach a raw client.
  4. Out-of-process hosts go through gateways. Agents built on other frameworks (the OpenAI Agents SDK and LangGraph hosts under hosts/) cannot import the chokepoint. E3 put a governed model gateway and tool gateway in front of them (src/aicoe/gateways/, D53), both driving the same enforcement plane, and gateways/equivalence.py compares the decision signature of the in-process and gateway paths so "same governance" is a test, not a claim.

P3 is the proof that the seam was placed right: it added the entire enforcement plane by changing chokepoint.py and nothing under agents/. Governance arrived behind a seam the walking skeleton already had.

16.4The governed path, step by step

Your build When the policy object is the full enforcement plane (it implements both PolicyEngine and RuntimePep), the chokepoint runs seven steps. Learn them in order; R01 has you trace a real call through each one.

Two invariants hold the path together, and the red team showed that the second one depends on the first.

  • Record the decision before the effect (step 3). If the decision record cannot be written, the call is refused. There is no such thing in this system as an action whose authorisation was not recorded first.
  • No action without evidence (step 7, GBL-EVID-01). If the action record cannot be written after the effect, the effect is reversed, rather than left standing unrecorded. This was added in P5-S4 after red-team finding RT-11 showed the guarantee had been resting on step 3 alone.

Step 4's "or replay" is idempotency (CTL-0006): a second identical write inside the dedup window returns the first receipt without executing again. Retries, network timeouts and models that call the same tool twice are normal, so a write path without idempotency eventually double-refunds someone.

16.5The PDP: fail-closed takes work

Your build default allow := false looks like fail-closed. It is not enough, and the header of tool_call.rego explains why in a paragraph worth memorising. In Rego an undefined term makes its whole rule body undefined. A deny rule that reads a missing field, even only to build its reason string, silently stops firing. So a bundle written the obvious way fails open on exactly the malformed request you most want refused.

The fix is a discipline: every fact the bundle reads is pulled through object.get with an explicitly conservative default. If the PIP did not say the tool is registered, assume it is not; if it did not say the principal is verified, assume it is not; if it did not say the agent is read-only, assume it can write; if it did not supply a quota, assume the principal is already at it. There is a test for the empty request.

default allow := false
allow if count(violations) == 0

decision := {"allow": allow, "violations": [v | some v in violations]}

tool_registered := object.get(tool, "registered", false)   # absent ⇒ deny

Three further choices from D17 are easy to miss and each one prevents a real class of bug:

  • One entrypoint. The bundle exposes a single object, data.aicoe.toolcall.decision, returning {allow, violations[]} where each violation names the control that refused. Callers never query partial rules, and every refusal is attributable to a control id.
  • An authored refusal ladder. Several controls often fire on one call. All go into evidence; which one is the headline is violation_precedence in params.yaml (deny-by-default and verified identity first, then separation of duties and approval, then injection, input, preconditions, money and quota). The first reason a human reads is the most fundamental one, and OPA and Cedar report the same one.
  • Money in integer minor units. Rego and Cedar evaluate JSON numbers as doubles, where 34.95 * 100 is 3494.9999999999995. A "refund at most the order total" rule over floats occasionally lies. The PIP converts the amount from its decimal string once; every rule compares integers.
Binding choice

ARB embeds Rego in-process through regopy (Microsoft's rego-cpp), behind a RegoEvaluator protocol, so a clean clone reproduces the governance story with no OPA binary or server. D17 is explicit that a production deployment would likely run the OPA server for bundle distribution and decision logs, swapping one adapter. rego-cpp is a second implementation of Rego, not OPA; the build uses only features verified on both. Chapter 17 compares Rego, Cedar and AGT's policy YAML in depth.

16.6The PIP: facts, not claims

Your build The PIP decides nothing. It turns a request into the document the policy evaluates, and its one rule is that a fact comes from trusted state, never from the agent's account. For a refund it re-reads the order itself instead of trusting that the model looked (the P1 lesson), resolves the currency from the order, normalises money, and attaches identity, quota, approval and guardrail state.

Naming carries the discipline. Where the PIP must record something a caller merely asserted, the field says so: in the cross-agent claim the sender's own statement is sender_asserted, the resolved directory subject is sender_subject, and no rule decides on the asserted one. That is CTL-0017 in a single naming convention: an asserted sender is not a sender until it resolves.

No dead policy

GAP-17 is the most instructive failure in the build. A Rego rule for the currency control was correct, traced cleanly to the control's authored trigger, loaded, and would have been counted as enforcement by any reviewer. It could never fire: it read input.arguments.stated_currency, and issue_refund(order_id, amount, reason) had no currency parameter, so nothing could ever produce that fact. The red team attacked it and could not reach it.

D30's ruling is the sentence to remember: a rule that cannot fire is not a control; it is a comment the linter can't see. tests/test_no_dead_policy.py closes the class, not the instance. It parses the set of facts the bundle reads through object.get, derives the set the PIP actually produces by driving real calls through a real plane, and fails if any read has no producer. Neither list is hand-maintained, and an idiom the parser doesn't understand fails the test rather than being skipped.

Gotcha

D23 adds a subtle distinction you'll reuse with clients: many controls have a derivable half the system computes from trusted state (the currency is the order's currency; an unresolvable order denies) and a declared half that needs the caller to assert something (the caller states a currency, so a disagreement can be caught). The derivable half removes the hazard; the declared half only adds detection. Build the derivable half first.

16.7After the effect

Your build Three hooks run after a call returns, and each answers a different question.

HookQuestionWhat it does
after_callDid the effect happen the way it was authorised?Checks the write's output contract (CTL-0010): the refund receipt must verify. If not, attempt a compensating action and refuse to report the effect as done.
transform_resultCan what came back steer the agent?Demotes untrusted tool output to fenced data (CTL-0014) and records what retrieval returned, which the output guardrail later checks citations against (CTL-0015).
action recordCan we prove it later?Writes the tool_call event; if that fails, reverse the effect (16.4).

Generic The general principle: any data that enters the context from a tool, a document or another agent is input from an untrusted party, however internal the source. Demotion makes that structural. The model still sees the text, but as data in a fence, and no control decision reads it as an instruction. Chapter 20 takes this further into containment by construction.

16.8Traces derived from evidence

Your build Observability and audit are easy to build as two sources of truth that drift apart. ARB avoids that by deriving the span from the evidence (P4-S2, D26). Every call opens a real OpenTelemetry span; once the action record is written, the chokepoint copies onto the span exactly the fields an auditor already has (control id, tier, allow or deny, latency, the record's content_ref), run through the same redaction function and the same redaction policy the evidence writer uses. A span never carries arguments or results at all.

Two consequences follow. "No raw PII in traces" becomes the same guarantee as "no raw PII in the open evidence log", not a second one to keep in sync. And because the span lives entirely inside the call's try/except, a failed exporter fails the trace, never the decision. Langfuse attaches behind that OTel seam; the default tracer exports nowhere.

16.9Where the PEP lives

Generic "Put a checkpoint on the path" leaves the hardest architecture question open: which path, at which layer. The options are not exclusive; mature estates layer them.

Assumption My recommended default for a client estate: in-process PEP for agents built on the client's chassis, a gateway for everything else that calls tools, a model gateway for all model traffic, and the system of record's own permissions scoped to each agent's identity as the floor. Then make the layers prove they agree, the way equivalence.py does for ARB's two paths.

16.11Client translation

In the room

The client story is three checkpoints on the agent's path (screen the input, check the action against policy, ask a person when the stakes are high) and one sentence: an instruction is not a control. The questions that follow are architectural:

  • "Our platform has guardrails. Isn't that this?" Guardrails screen content; a PEP authorises actions on facts from trusted state. You need both, and they fail differently: a guardrail can be fooled by phrasing; a policy on "refund ≤ order total, read from the order system" cannot.
  • "Where do we put the checkpoint across Copilot Studio, Agentforce and our custom agents?" Layer it: native controls where the platform offers them, a gateway in front of shared tools and systems of record, an in-process PEP for what you build, and one evidence standard across all of them.
  • "What if the policy engine is down?" Writes stop; reads may continue by explicit decision. Saying this calmly, with the reason, is a credibility moment.
Check before quoting

Platform gateway features (Google Agent Gateway, AWS AgentCore Gateway and Policy, Microsoft's agent controls) change release status often. Confirm what is generally available, in which regions, before naming any of them as a client's enforcement point.
