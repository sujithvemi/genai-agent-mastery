PART III · CHAPTER 15

The lifecycle and its gates

Every agent walks the same stages from idea to retirement; its tier decides how heavy each gate is. The gate itself should be a pure function of authored configuration and freshly generated proof, so that "deployable" is a fact about this configuration, on this machine, now, and a change anywhere sends the agent back through it.

15.1Stages and gates

Generic An agent development lifecycle has the stages any product has, with a gate at each boundary. A gate is a checkpoint with a list of evidence; if the evidence is present the agent moves on. Five principles make it work without becoming a parallel bureaucracy:

  1. One lifecycle. Gates sit at boundaries the delivery process already has (design review, merge, release). Governance does not run a second track.
  2. The tier changes the weight of a gate, not the stages. A LOW agent's release gate is automated checks plus a self-certified checklist; a CRITICAL agent's needs named sign-offs, red-team results and executive acceptance of residual risk.
  3. No evidence, no promotion. The evidence collected at each gate is the governance record; there is no separate attestation to write.
  4. Early stages are fast because they are contained. Prototypes move quickly because they use synthetic or masked data, cannot write to live systems and have no external users, not because nobody looked.
  5. Change re-enters the lifecycle. A new model, tool, permission or data source is a new risk decision.

15.2How the agent lifecycle differs from software

Generic Most of the lifecycle is ordinary software delivery, which is good: reuse it. Four things are different, and each changes how gates work.

  • Behaviour is not fully determined by code. The same code with a different model, prompt, retrieved corpus or memory behaves differently. So the unit you version and approve is the whole agent configuration: model pin, instructions, tool set and descriptions, policies and params, data sources, memory settings and edges.
  • Correctness is statistical, controls are not. Quality is measured on datasets with thresholds; control conformance is binary and must be proven each run. Mixing the two (a "95% pass rate" on refusals) is a category error: a control that refuses 95% of the time is not a control.
  • Dependencies move without a commit. A provider can change what an alias points to; an MCP server can change a tool description; a knowledge base gains documents. Gates must detect change in inputs you do not commit.
  • Some failures are only visible in production. Approval fatigue, cost runaway and drift need run-time measures that feed back into recertification.

15.3The gate as a function

Your build ARB's gate (src/aicoe/governance/gate/engine.py, evaluate_gate) is a pure function of the agent's manifest, the gate inputs, the taxonomy and the catalog. Its output, GateDecision, carries the tier and the reason, deployable, a status per required control, the reasons for any block, the non-waivable set and whether it is enforced, whether executive sign-off is valid, any undeclared edges, the model pin it read, the configuration digest it judged and the sign-off binding. When an evidence writer is supplied, the decision is itself recorded as an adlc_gate event.

Three properties of this function are deliberate:

  • "Met" means bound, ran and passed on this run. D22 refused to let the gate believe a registry that merely claims a binding: enforcement/conformance.py runs a check per control against the real plane, and the gate counts only passing checks. D27 then made the conformance report a generated, gitignored artifact: a committed report is "a table someone wrote", which is exactly what the gate must not believe.
  • The required set drives the suite, not the other way round. D27 also fixed a quiet flaw: the suite had run whatever checks existed, and a required control with no check blocked the gate correctly but invisibly. The suite now runs the derived required set, and a missing check is a row reading check_ran: false. The general lesson, in D27's words: fail-closed is not enough on its own; the artifact has to be able to say why it failed closed.
  • Every report row points at chained evidence. Each conformance check writes to the run's own hash-chained log, and each row's evidence_ref is the hash of a record saying the same thing. A row cannot claim a pass without a verifiable record agreeing.

The gate is honest about its starting state, too. Before P3 built any bindings, the gate blocked every agent and listed every unmet control with its gap. The gov-gate-as-designed target still shows that: the gate with nothing bound and nothing proven. It is the best five-second demonstration that the gate can say no.

15.4Inputs the gate must not trust

Your build A recurring move in ARB's E-phases was to stop the gate trusting anything a caller could supply. The design-time checks (gate/design.py) read facts straight off the manifest and params on every evaluation, never from GateInputs, because a caller supplies GateInputs and could supply it wrongly. Two examples:

  • CTL-0021: a manifest with no model block, or whose model id is an alias, is blocked. The loader already refuses an alias; the gate checks again, because "a gate that trusted its loader would pass a manifest built in memory around it".
  • CTL-0020: a pinned model with no price entry is a gate failure, never a zero charge, and since D61 a tier with a token limit but no cost limit fails too.

The same principle covers the sign-off, the registry and the directory: the gate reads the committed files itself (D59, point 4), and accepts them as arguments only in tests.

15.5Sign-off bound to a configuration digest

Your build The most important lifecycle control in the catalog is CTL-0022, closing GAP-25: a deployment sign-off was not bound to the configuration it approved. Before it, a CRITICAL agent's executive sign-off approved "the agent", and anything could change underneath it. Now (D59):

  1. The digest is SHA-256 over a canonical object: the manifest as the gate parsed it (so a comment edit is not a change, and an in-memory manifest cannot hide behind its file), the sorted required control and invariant ids, each required control's catalog file, the model pin, and params.yaml. Files are hashed with line endings normalised. digest_inputs lists one line per input.
  2. Independent recompute. recompute(digest_inputs) re-reads every listed file, trusting none of the listed hashes.
  3. Four distinct failures, each with its own sentence: no sign-off; a sign-off with no digest; a record whose digest disagrees with its own inputs (edited after signing); and a stale record, with a human-readable diff of what changed (+ CTL-x, ~ model pin: a → b, ~ params.yaml).
  4. Regeneration refuses unless the digest is the one unmet requirement and an accountable sign-off is already on record (the synthetic-approver path is authorised under D54 and labelled as such).

The effect is that "approved" becomes a property of a specific configuration. Re-pinning the customer-service agent from a local model to Vertex in E4 moved the digest, re-blocked the gate and required a new sign-off, which is exactly what should happen.

pm-agent pm-agent took the same idea further on the signing side. Its sign-off record carries an HMAC (later Ed25519) signature; the gate requires the record's agent and tier to match the derived tier, so a HIGH sign-off cannot cover a CRITICAL agent (D-PM-P4-i); and at CRITICAL a sign-off made with the published development key is refused unless explicitly opted into for testing (D-PM-P4H-i). It also chose not to commit any sign-off for its CRITICAL foil agent: the gate blocks by default, and the deployable path is proven with a fixture (D-PM-P4-c). A committed sign-off would have made the gate say DEPLOYABLE for an agent no accountable person accepted.

15.6The gate's run-time twin

Your build A release gate decides once; the configuration can drift afterwards. ARB closes the gap with CTL-0023: the agent registry (governance/registry/agents.yaml, regenerated by make gov-inventory) records each agent's gate verdict and configuration digest, and the run-time plane checks, before acting, that the agent is registered, DEPLOYABLE, and running the digest the registry recorded. An unregistered agent, or one whose configuration moved since its gate, is refused at run time. The gate says "this configuration may run"; the run-time check says "and this is that configuration".

Conformance runs need to exercise a not-yet-deployable plane, so the plane offers a pre_deployment() context that excuses the registry check. D62 found the obvious hole (any code in the process could enter it and run a drifted configuration) and closed it in two halves: an AST test that nothing outside the conformance harness calls pre_deployment(), and an audit check that flags any registry_check record made in pre-deployment mode in a log that is not a conformance chain. Preventive and detective, for the same hole.

15.7The fast lane

Generic Most estates are dominated by low and medium-risk agents: question-answering over internal documents, summarisation, drafting for a person to send. If those pay the same toll as a payments agent, builders route around governance. A fast lane keeps them inside it:

  • Self-certified LOW. The owner completes intake and a checklist; automated checks run; a sample is audited after the fact.
  • Pre-approved patterns. "Read-only Q&A over labelled documents in a managed environment, internal users" is approved once as a pattern; agents built from it inherit the decision and only prove they match it.
  • Templates carry the controls. An approved template already has identity, logging, screening and the PEP wired; the team adds tools and prompts. Most controls are then bound by construction and proven by the template's conformance suite.
  • Published turnaround by tier. For example LOW in two working days, MEDIUM in five, HIGH and CRITICAL by plan. Publishing the number makes governance accountable for speed, too.

Fleet-first tiering is what makes a fast lane safe: the lane is defined by derived tier and shape, so an agent cannot talk its way into it, and a change that moves its tier moves it out automatically.

Retirement is the stage organisations skip. An agent that is "turned off" but keeps its identity, keys, registry entry and inbound edges is a dormant credential and an orphaned integration. Retiring properly means revoking identity and capabilities, marking the registry entry retired (so the run-time check refuses it), removing declared edges and notifying peers, and keeping its evidence for the retention period, verifiable with keys that are themselves retained.

15.9The gate in CI/CD

Your build A gate that runs only when someone remembers is advice. D45 wired ARB's gate as a required promotion check, and in doing so found that CI had only ever gated one agent: the second archetype gated locally and never in CI. The fix was to run aicoe gov fleet (conformance and the gate over every manifest under governance/agents/), so a newly onboarded agent is covered the moment its manifest exists, with no second CI edit. That is a pattern worth stealing: the pipeline should discover the fleet, not list it.

pm-agent pm-agent's gate added two operational rules that matter once evidence is signed: the gate refuses before writing anything if it cannot seal its own record (a signer preflight, exit code 4, D-PM-P5-k), and it refuses to start on an evidence log with an unsigned tail unless an explicit, recorded acceptance is given (D-PM-P5-h). A gate that appends a record it cannot sign, or signs over a tail nobody checked, would quietly degrade the evidence it relies on.

Chapter 30 places the gate in a full pipeline with environments, keyless deployment and progressive rollout of code, prompts and models.

15.12In the room

In the room
  • "How do you know the agent in production is the one you approved?" "The approval names a digest of the configuration: model pin, controls, policies, manifest. The agent checks its own digest against the registry before acting. If anything moved, it stops and the gate re-runs."
  • "Won't gates slow every team down?" "Low-risk agents go through a fast lane with published turnaround; the gate is a CI check that takes minutes. The heavy path is for agents that can move money or change records on their own."
  • "Who can override the gate?" "No one can make an unmet control met. Waivers are recorded and expire, and at the highest tier the approval and separation-of-duties controls cannot be waived at all."
