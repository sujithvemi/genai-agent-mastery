PART I · CHAPTER 7

The chassis: seams, fakes and tests that can fail

Both builds rest on the same chassis: a governed core that imports no vendor, a set of typed seams with a fake and one or more real bindings behind each, and a test suite that checks claims about the architecture as well as behaviour. This is what makes "portable", "model-agnostic" and "the controls hold on any cloud" testable statements rather than slideware.

7.1Why a chassis

Generic The architecture is ports and adapters, Alistair Cockburn's "hexagonal" pattern (2005): the application core talks to the world only through ports it defines, and adapters bind those ports to particular technologies. Michael Feathers supplied the vocabulary that suits testing: a seam is "a place where you can alter behaviour in your program without editing in that place" (Working Effectively with Legacy Code, 2004). For a governed agent platform the pattern does three jobs at once:

  • Portability. Models, clouds, gateways, policy engines and agent frameworks change quickly. If they live behind seams, a change is an adapter, not a rewrite.
  • Testability. Every seam has a fake, so the whole governed path runs offline, deterministically, in CI, with no credentials.
  • Governance independence. The enforcement plane is part of the core, so its decisions cannot depend on which model or cloud is underneath. That is the property a client's risk function actually cares about, and the chassis makes it testable (7.5).

7.2Seams as Protocols

Generic In Python the natural seam is a typing.Protocol (PEP 544): structural typing, so an adapter conforms by having the right methods, with no inheritance from the core. That keeps the dependency arrow pointing inward. Vendor code never needs to know the core exists, and the core never imports the vendor.

Reference build The ARB defines its seams under aicoe/platform/. Counting the Protocols there gives the shape of the chassis: model (ModelProvider, plus a ModelCallHook), runtime (Agent, RuntimeAdapter), tool gateway (ToolGateway, McpServerConnection), policy (PolicyEngine, RuntimePep, RegoEvaluator), identity (DirectoryService), state (StateStore), memory, retrieval (Retriever), screening (ContentScreen), classifier, anchoring (AnchorSink), signing (Signer, Verifier), observability (Tracer, Span), payments (PaymentsAdapter, ReversiblePayments), cross-agent channel (AgentChannel) and cloud (CloudTarget). Fifteen seam packages carry a fakes.py.

pm-agent pm-agent has the same chassis with the seams its domain needs: Orchestrator (fake and LangGraph), JiraReadAdapter and JiraWriteAdapter (fakes, Atlassian MCP and REST), ApprovalGate, Executor, LedgerStore, ReadCache, Signer and KmsClient, and the PEP's own seams (PolicyEngine, Guardrail, IdentityResolver, EvidenceSink).

Gotcha

A @runtime_checkable Protocol's isinstance check only confirms that the methods exist; it does not check their signatures. A fake whose complete() takes the wrong arguments passes isinstance and fails in use. That is why both builds also prove conformance statically (7.3).

7.3Fakes, and proving they conform

Generic Test doubles come in grades. Google's Software Engineering at Google (Winters, Manshreck and Wright, 2020), in its chapter on test doubles, ranks them: prefer the real implementation where it is fast and deterministic, then a fake (a lightweight working implementation), and only then stubs and mocks, which encode assumptions about call sequences and make tests brittle. Fakes earn their place only if they stay faithful to the real thing, so a fake needs its own tests.

Reference build Fidelity is checked at two levels:

  • Static conformance. platform/_conformance.py is "checked by mypy and never executed". It assigns each fake and each real binding to its Protocol type, so if either drifts from the seam, make type fails with a precise message. pm-agent has the same file, which also serves as the non-vacuity anchor for its firewall: the LangGraph binding is named there, under platform/runtime/, where importing it is allowed.
  • Behavioural equivalence. Where a seam has two real bindings, a test runs both and asserts they decide the same: OPA against Cedar (test_policy_parity.py, D22), the direct gateway against FastMCP (test_gateway_equivalence.py), the fake model against live models (test_portability.py), and in pm-agent the fake orchestrator against LangGraph (test_runtime_portability.py).

7.4The import firewall

Reference build D32 made portability "falsifiable, the way OPA/Cedar parity is". The mechanism is a test that parses every module outside aicoe/platform with Python's ast and fails if any of them imports a vendor root:

# tests/test_import_firewall.py (reference build), abridged
FORBIDDEN_ROOTS = frozenset({
    "google", "googleapiclient", "vertexai", "litellm", "fastmcp", "mcp",
    "cedarpy", "regopy", "langfuse", "openai", "anthropic", "boto3", "botocore",
})

def test_no_core_module_imports_a_vendor_sdk():
    offenders = {p: _module_roots(p) & FORBIDDEN_ROOTS for p in _core_modules()}
    assert not any(offenders.values())

def test_the_firewall_test_is_not_vacuous():
    seen = set().union(*(_module_roots(p) for p in PLATFORM_ROOT.rglob("*.py")))
    for expected in ("google", "googleapiclient", "fastmcp", "cedarpy", "regopy", "langfuse"):
        assert expected in seen   # the boundary is live, not empty

The second test answers the first prediction question. A firewall test passes trivially if the vendor code has been deleted, or if the scan points at the wrong directory. The non-vacuity test fails in exactly those cases.

pm-agent pm-agent's firewall is finer-grained. It confines each vendor to its own seam rather than just to "platform": LangGraph and psycopg only under platform/runtime (and psycopg also in platform/memory/postgres.py), mcp and httpx only under platform/jira, regopy only under platform/policy, cryptography only under platform/crypto, OpenTelemetry and Langfuse only in the OTel module, phonenumbers only in platform/memory/pii.py, and sqlite3 only in the ledger store. Each rule has its own non-vacuity test, and several have a bite test: it writes a copy of a legitimate module with one forbidden import added into a temporary directory and asserts the checker flags it (test_the_psycopg_rule_bites_inside_the_memory_directory). D-PM-2b dropped Cedar, and cedarpy stays on the forbidden list so that it "must never reappear".

Gotcha · what an AST firewall cannot see

The scan reads import and from … import statements. It does not see importlib.import_module("…") with a string, __import__, or a vendor reached transitively through an allowed third-party library. Both builds use importlib in the core, legitimately: the ARB demo deliberately loads the red-team corpus from tests/ ("imported, not copied", so the demo cannot drift from the gated cases), and pm-agent uses lazy attribute loading in agents/__init__.py. Neither reaches a vendor. If a client's codebase needs a stronger guarantee, add a runtime check (import the core in a clean interpreter and assert no vendor module appears in sys.modules) or use a contract tool such as import-linter.

7.5Portability as a tested claim

Reference build The firewall proves that the core could be moved. test_portability.py proves that moving it changes no decision. It runs the governed golden set and a sample of the red-team corpus (one attack per major control family: TB-CEILING, TB-NON-REFUNDABLE, TB-NEGATIVE-AMOUNT, INJ-COMPEL-WRITE), and records for each case which controls refused and what reached payments:

  • The fake-model leg always runs and is pinned to a baseline in the file, so any change in a decision shows up as a diff.
  • The LiteLLM and Vertex legs run only where a provider and credentials are configured. When they run, their decisions must match the fake's exactly. The file is candid that these are "proof a deployment can demand, not a CI gate".
  • An always-on gateway leg swaps DirectToolGateway for FastMcpGateway under the same plane and asserts that no decision moves, because "the tool-call ingress is transport, the PEP is the authority".

This is the precise form of the client claim "our controls are model-agnostic". The enforcement decisions are a property of the plane, so the same refusals happen whatever model proposes the call. The model's quality varies by provider; the plane's decisions do not.

7.6The payoff: a framework swap with zero code

Reference build D48 is the evidence that the chassis works. The AICoE playbook targets Google ADK 2.5.0 while main ran on 2.8.0, so a branch pinned ADK to exactly 2.5.0. "The delta is two pins and zero code." Every google.adk import lives in two adapter files (platform/model/adk.py and platform/runtime/adk.py). The eight ADK primitives those adapters touch were API-stable across the versions for those call sites, so neither adapter changed, and git diff main..adk-2.5.0 -- src/ was empty. Every enforced result held: the golden set, the fleet verdict, policy parity, portability, the import firewall, no-dead-policy and the full red-team corpus.

Two lessons follow. First, the method was "regression-guarded native rewrite": pin the target version, run the suite, and let the red tests draw the worklist (here there was none). Second, the decision also recorded a cost found later: ADK's convenience extensions extra pulled in a LangGraph version cap the build never used (D53). Even a clean swap can hide inherited dependency baggage, and the place to find it is the lock file.

7.7Tests that guard the governance

Reference build The most distinctive part of the suite tests the governance machinery itself rather than behaviour. A selection:

The plane-bypass tests repay study. Each closes a specific route around the controls: entering pre_deployment() after a deployed plane is built relaxes nothing; a bare EnforcementPlane(...) skips the inventory check, so production builders may only use build_enforcement_plane; and an in-process params override would bypass the digest that sign-off is bound to, so no production builder accepts one. This is complete mediation (Chapter 12) applied to the construction of the enforcer itself.

7.8Falsifiers: tests that prove a test can fail

Generic A test that cannot fail is decoration. The pattern running through both builds is to pair each claim test with a falsifier: a test that shows the checker detects a deliberately broken input. Four forms appear:

  1. Non-vacuity. Prove the thing being guarded exists (the vendor imports really are under platform/; the Rego parser really found facts).
  2. Bite. Plant a violation in a temporary copy and prove the checker flags it (the psycopg and OTel rules; "the check still catches a fact with no producer").
  3. Lie. Feed the checker an output that contradicts the evidence and prove it rejects it (the demo checker test asserting "the checker accepted a matrix junit contradicts" never happens).
  4. Red before green. A new guard is written to fail on the current state, then the fix makes it pass (D50's living-docs test was "red before the sweep and green after").

Mutation testing (for example mutmut for Python) automates the general version of this by altering code and checking that some test fails. For governance checkers the hand-written falsifier is usually clearer, because the interesting mutations are semantic (a missing producer, a leaked import), not syntactic.

7.9Byte stability and pinned baselines

Both builds Evidence hashes, config digests and pinned baselines only work if the bytes are stable. pm-agent's very first decision after scaffolding, D-PM-P0-b, set * text=auto eol=lf in .gitattributes because the build host is Windows and fixtures must hash identically on every platform. The same discipline shows elsewhere: dependencies pinned exactly with a lock file, canonical JSON before hashing (Chapter 22), fixture data instead of live data in CI, and baselines kept in the test file as small literal dictionaries so that any change in a control decision appears in a code review diff.

7.12In the room

In the room
  • "Are we locked into this framework?" "In our reference build a framework version swap changed two dependency pins and no code, and every control decision held. Ask any vendor for the equivalent evidence."
  • "Do the controls depend on the model?" "No. The same refusals happen on a fake model, a local model and Gemini on Vertex, and a test fails if they ever diverge. The model's quality varies; the plane's decisions do not."
  • "How do you know your tests test anything?" "Each architectural check has a partner test that breaks the rule on purpose and proves the check catches it."
