PART X · CHAPTER 52

Capstone A: govern a new agent by hand

The proof that you, not the builds, can govern an agent: a new agent with one real write, taken from an agent card to a tiered control set, a hand-written chokepoint, policy and evidence chain, an AGT parity table, a keyless pipeline with the gate as a required check, five attacks and a two-page defence. Stage by stage, with checkpoints, traps and a rubric.

RepsGF-L2 · R10, R24, R25

52.1What this capstone proves

Generic The builds prove that a governed agent can be built. Capstone A proves that you can do it, on an agent the framework has never seen, with your own hands. It is level GF-L2 of the governance frameworks track: apply, not just understand. The rules come from learning/capstones/A_govern_a_new_agent.md:

  • You write the code and the governance artefacts. Claude coaches and reviews; it does not author. Stages A3 and A5 are hand-built without assistance.
  • Reuse ARB's catalog semantics and ideas; do not copy its code.
  • Synthetic data only. Work in genai-agent-mastery, under agents/<your_agent>/ and governance/.
  • Pick an agent with exactly one real write. That write is the whole governance story.

52.2A0 · The agent card

Two suggested agents: an expense pre-approval agent that reads a claim, checks policy and can submit it, or a meeting-notes to Jira agent that proposes tickets and creates them only with approval. Choose the one whose write you understand best. Write the card in the shape of an ARB manifest, because the tiering rule will read it:

name: expense_preapproval            # or notes_to_jira
owner: you@example.com
description: >-
  One paragraph: purpose, users, what it may do.
axes:                                # one value per axis, with a reason comment each
  data_sensitivity: ...              # none | internal | PII | sensitive/regulated
  action_class: ...                  # read-only | reversible-write | irreversible/financial-write
  exposure: ...                      # internal-only | authenticated-external | public
  autonomy: ...                      # suggests | acts-with-confirmation | acts-autonomously
  blast_radius: ...                  # single-record | multi-record | systemic
tools:
  - name: ...                        # two reads, then the one write with writes: true
model: {provider: ..., model: ..., version: ...}

Checkpoint. Every axis value has a one-line reason that names a tool or a data field, as ARB's customer_service_ops.yaml does. If a reason says "probably", the value is not decided yet.

52.3A1 · The ungoverned agent

Grow agents/hello_agent into the real agent on ADK, with the two reads and the write, running on a local model or Vertex. No controls yet; that is the point. Then list five ways it can do harm, each tied to an OWASP agentic risk id (Chapter 32): for example, an injected instruction in a claim's free-text field that submits a different claim (ASI01), a submission above the policy limit (ASI02), acting for a user who did not ask (ASI03), a retry that submits twice, and an approval faked by the model's own text.

Checkpoint. You can make at least two of the five happen in a scripted run. A harm you cannot demonstrate is a hypothesis; mark it so.

52.4A2 · Tier it and choose the controls

Apply ARB's rule by hand before you run any engine: score each axis, apply highest-wins banding, check the CRITICAL clauses (the irreversible or financial write acting autonomously, or two axes at the top), then select the controls whose min_tier and applies_when match (Chapter 13). Only then run ARB's engine on your card, if you want a check, and explain any difference.

Defend each control's presence in one sentence, and each absence too. An expense agent that submits for human approval may not need ARB's refund ceiling, but it needs something like it: a policy limit decided on trusted facts, not on the amount the model asserts (Chapter 16).

Checkpoint. Tier and control list written, with the derivation shown and each inclusion and exclusion defended.

52.5A3 · The PEP, the policy and the evidence, by hand

The core of the capstone. Build it in this order, tests first, and keep each piece small enough to explain from memory (Rebuild rep R10 is the warm-up: a chokepoint and a hash-chained log in under 120 lines).

  1. The chokepoint. One function every tool call passes through; tools are not callable any other way. Write the test that proves it: monkeypatch the write tool and assert that calling the agent's tool list directly cannot reach it.
  2. The PIP. Fetch the facts the policy needs (the claim's real amount, the user's limit, whether an approval exists) from your synthetic sources, never from the model's arguments.
  3. The PDP in Rego. Three controls, deny by default, every fact read through object.get with a conservative default, one decision entrypoint returning allow and a list of violations each naming its control (Chapter 17). Include the empty-request test.
  4. The approval. A signed grant bound to the exact action (its hash) and verified at the PEP before the write; the approver may not be the requester.
  5. The evidence. Append-only JSONL, each record carrying the previous record's hash; a verify command; a tamper test that edits one record and watches verify fail (Chapter 22). Write the evidence record before the effect, and refuse the effect if the write fails.
  6. Idempotency. A key derived from the run and the step, honoured by the write tool.

Checkpoint. The write is blocked without approval; it succeeds with a valid grant; a replayed grant is refused; every case leaves evidence; verify passes, and fails after tampering. Each test was red before it was green.

52.6A4 · AGT parity

Express the controls AGT can express as AGT policies, in their own environment, default deny with one positive allow each, and run both engines on the same cases. Record which controls are expressible, the parity result, and a single-rule mutation per policy (Chapter 47).

Checkpoint. A two-engine parity table for your agent, stated with the AGT version.

52.7A5 · The gate and a keyless pipeline

This stage is also the M1 Rebuild (rep R24): Terraform plan on every pull request and apply on merge, authenticated by workload identity federation, with your gate as a required check. Your M0 work in infra/terraform/wif.tf already has the pool and provider; M1 makes CI use them.

  1. Trust only this repository and branch. On the provider, an attribute condition such as assertion.repository == "<you>/genai-agent-mastery", and on the service-account binding, the principal set for that repository. Apply only from refs/heads/main.
  2. Two service accounts. A read-only planner for pull requests and an applier for main, each with the narrowest roles the Terraform needs.
  3. The workflow. permissions: id-token: write; authenticate with the federation action; terraform plan posted to the pull request; your gate (manifest validation, tier derivation, conformance tests) as a separate job; apply only on push to main, in a protected environment that needs your approval.
  4. Branch protection. Make the gate and the plan required checks, so a failing gate cannot merge (Chapter 30).

Checkpoint. A pull request shows the plan and the gate result; breaking one control's test turns the gate red and blocks the merge; merging deploys; no key exists anywhere.

52.8A6 · Red team and the defence note

AttackHow to run itExpected resultEvidence to show
Injection in dataAn instruction inside a claim or meeting noteNo effect outside the user's request; the instruction is treated as dataThe refused or unchanged call and its record
Confused deputyAsk the agent to act for another userRefused: the principal is resolved, not assertedThe violation naming the control
Over limitA write above the policy limit, with the model claiming a lower amountRefused on the PIP's factThe decision with both amounts
Missing or forged approvalWrite without a grant; with a grant for a different action; replayed grantAll refusedThree records
Evidence tamperEdit one recordverify fails at that recordThe verify output

Then write governance/DEFENCE.md, at most two pages, the answer to "walk me through how this agent is governed":

  1. The agent and its one write, in three sentences.
  2. Its tier and why, with the axis values.
  3. The controls, each with where it is enforced and the test that proves it fires.
  4. The five attacks and what stopped each.
  5. Residuals: what is not covered, stated where the claim is made (ARB's D61 rule).
  6. How a change is re-gated.

52.11Prove it

Defend cold · GF-L2
  1. RecallThe seven stages and the artefact each produces.
  2. ApplyDerive your agent's tier aloud from its card, then name the one axis change that would make it CRITICAL.
  3. ApplyShow the test that proves your chokepoint is the only path to the write.
  4. DesignExplain your federation trust conditions and what an attacker with a fork of your repository can and cannot do.
  5. Trade-offEvidence before the effect (refuse on failure) against evidence after (never block the user). Which, and why, for your write?

Reps: R10 (Rebuild warm-up), R24 (M1), R25 (AGT), then the stages. Card candidates: one write carries the story · facts from the PIP, never the arguments · approval is a signed grant bound to an action.
