AWS: Bedrock and AgentCore

AWS splits its agent offer in two. Amazon Bedrock is the model layer: models, guardrails, knowledge bases, tuning and capacity tiers. Amazon Bedrock AgentCore is a framework-neutral and model-neutral set of agent infrastructure services, and in 2026 it has moved fastest of the three clouds: a deterministic Cedar policy engine on tool calls, a registry, evaluations, optimization with A/B testing, a managed harness and agent payments are all generally available. Many of your clients will run agents here, so you need it at the same depth as Google.

42.1The shape of AWS's offer

  • Amazon Bedrock: managed access to many model families (Amazon Nova, Anthropic Claude, Meta Llama, Mistral, DeepSeek, OpenAI's open-weight models and others), Guardrails, Knowledge Bases, the original Bedrock Agents and Flows, prompt management, model evaluation, customization, and capacity tiers (Reserved, Priority, Standard, Flex; Chapter 9).
  • Amazon Bedrock AgentCore: agent infrastructure that "works with any framework and foundation model", including models outside Bedrock. Generally available since October 2025 and expanded through 2026.
  • Strands Agents: AWS's open-source agent SDK, the default in AgentCore tooling (Chapter 35).
  • Business and developer agents: Amazon Quick (no-code background agents for business users), Kiro (an agentic development environment), the AWS DevOps Agent, AWS Transform, and the security agent AWS Continuum announced in June 2026.

42.3AgentCore Policy, examined

Generic AgentCore Policy is the closest any cloud comes to the PDP in your reference model, so it repays close reading. From the developer guide:

# the developer guide's own example: refunds under $1,000
permit(principal,
  action == AgentCore::Action::"RefundTarget___process_refund",
  resource == AgentCore::Gateway::"<gateway-arn>")
when { context.input.amount < 1000 };
  • A policy engine is a collection of Cedar policies attached to a Gateway. In ENFORCE mode "every tool call is intercepted and evaluated", "all actions are denied unless explicitly permitted", any matching forbid denies (forbid wins), and decisions are logged to CloudWatch.
  • Policies can be generated from natural language (--generate "Only allow refunds under 1000 dollars"), which produces Cedar for review; the enforced artefact is still Cedar.
  • Validation runs schema and semantic checks, rejecting a policy with findings by default; wildcard resources are rejected.
  • Dogwood, open-sourced under Apache 2.0 and reported by InfoQ in August 2026, extends Cedar with temporal conditions over an agent's prior tool calls and outcomes: approvals, rate limits, running totals. Any Cedar policy is valid Dogwood. Temporal clauses give up Cedar's automated analysis, and AWS describes the reference interpreter as for exploration, not production Verify.
  • Since June 2026 Policy can also call Bedrock Guardrails to check agent actions.

The prediction questions:

  1. The example checks the amount the agent supplied. It cannot check that the amount is no more than the order's total, that the order is refundable, or that the currency matches, because those are facts in the order system that the policy does not read. Your CTL-0002, CTL-0003 and CTL-0012 need a PIP; on AWS that means the tool (the Lambda target) re-reading trusted state, or a pre-check service in the path (Chapter 16).
  2. Dogwood's running totals and approvals over prior calls resemble ARB's CTL-0007 (rate and value budget on trusted counters) and parts of CTL-0004: state the enforcement point keeps itself, rather than the agent's account. That is the right design; check where the history is stored and whether it survives restarts and replicas (your GAP-20 lesson; Chapter 3).
  3. Automated reasoning checks are model-assisted validation of responses. However accurate, they are probabilistic relative to your rules, so they may restrict (hold or block an answer) but should not be the thing that allows an effect (D52; Chapter 20).

Reference build ARB already runs Cedar: governance/policies/cedar/tool_call.cedar mirrors the Rego bundle, and D22's parity tests prove the two engines agree on every golden refund, boundary case and read (Chapter 7). Porting ARB's refund rules to AgentCore Policy would therefore be a translation of a tested policy, with the trusted-fact checks staying in the tool layer.

42.4Identity and delegation

Generic AgentCore Identity gives agents workload identities "compatible with industry-standard workload identity patterns", authenticates inbound callers with JWT authorizers from existing identity providers (Amazon Cognito, Okta, Microsoft Entra ID, Auth0), and manages outbound credentials through credential providers so agent code does not hold them. On-behalf-of token exchange (April 2026) and a consent portal (September 2026) cover user delegation. Gateway enforces inbound traffic from itself to Runtime targets. The design goal matches yours: a resolved principal, delegated narrowly, with credentials outside the agent (Chapter 18). Under the hood, IAM remains the authorisation system for AWS resources, with condition keys for AgentCore resources.

42.5Bedrock: models, guardrails, knowledge

  • Guardrails has six policy types: content filters (including prompt-attack detection), denied topics, word filters, sensitive-information filters (PII and custom patterns), contextual grounding checks, and Automated Reasoning checks, which AWS says validate responses "with up to 99% accuracy". The ApplyGuardrail API applies guardrails to any model, including non-Bedrock ones, and guardrails can be enforced across accounts in an AWS Organization.
  • Knowledge Bases and the newer AgentCore Managed Knowledge Base for retrieval (Chapter 4).
  • Customization: fine-tuning, continued pre-training, distillation and reinforcement fine-tuning for selected models Verify.
  • Bedrock Agents and Flows: the earlier managed agent and workflow features. For new agents AWS points to AgentCore; check which a client's existing agents use.
  • Capacity: Reserved (1 or 3 months, minimum 100,000 input and 10,000 output tokens per minute, overflow to Standard), Priority, Standard and Flex tiers; cross-region inference profiles; batch.

42.6Beyond the developer platform

Agents built by business users in Amazon Quick, developer agents in Kiro and the AWS DevOps Agent, and agents bought through AWS Marketplace all enter a client's estate without passing through AgentCore. Your inventory and reconciliation discipline (CTL-0023) has to find them; ARB's reconciliation fixture already includes an export shaped like an AgentCore runtime listing (D59; the field names are the build's, not AWS's schema).

42.10In the room

In the room
  • "AgentCore Policy enforces our rules, right?" "It enforces rules on what the agent asks for, deterministically, and it is the best native policy engine in the market today. Rules that need your systems' facts, such as 'no more than the order total', still need a check that reads those systems."
  • "Can we use Guardrails instead of policies?" "Use both: guardrails screen content and may block; policies decide actions. A screen should never be the thing that allows a refund."
