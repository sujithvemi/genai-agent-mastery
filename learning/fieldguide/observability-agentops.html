PART V · CHAPTER 31

Observability, SLOs and AgentOps

Operating agents means answering two kinds of question: is it working (latency, errors, cost, quality), and can we defend what it did (who decided, on what facts, under which control)? The first is observability; the second is evidence. Your builds make a strong architectural choice that this chapter recommends: traces are a view of the evidence, joined to it one to one and never a second record. Then it covers SLOs for agents and for the governance plane, alerting, incident response and how to stop an agent.

31.1Four signals, not three

Generic Classic observability has metrics, logs and traces. Agents need a fourth: evidence, the tamper-evident record of decisions and effects (Chapter 22). The difference is purpose and guarantees: telemetry is sampled, best-effort and optimised for debugging; evidence is complete, ordered, signed and retained for defence. Mixing them up produces either expensive telemetry or untrustworthy evidence.

31.2Traces as a view of evidence

pm-agent pm-agent's tracing module states the rule: "evidence stays the system of record and spans are the view." Three mechanisms make it hold:

  • Fail-soft tracing. Every tracer is wrapped so that a failing tracer degrades to no-op; it "never blocks a run, never swallows an exception from the code the span wraps, never touches evidence."
  • The join. After each evidence record is durably appended, its id is attached to the innermost open span. A join check then verifies both directions: every evidence id on a span resolves to a record (no dangling claims), every record in the traced window belongs to exactly one span (no orphans, no duplicates), every node and PEP span carries at least one evidence id (no bare spans), and each PEP decision span claims exactly one tool-call record.
  • Falsifiers. Breaking the evidence hook, dropping a PEP span, or a node that writes no evidence turns the join red.

The first prediction question: the evidence is right, by design. A disagreement means a span was dropped or invented, and the join is the test that finds it. ARB takes the same position from the other side: traces are derived from evidence through one redaction policy, so telemetry can never leak more than evidence minimisation allows (Chapter 21).

31.3OpenTelemetry for agents

Generic OpenTelemetry's generative-AI semantic conventions standardise attributes for model calls (operation, provider, requested and response model, input and output token counts) and spans for agent invocations and tool executions, so traces from different frameworks and platforms look alike Verify the current status and names, since the conventions were still evolving at last check. Practical rules:

  • Instrument with OpenTelemetry and choose back ends separately (Langfuse, Phoenix, Datadog, Cloud Trace); your builds bind OTel to Langfuse.
  • Record the response model, not only the requested one; record token usage and cost per span.
  • Do not put prompts and outputs in traces by default; if you do, apply the same redaction as evidence.
  • Propagate trace context across the gateway, A2A calls and tools, so a multi-agent run is one trace.
  • Turn off vendor default exporters you did not choose (Chapter 35).

Error budgets work as for services: when a budget is spent, releases slow and reliability work comes first. Distinguish correct refusals (a control doing its job) from failures; counting refusals as errors pressures teams to weaken controls.

31.5SLOs for the governance plane

Reference build ARB's docs/operating/SLOS.md defines three SLOs, each against an artefact the build already produces, with the command that computes it today:

  1. Evidence-write success: 100%. The second prediction question. This is "not a 'four nines' availability number": because a failed evidence write refuses the action (GBL-EVID-01), anything below 100% would mean unrecorded actions, "the exact defect GBL-EVID-01 exists to make impossible". It is an invariant to verify (make audit-verify), not a performance level to tolerate.
  2. Anchor freshness within the stated window (every 10 records or 300 seconds, whichever first). A widened window "is an incident ... not a metric to average over a week".
  3. Conformance coverage: 100% of each agent's derived control set bound, checked and passing, distinguishing a gap (no check exists: a build defect) from a fail (the check ran and failed: a runtime regression), because they need different owners.

The document is candid that none has a live dashboard yet, and names the counter that live wiring would add. Defining SLOs as falsifiable before they are wired to alerts is the right order.

31.6Alerts

pm-agent pm-agent evaluates six alert rules over the evidence log rather than over live processes: a spike in deny rate, a broken hash chain, an unsigned tail, the rate of plans with quarantined items, the rate of wholly blocked plans (warn-only until thresholds are ratified from live data), and memory-integrity failures. Rates compare exact fractions with no rounding, and fire only when at least one event was counted, so a threshold of zero means "any one" and an empty window never fires. Alert on symptoms users feel and on control-plane integrity; page a human only for what needs a human now.

31.7Incidents and runbooks

Reference build ARB's governance-incident runbook covers three triggers (a control fired in production, a red-team finding outside the corpus, the evidence chain looks broken) with one shape:

  1. Identify the control and run from the evidence record; reconstruct the decision with aicoe audit trace, revealing no more than the investigating principal already holds.
  2. Confirm the control behaved as designed: a refusal that matches its trigger "is normal operation, not an incident, however alarming the refusal reads".
  3. If the chain looks broken, verify against anchors; treat truncation or divergence as a possible tamper event, freeze changes to the sink, preserve the files, escalate to the data-governance owner and the CISO.
  4. Turn every new finding into a red-team case; record gaps and get a ruling before changing the enforcement plane.
  5. The gate is the backstop: a regressed binding re-blocks the agent on the next run.

The other runbooks (control changes, onboarding agents and edges, re-pinning MCP tools, framework currency, approval sessions) are the operational counterpart of the lifecycle in Part VI.

31.8The kill switch

Generic The third prediction question. Three levers, fastest first:

LeverEffectLeaves running
Deny at the enforcement point (registry state "suspended", or a deny rule at the gateway)No new effects anywhere, immediatelyReads and conversations, unless also blocked
Revoke the agent's identity and credentialsThe agent cannot authenticate to anythingIn-flight calls with unexpired tokens; make tokens short-lived
Stop the runtime (scale to zero, disable the endpoint)No new runsParked runs in storage; resume them deliberately or cancel them safely

Have all three scripted, tested, and owned, with the evidence of who pulled which lever. ARB's inventory check is the first lever already: a subject not registered and DEPLOYABLE is refused at the chokepoint, the tool gateway and the model gateway (CTL-0023).

Check the default content-capture setting, the retention period and the storage region for each, and check which OpenTelemetry generative-AI convention version the service emits before joining traces across vendors.

31.12In the room

In the room
  • "Can we see everything the agent did?" "Two ways. Traces show how a run went, for engineers fixing problems; they may be sampled. The evidence record shows every decision and every change, complete and tamper-evident, for audit. They are linked, and we check the link."
  • "How do we stop it in an emergency?" "Three switches, fastest first: refuse all of its actions at the enforcement point, revoke its credentials, then stop the runtime. Each is scripted, tested and logged, and the first takes effect in seconds."
