PART V · CHAPTER 32

Security architecture and multi-tenancy

Agents add new attack surfaces (instructions hidden in content, tools that can be misused, memory that can be poisoned, other agents that can lie) to all the old ones. Part IV built the controls; this chapter is the security architect's view around them: threat modelling, trust boundaries, network segmentation and egress, secrets, supply chain, and keeping tenants apart in every store an agent touches.

32.1Threat modelling an agent

Generic Start with a data-flow diagram and its trust boundaries, then enumerate threats per element (STRIDE works: spoofing, tampering, repudiation, information disclosure, denial of service, elevation of privilege), then add the agent-specific ones. The first prediction question: the model's output. In an ordinary service the application logic is trusted; in an agent, the component choosing actions can be steered by any text it reads, so its proposals are untrusted input to your enforcement point (Chapter 16). Frameworks that help structure this: OWASP's agentic threats and mitigations guidance, the Cloud Security Alliance's MAESTRO layers, and MITRE ATLAS for adversary techniques.

32.3Trust boundaries

Draw these explicitly, and put an enforcement point on every one an effect crosses:

  • User to agent (authentication, input screening);
  • Agent to model provider (data egress, model identity);
  • Model output to agent logic (untrusted proposals);
  • Agent to tools and business systems (the PEP);
  • Retrieved content and tool results to the model (untrusted data in context);
  • Agent to agent (no transitive authority);
  • Agent to sandbox and sandbox to network;
  • Tenant to tenant.

32.4Segmentation and egress

Generic The second prediction question: anything the network allows. Injected instructions can make a code sandbox or browser exfiltrate data to an attacker's server, download tools, or attack internal services. Controls:

  • Default-deny egress for agents and sandboxes, with an allow-list of model, tool and data endpoints, enforced by an egress proxy or gateway that logs destinations (GEAP Agent Gateway egress, AgentCore VPC egress, firewall policies).
  • Service perimeters around data and model APIs (VPC Service Controls on Google Cloud; private endpoints elsewhere) so stolen credentials cannot pull data out from outside.
  • Private connectivity to model endpoints and tools (Private Service Connect, PrivateLink).
  • Segmented workloads: executors and sandboxes in separate networks from the control plane and evidence stores.

32.5Secrets and keys

  • No secrets in prompts, tool descriptions, memories, logs, sandboxes or images. A secret the model can see is a secret injected text can ask it to repeat.
  • Workload identity instead of keys; a secret manager for what remains; rotation on a schedule and on suspicion.
  • Signing keys (evidence, sign-offs, approval grants) in a KMS, with custody and rotation documented; ARB uses Cloud KMS for Ed25519 evidence signing live, and finding F-01 notes that verification of those signatures is not yet wired.
  • Downstream user credentials held by a vault or gateway, never by agent code (Chapter 27).

32.6Supply chain

An agent's supply chain is wider than its dependencies: models (pinned, identity-checked), MCP servers (registered, description-pinned), tools and connectors, prompts and skills from shared libraries, framework and SDK versions, container base images, and evaluation datasets. Apply the same discipline to each: provenance, pinning, review, and detection of change (Chapter 38).

32.7Tenant isolation, store by store

Generic The third prediction question has many answers. Tenant data can cross tenants in:

Store or channelLeakControl
Response and tool cachesA cached result served to another tenant or userKeys include tenant and permission scope (pm-agent CTL-0021)
Prompt and prefix cachesTiming side channel reveals another tenant's promptPer-tenant cache scope (Chapter 9)
Long-term memoryFacts about one tenant recalled for anotherScope by tenant and user; tests with two principals
Vector indexesRetrieval returns another tenant's documentsTenant and permission filters at query time, or separate indexes
Session and checkpoint storesRun state readable across tenantsTenant-scoped access and keys
Traces and logsOperators or tools see other tenants' contentRedaction; per-tenant access to telemetry
Evaluation datasetsProduction samples reused across tenantsConsent, minimisation, tenant tagging
Fine-tuned modelsOne tenant's data shapes another's outputsPer-tenant tuning or none
Quotas and budgetsNoisy neighbour denial of servicePer-tenant limits and bulkheads

The test that catches most of these is simple and should exist for every store: two principals in two tenants request the same thing, and neither sees the other's data (pm-agent's cache test is the template).

32.8Testing security

A red-team corpus run in CI (ARB's tests/redteam/ has suites for guardrail evasion, trust boundaries, evidence integrity, cross-agent attacks, the model plane, sign-off and inventory, MCP integrity, the approval UI, classifier compromise and an evolution pass; every finding becomes a case), automated scanners (garak, PyRIT, promptfoo's red-team mode; lab T18), periodic human red teams against current techniques, and falsifiers that show each control fires (Chapter 24).

Generic The screening services in the first row are detectors. Under this book's rules they may restrict an action (D52) but never authorise one, and their findings are inputs to your PDP rather than decisions (Chapter 16). Measure each against your own red-team corpus before relying on it; published detection rates are for the vendor's test sets, not your tools and data.

Check before quoting

Screening services differ in where they can run (inline at a gateway, as an API, only on the platform's own models), which languages they cover, what they add to latency and how they are priced (per text unit, per request). Check each before putting one on the critical path of every tool call.

32.11In the room

In the room
  • "Can't we just turn on a prompt-injection filter?" "Turn one on, yes, and measure it. But a filter catches some attacks; it cannot stop the agent doing something harmful with an instruction it missed. What stops that is the agent having no authority to do it, checked on every action."
  • "Could another customer's data show up in our answers?" "Every store that could carry it is listed, with the control that separates tenants and a test that tries to cross. The list includes the less obvious ones: caches, memories and traces."
