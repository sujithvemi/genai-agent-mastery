PART I · CHAPTER 2

The loop, tools and typed outputs

An agent's loop is simple: call the model, run the tools it asks for, feed back the results, repeat until it answers. The engineering is in the edges: how tools are described and validated, how a refusal is shown to the model, how an answer is forced into a shape the system can check, and how the loop is made to stop.

2.1The loop

Generic Strip any agent framework down and the core is a loop (the pattern the ReAct paper named in 2022: reason, act, observe):

messages = [system, user]
while True:
    reply = model(messages, tools=tool_schemas)
    if reply.tool_calls:
        for call in reply.tool_calls:
            result = run(call.name, call.arguments)     # ← the harness runs it
            messages += [reply, tool_result(call.id, result)]
        continue
    return reply.text                                     # ← a final answer

Everything else (memory, retrieval, planning, sub-agents) is an elaboration of what goes into messages, what run is allowed to do, and when the loop stops. For governance, the line that matters is run: the model never executes anything. It emits a request, and the harness decides. That is why the chokepoint can exist at all (Chapter 16).

2.2How tool calling works

Generic Function or tool calling is a convention between harness and model provider. The harness sends tool definitions (a name, a description and a JSON Schema for the arguments) with each request; the model, trained to use them, returns a structured request naming a tool and its arguments instead of, or as well as, text; the harness executes it and returns the result in a message tied to the call's id. Three consequences follow:

  • The description is part of the prompt. Tool names and descriptions steer the model as much as the system prompt does, which is why a changed tool description from an MCP server is an attack (Chapter 5).
  • Arguments are model output. They can be malformed, out of range or adversarial. Validate them against the schema and then against policy, never trust them because they parsed.
  • Results are model input. Whatever the tool returns enters the context and can steer the next step. Fence it (Chapter 20).

Your build ARB's gateway, which serves tools to out-of-process hosts, adds semantics the in-process path gets for free: it only executes calls the model actually issued, serially and in order, and they expire (D63 items 7 and 24). The gateway is the only component that knows what the model asked for, so it owns those rules, and a host that rewrites the model's arguments or runs calls concurrently is an escalation, never something the gateway relaxes to accommodate.

2.3Designing tools

Generic Anthropic's guidance on writing tools for agents, and the source-code study of harnesses in Chapter 1, converge on a few rules that also make tools easier to govern:

  • Few, high-signal tools. A tool per meaningful operation, not per API endpoint. Fewer tools mean fewer descriptions to steer the model wrongly and fewer policy rules to write.
  • Separate reads from writes. A tool that both reads and writes cannot be given a clean action class; split it so tiering and policy can treat them differently.
  • Narrow, typed arguments. An order id and an amount, not a free-text "instruction". ARB's issue_refund(order_id, amount, reason) is a deliberately narrow contract; GAP-17 showed the cost of a field the contract lacked.
  • Return structure, not prose. Structured results can be classified for evidence (D21) and checked by an output contract (CTL-0010).
  • Make tools idempotent where they write, or give the harness an idempotency key (CTL-0006).

pm-agent pm-agent took tool design to its logical end for effects: the model does not call write tools at all; it proposes typed actions from a closed union, and the system turns approved actions into tool calls (ADR-0005). Its contracts are Pydantic models that carry planning-facing strings rather than domain enums, so the wire format does not couple to the domain model at the MCP boundary (D-PM-P0-d).

2.4Refusals the model can read

Your build When the PEP refuses a call, there are two audiences, and D19 gave each its own shape. Code that calls a tool directly gets an exception (PolicyDenied), so a programmatic caller cannot ignore a refusal. The model gets a tool result: {"error": "policy_denied", "control_id", "reason", "guidance"}, produced by a model-facing wrapper around the chokepoint. The reason is practical: an exception thrown through the framework's tool boundary ends the turn, so the effect is refused but the customer hears nothing, which is worse as a product and worse as an audit story than a refusal the agent can explain. The wrapper lives in enforcement/, so agent code is unchanged.

Gotcha

A model that reads a refusal may try again with different arguments: split the refund, change the reason, try another tool. That is fine only because the refusal is enforced on every call, not remembered by the model. Never rely on "the model was told no".

2.5Structured outputs

Generic There are three levels of asking a model for structured output, with different guarantees:

LevelHowGuarantee
Prompted"Reply in JSON with fields…"None
JSON modeThe provider guarantees syntactically valid JSONParses; any shape
Schema-constrainedThe provider constrains decoding to a JSON Schema (grammar-constrained sampling: tokens that would violate the schema are masked)Matches the schema's syntax; content still unverified

Even the strongest level constrains form, not truth: a schema can require a citations array; it cannot require that the citations exist. And constrained decoding has an interaction worth knowing: a server that enforces a JSON grammar on every reply makes tool calls impossible, because a tool call is a different shape.

Your build ARB's E5.1 (D71) met both points. Live, 14 of 26 Vertex answers were not in the typed shape, so the fixed refusal went out. The fix asks the provider for the shape (on Vertex, a JSON response type with a response schema; on the model gateway, a JSON-schema response format), but only on the final answer turn and only for bindings that combine structured output with function calling; the local server's pin is left alone because its grammar would block tool calls. The module states the principle in its first paragraph: this is a request to the model, never trusted. The contract parser is unchanged and remains the enforcement.

2.6The typed answer contract

Your build CTL-0026 changes what an answer is, which is a stronger move than checking answers. A user-facing answer is exactly one of two things: the typed shape {"answer": "...", "citations": ["..."]} with at least one citation, every citation an id this turn actually retrieved or read; or a fixed refusal, verbatim (including the plane's own fixed refusals for budget and inventory). Anything else (free text, no citation, an extra key, a citation that is not an id) is rejected and the fixed refusal is delivered. Nothing is repaired or guessed; one Markdown JSON fence is tolerated because models emit it unprompted and it changes nothing. A monotone support classifier may then hold an answer whose cited passage does not support it, but can never deliver one the parser rejected.

The reason for the design is a residual the earlier citation check could not close (RESID-03): an answer that states policy without citing anything slipped past a check that only inspected the citations it could see. Making "uncited prose" impossible as an answer shape closes it by construction.

2.7Shape slips and coercion

pm-agent Small local models slip shapes often. In pm-agent's first live run a 7B model returned a field as a list where a string was expected, which crashed the intent parser and aborted the run. The fix (D-PM-P1-h) coerces every model-supplied JSON field so a slip degrades to the deterministic fallback instead of aborting, and, more importantly, grounds identifiers in the request: the model's project or issue key is trusted only if it appears in the request, otherwise the request's own key wins. The live model had emitted a fixture key instead of the real one. Coercion keeps the run alive; grounding keeps it honest.

There is a tension with ARB's "nothing is repaired" rule, and it resolves cleanly: coerce internal planning fields where a fallback exists and the result is checked downstream; never repair what is delivered to a user or executed as an effect.

2.8Stopping the loop

Generic A loop with no bound is a cost and safety incident waiting for a model that never stops calling tools, or an injected "keep going". Bounds belong in the harness, enforced, not in the prompt:

  • A cap on model calls per turn (ARB: max_model_calls_per_turn: 8, part of CTL-0020).
  • Token and cost budgets per agent and per principal, with an unreported usage charged at the ceiling rather than as zero (make demo-budget).
  • A wall-clock timeout per turn and per run, and a cancel that actually stops effects (Chapter 19).
  • Verify-on-stop: before accepting "done", check the stop condition deterministically (tests pass, the typed answer parses), a pattern the harness study found in several production harnesses.
