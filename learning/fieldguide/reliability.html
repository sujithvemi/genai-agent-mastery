PART V · CHAPTER 29

Reliability for LLM systems

Agents depend on a shared, rate-limited, slow and occasionally wrong component, the model, and on tools whose effects cannot always be undone. The classic stability patterns (timeouts, retries, circuit breakers, bulkheads, load shedding) all apply, with one twist that changes everything: a retry can repeat an effect. This chapter adapts the patterns to agents and decides, control by control, whether failure should close or open.

29.1Why agents fail differently

  • The model is a shared, quota-limited dependency with long, variable latency; 429s are normal weather on shared capacity (Chapter 9).
  • Outputs can be wrong without erroring: a malformed tool call, an untyped answer, a fabricated id. Validation failures are reliability events.
  • Runs are long and multi-step, so partial failure is the common case.
  • Effects are real, so the usual reflex (retry) is dangerous.
  • Loops can run away: a model that keeps calling tools, or two agents that keep asking each other.

29.2Timeouts

Generic Every remote call gets a timeout, and the budgets nest: the turn's deadline is shorter than the run's, each model call's is shorter than the turn's remaining budget, each tool call's shorter still. Without timeouts, slow dependencies exhaust threads and connections and the failure spreads (Nygard's "integration points" are the first stability antipattern). The first prediction question: a timeout tells you only that you stopped waiting. The effect may have happened, may not, or may happen later. That is why effectful tools need idempotency keys and a way to query outcome by key.

29.3Retries that respect effects

Generic Retry only what is safe to retry:

CallRetry?How
Model call (no effect)Yes, on 429, 503 and timeoutsExponential back-off with jitter, a retry budget, honour Retry-After
Read toolYesSame
Write tool with idempotency keyYes, with the same keyTarget de-duplicates
Write tool without idempotencyNoQuery outcome; reconcile; escalate
Whole turn after an effectNoAbort and resume from the checkpoint after the effect

Reference build D71's ruling is the worked example: retry a whole turn only on 429 or RESOURCE_EXHAUSTED and "only if no effectful tool call completed in that attempt", from a fresh enforcement plane, at most three attempts with 120, 240 and 480 second back-off and ten retries per measurement, recording the full error body; "a 429 after an effectful call aborts". The retry is keyed on the error class, never on the outcome, so it cannot be used to fish for a different decision (Chapter 9). ARB's CTL-0006 requires idempotency on writes for the same reason.

Retries also need a budget: if every layer retries three times, five layers produce 243 attempts. Limit retries per request and per dependency, and prefer retrying at one layer.

29.4Circuit breakers and bulkheads

  • Circuit breakers stop calling a failing dependency for a while, so callers fail fast instead of piling up; half-open probes test recovery. Use them on model providers (per model and region), on tools and on gateways. Azure API Management's breaker, for example, honours the back end's Retry-After to decide how long to stay open.
  • Bulkheads isolate resources so one failure cannot sink everything: separate connection pools and concurrency limits per tenant, per model provider and per tool; separate worker pools for interactive and background agents.

29.5Rate limits, back-pressure and load shedding

Generic Protect the system and fair shares within it: token-bucket rate limits per tenant at the gateway; quotas in tokens, not requests (Chapter 33); back-pressure from workers to the queue (stop pulling when saturated); and load shedding when overloaded, rejecting low-priority work early with 429 and Retry-After rather than accepting everything and timing out later. Prioritise interactive over background work, and approvals and cancellations above all, because they unblock or stop other work.

pm-agent pm-agent's CTL-0007 caps a run's fan-out of issue reads and its token and cost use per principal and window, with a time-boxed, approved exception path. A planning agent asked about a huge epic should throttle, not exhaust the quota for every tenant.

29.6Graceful degradation

Generic Decide in advance what the agent does when part of it fails:

  • Fallback model: a declared, priced and gated alternative pin, never a silent vendor fallback (Chapter 10).
  • Read-only mode: answer and propose, but take no actions, when the enforcement path or a write dependency is unhealthy.
  • Queue for later: accept the request, finish when the dependency recovers, and say so.
  • Hand to a human with the context gathered so far.

The third prediction question has a control in pm-agent: CTL-0022, degraded-context disclosure, requires that "partial or failed retrieval is disclosed in the output, not hidden"; its test reads a partial epic and checks that the plan names the gap. An agent that silently plans from incomplete data is less reliable than one that fails.

Write these down per control (the catalog's exception_path and detection window are the place), and test each failure path; a fail-closed claim that has never been exercised is an assumption (Chapter 24).

29.8Stuck runs and runaway loops

  • Bounded loops: per-turn model-call caps, step limits and token budgets end runaway reasoning (ARB's CTL-0020 per-turn call cap; its golden case for a runaway loop must stay refused after any recalibration).
  • Cross-agent ping-pong is bounded per agent turn in ARB, not end to end, a named residual (D58); a hop count or deadline carried in the provenance envelope closes it.
  • Watchdogs find runs with no progress past a deadline and cancel them safely (pm-agent's CTL-0023: cancel leaves consistent state and an evidence event).
  • Dead-letter queues catch messages that keep failing, with alerts and an owner.

29.9Testing failure

Inject the failures the design claims to handle: provider 429s and timeouts, tool timeouts after the effect, evidence-store outages, a ledger that is unreachable, a classifier that times out. Fakes behind seams make this cheap (Chapter 7); game days in staging test the runbooks and the people.

Throttling looks different on each provider: Vertex AI returns 429 with RESOURCE_EXHAUSTED, Bedrock raises a ThrottlingException, and Azure OpenAI returns 429 with retry-after headers. A retry policy written for one will misclassify another, so test classification against each provider you route to, and confirm which quotas are per region, per model or per project.

29.12In the room

In the room
  • "What happens when the model provider is down?" "The agent fails fast rather than hanging, sends work to a second region or model where we have agreed one, and degrades to 'queued for later' or 'hand to a person'. It never skips a control to stay up."
  • "Could a retry send the same email twice?" "Only something with no effect is retried freely. A step that changes something is retried only with a key the other system uses to ignore duplicates; otherwise we check what happened and ask a person."
