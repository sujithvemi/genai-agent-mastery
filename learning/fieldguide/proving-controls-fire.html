PART IV · CHAPTER 24

Proving controls fire

A control is a claim until something tries to break it. Proof has three layers: a conformance check per control, run against the real enforcement plane on this build; a falsifier that shows the check would fail if the mechanism were gone; and a red team that assumes the model is fully hostile and hunts for any input where the enforced decision changes.

24.1The standard

Your build D29 set the standard the red team works to, and it is worth adopting word for word: a control holds if, under adversarial input, the enforced decision is unchanged. The money still does not move, the evidence still records, a cited article still had to be retrieved, whatever the model says or does. A red-team success is a reproducing test that turns red; the fix is a policy or middleware change that turns it green while the parity and conformance suites stay green.

D29 also drew the boundary that keeps a red team useful: model quality is out of scope for a governance finding. A wrong answer that was refused is a model bug, not a control failure. A prompt that makes the model rude is not a finding; a prompt that makes the refund execute is. Without that line, red-teaming drifts into theatre about what the model said, and stops measuring whether enforcement holds, which is the only claim a governance build makes.

Three failure classes to attack, from D29: a control that fires on the happy path but can be bypassed by phrasing, encoding or injection; a decision that rests on facts the model supplied instead of facts derived from trusted state; and a record or approval produced without the authority it claims (forgery, self-approval, replay).

24.2Conformance per control

Your build Chapter 15 described the conformance report as the gate's input. Here are the properties that make it proof rather than paperwork:

  • It runs against the real plane, not a unit-tested rule in isolation (D22). A conformance check for the refund ceiling drives a refund above the cap through the actual chokepoint and asserts the refusal, the control id and the evidence record.
  • It is driven by the derived required set (D27), so a required control with no check appears as a row reading check_ran: false, not as an absence.
  • Every row points at chained evidence agreeing with it, so the report cannot claim more than the run recorded.
  • It is generated each run and never committed, because a committed report is a table someone wrote.
  • It is positive per agent (D39). Each agent's required controls must each be shown firing for that agent. When the second archetype onboarded, four required controls could not fire for it, because their bindings had been written behind a write-only guard. Fleet-level conformance would have hidden that; per-agent conformance exposed it.

24.3Falsifiers

Generic A passing test proves nothing unless it could have failed. A falsifier is the deliberate act of removing or disabling the mechanism under test and confirming the test now fails. It is the cheapest high-value practice in this book.

Your build The builds use falsifiers in several forms:

  • Unbind a control, watch the gate block. make demo-gate-flip: the gate as designed (blocked), the live gate (allowed), one control unbound in a copy (blocked again). Fail-closed is proven, not asserted.
  • Disable a mechanism, run the full suite (D56). Three mechanisms survived a full 912-test run with their mechanism disabled, including the golden scorer. D55's crosswalk rule now requires, for every row claiming a control or mechanism, a test that fails when it is removed; if none exists, the builder escalates rather than writing a vacuous one.
  • Attribute refusals to the mechanism (pm-agent D-PM-P4-n). Removing the approver-versus-executor comparison passed every test, because a different rule refused the same probes under the same control id. The fix made the conformance rows require refusal by the comparison itself, identified by reason, and added a gate that removes only that comparison.
  • Falsifier switches in the product. pm-agent's output guard can be disabled by an explicit injectable (Guardrail(output_guard=None), and a CLI flag labelled "FALSIFIER ONLY"), so "disable the guard and the steer is obeyed again" is runnable offline and live (D-PM-P5-c).
  • Reachability (test_no_dead_policy.py) and the import firewall are falsifiers for whole classes: a rule nothing can reach, or a vendor import that leaks past a seam, turns a test red.

24.4Vacuity, made explicit

Your build Some required controls cannot be triggered by some agents. Separation of duties holds for a read-only agent because it has nothing to approve. D39 accepted that, with a rule worth adopting everywhere: a vacuously satisfied control must say so, and its precondition must be tested. The advisor's conformance row records "no approval-requiring write in this agent's tool surface, so separation of duties is not applicable, satisfied by shape", and it asserts that precondition. The day someone adds a write tool to the advisor, the vacuity assertion fails and forces a re-derivation, instead of a dormant invariant quietly becoming load-bearing without anyone noticing.

24.5Hostile models

Generic The red team's most useful assumption is that the model is fully adversarial: it will call any tool, with any arguments, say anything, and obey any injected instruction. If the controls hold under that model, they hold under any real one. This is cheaper than it sounds, because you do not need a jailbroken frontier model; you need a scripted fake that behaves like one.

pm-agent pm-agent's harness has scripted adversaries: a model that obeys whatever a hostile comment says (it extracts the comment body from the plan prompt and echoes it), and a model that fabricates citations to issues that do not exist. ADR-0005's proof replaces the planner entirely with a hostile model emitting arbitrary actions from the attack corpus, and requires zero attacker-originated executed effects. Your build ARB extends the same standard to classifiers (D52): the red team includes a fully compromised classifier, and the control holds if no decision is more permissive with it than without it (test_s10_classifier_compromise.py).

24.6A red-team programme

Your build ARB's red-team corpus lives in tests/redteam/, organised by attack class, with a harness, invariants and a report. On 2026-10-20 it held 20 files and about 170 test functions:

SuiteAttacks
S2 guardrail evasionEncodings, homoglyphs, format characters, fence forgery
S3 trust boundaryDecisions resting on model-supplied facts; preconditions bypassed by phrasing
S4 evidence integrityEdits, truncation, refused writes, unrecorded effects (RT-11)
S5 cross-agentSpoofed senders, undeclared edges, authority smuggled in messages, lost provenance
S6 model planeRunaway loops against budgets, impostor models against the pin
S7 sign-off and inventoryStale or edited sign-offs, unregistered agents, the pre-deployment escape hatch

S11 evolution passRe-attacks after the evolution phases

The P5 verdict (D30) is the template for reporting one: 41 attacks; 27 held on first contact; 14 exposed a finding, 11 distinct; all closed by an authored policy or middleware change, none by changing a tool contract or weakening fail-closed. And the sentence that matters more than the ratio: one finding moved real money. RT-11 found that an evidence sink which accepted the decision record and refused the action record let a fully approved refund execute unrecorded, while the audit still reported VERIFIED. That a red team found a money-mover on an "enforced, auditable" build is the whole point of having one.

D30 also turned findings into standing principles, which is how a red team improves a programme rather than a build: a probabilistic detector is only ever a second tripwire; identity is resolved, not compared; a rule that cannot fire is not a control; a detection window must be declared, not discovered; and an anti-abuse control that miscounts must miscount toward less budget and fewer writes. Residuals that need infrastructure a local build cannot provide are named, bounded and scheduled, not hidden.

The demonstration to show anyone is make demo-redteam: it replays named attacks, including RT-11, and judges each from its evidence.

24.7Independent verification

Generic The builder of a control is the person least likely to find the input that defeats it, because they designed against the attacks they imagined. Independent verification is a structural answer, not a matter of trust.

pm-agent pm-agent runs a separate validation thread (T3) for every stage gate. It receives the stage's acceptance criteria and the code, not the builder's reasoning, writes a report with findings and a verdict (PASS, CONDITIONAL PASS, FAIL), and the owner's thread (T1) rules on each finding. Many of the decisions cited in this book came from T3 findings: the off-PEP registry call, the SoD attribution gap, the over-redacting fence, the URL fragments surviving redaction, the provenance lane that depended on the detector. A build that only grades itself would have shipped every one of them.

24.8Posture as a release criterion

Generic Combine the ladder from Chapter 14 with this chapter's proofs and you get a release criterion that is hard to argue with: for each required control, state its rung and the artifact that earns it.

24.11In the room

In the room
  • "Our controls are tested." Ask: would any test fail if you removed the control? Has anyone outside the team tried to break it? Does the test run against the deployed configuration?
  • "What did your red team find?" Lead with the money-mover: "The most important finding was one where a refund could execute without its record. We fixed it by reversing any effect whose record cannot be written, and that attack is now a permanent test."
