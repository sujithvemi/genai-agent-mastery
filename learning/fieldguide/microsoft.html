PART VII · CHAPTER 43

Microsoft: Foundry, Copilot Studio and Agent 365

Most enterprises already run Microsoft 365, so most will have Microsoft agents whether or not anyone planned them: makers build them in Copilot Studio, developers in Foundry, and vendors ship them into Teams. Microsoft's distinctive strength is estate governance: an identity for every agent in Entra, a tenant-wide registry in Agent 365, and the Purview and Defender machinery that already governs people and documents. This chapter covers the four planes, the two control planes that confuse clients, and how your catalog maps onto them.

43.2Foundry: the pro-code platform

  • Foundry Models: OpenAI models, Microsoft's own MAI models, Anthropic's Claude, open models and partner hosts (Fireworks AI on Foundry is GA). Deployment types decide where data is processed and how capacity is bought: global, data zone or regional; standard (pay per token), provisioned (PTU) or batch; with priority and flex processing at request level (Chapter 9).
  • Foundry Agent Service: hosted agents with sandboxed sessions, state and a file system, for any framework, through the Responses API and an Invocations protocol (GA expected July 2026 Verify); Routines for scheduled agents; Toolboxes, a single managed endpoint for tools, skills and MCP clients with governance; a skills catalogue; tool search; memory (procedural, user and session; preview); voice agents; publishing to Teams and Microsoft 365 Copilot.
  • Microsoft Agent Framework 1.0 (April 2026; .NET and Python): agents, graph workflows with checkpointing, middleware, MCP and A2A; the agent harness with skills, memory and middleware is stable, and it integrates the GitHub Copilot SDK and Claude Agent SDK (Chapter 35).
  • Foundry IQ: managed knowledge bases with agentic retrieval (GA), part of a wider "Microsoft IQ" layer.
  • Quality and safety: evaluations for any framework (preview), a rubric evaluator, the AI Red Teaming Agent and scheduled red-team scans, guided guardrail setup (PII filters, jailbreak protection, task adherence), and Azure AI Content Safety with Prompt Shields Verify. Agent Optimizer was announced for preview.

43.3Copilot Studio: the maker platform

Generic Copilot Studio is where agent sprawl begins in most Microsoft estates. Its governance is the Power Platform's:

  • Environments are the unit of control; Managed Environments add sharing limits, environment-group rules and network scoping. A common pattern is to detect agents made in the default environment and steer makers to a governed one.
  • Data policies govern connectors, knowledge sources and actions; enforcement for Copilot Studio is on by default and per-agent exemptions are no longer supported. Advanced connector policies (preview) use an allow-list model that can target MCP servers. Custom connectors are the route to custom MCP servers and external agents, so their endpoints need allow-lists.
  • Credentials. Connectors can run with the maker's credentials or the end user's. The first prediction question: with maker credentials, every user of the agent sees what the maker can see. That is the most common source of unintended data access, and an admin setting can restrict agents to end-user credentials (which breaks agents triggered without a live user).
  • Identity. Since May 2026 every new Copilot Studio agent automatically gets an Entra Agent ID, a child of a Copilot Studio agent-identity blueprint; existing app-registration identities are being migrated. Connector permissions appear as API permissions on the agent identity, and Conditional Access can target them (device, network, risk) before a token is issued; the connector runtime re-validates against data policies so the scopes cannot bypass them.

The third prediction question: agent-level identity turns makers' agents into governable principals. Identity teams can see what each agent can call, apply Conditional Access to its connector access, and run access reviews and sponsor workflows, instead of governing a tangle of maker accounts and app registrations.

The second prediction question: both, for different questions. The CISO's view of "every agent with access to our data, who sponsors it, and what it can reach" is Agent 365 and Entra; "is this engineered agent's quality and guardrail posture within policy" is Foundry Control Plane. Neither sees agents on Google or AWS unless they are registered into it, so a registry of record remains yours (Chapter 45).

43.6API Management as the AI gateway

Generic Azure API Management's AI gateway features (Microsoft Learn, updated May 2026) are a mature model and tool gateway:

  • Token limits per consumer, per minute or as quotas over an hour to a year, keyed on subscription, IP or any expression; prompt tokens are pre-calculated so requests over the limit never reach the model. This is a building block for your CTL-0020 ledger, keyed to the resolved principal.
  • Token metrics with custom dimensions, and prompt and completion logging for billing and audit.
  • Semantic caching backed by Redis (Chapter 10 for its risks).
  • Load balancing (round robin, weighted, priority so provisioned capacity is used first, session-aware) and a circuit breaker that honours the back end's Retry-After.
  • Content safety policy calling Azure AI Content Safety; managed identities instead of keys.
  • MCP: expose REST APIs as MCP servers, govern remote MCP servers, secure them with OAuth, register them in API Center; A2A agent APIs can be imported.
  • Previews: a unified OpenAI-compatible model API across back ends, and an AI gateway inside Foundry.

43.7The open trust stack

Generic Microsoft's open-source governance components, two of them announced at Build 2026 (2 June 2026) as an "open trust stack":

  • Agent Governance Toolkit (AGT), open-sourced on 2 April 2026, the open-source toolkit your build evaluated: ARB ran a parity spike and decided not to adopt it, with a revisit trigger (D63). Its model, gaps and fit are the subject of Chapter 47.
  • Agent Control Specification (ACS), part of AGT: an open specification for placing controls at five checkpoints in an agent workflow (input, model, state, tool execution, output), written as policy YAML and described by a partner as "a portable, declarative contract enforced outside the model". Its controls may include classifiers and LLM judges, so apply your D52 rule to each.
  • ASSERT: an open-source evaluation framework that turns written policies into generated test scenarios (Chapter 39).

ACS's five checkpoints line up closely with your enforcement points: input screening, model-call controls (budget, pin), state (memory and control state), tool execution (the chokepoint) and output (the answer contract). That makes it a plausible exchange format for a cross-platform toolkit (Capstone B), worth tracking.

43.10A reference landing

Assumption For a client on Microsoft 365 and Azure:

  1. Agent 365 and Entra Agent ID first: inventory everything, assign sponsors, apply Conditional Access templates, block maker credentials where possible.
  2. Copilot Studio in Managed Environments with data policies, sharing limits and an approved connector and MCP allow-list.
  3. Pro-code agents on Foundry Agent Service or Azure Container Apps, behind API Management for models and tools, with your PDP and PIP for business rules.
  4. Purview for audit, DSPM and DLP; Defender for threat detection; your evidence plane for decision evidence.
  5. Foundry Control Plane for guardrail policy assignment, evaluation and red teaming of engineered agents.

43.11In the room

In the room
  • "We have hundreds of Copilot Studio agents. Where do we start?" "Inventory and identity: Agent 365 and Entra Agent ID give every agent an owner, a sponsor and visible permissions. Then remove maker credentials from agents that serve other people."
  • "Is Agent 365 our agent governance?" "It is the estate's identity and inventory layer, and a strong one. Business rules on actions, decision evidence and release gates for engineered agents still sit in your platform layer."
