PART VI · CHAPTER 38

Versioning, registries and release management

An agent's behaviour is set by many things that version separately: code, prompts, tool contracts, model pin, policy, parameters, retrieval index and evaluation set. Releasing an agent safely means treating them as one release unit, binding approval to exactly that unit, recording it in a registry, and shipping it progressively with a rollback plan that admits what cannot be undone. Your reference build has the strongest binding mechanism in this book, and also, as this chapter finds, a gap in what it binds.

38.1What is a version of an agent?

Generic The first prediction question usually produces a longer list than people expect:

Every layer can change behaviour. A versioning scheme that covers only code (the git commit) misses the prompt service, the provider's model alias, the policy repository and the retrieval index. The release unit is the set of all of them, identified by one content digest computed from their canonical forms.

38.2Binding approval to a version

Reference build CTL-0022 is the mechanism to study. Its objective: "An accountable deployment sign-off covers exactly the configuration the human approved. Any change to what was approved … makes the sign-off stale, and a stale sign-off is no sign-off." D59 built it with four properties worth copying:

  • Canonical inputs. The manifest is hashed as the gate parsed it, so a comment edit is not a change and an in-memory manifest cannot hide behind its file; files are hashed with line endings normalised, so Windows and Linux agree.
  • Recomputable. The record lists every input as <kind> <ref> sha256:…, and an independent function rebuilds the digest from that list alone; a test asserts the two agree.
  • Four distinct failures: no sign-off; a sign-off naming no digest; a record whose digest disagrees with its own inputs (tampered); and a stale record, reported with a diff of what changed (+ CTL-x, ~ model pin: a -> b, ~ params.yaml).
  • Signed. Since E4-S3 the record is Ed25519-signed and verified against a trust list of public keys.

D61 extended the digest to the agent's own MCP tool pins, on the reasoning that "a tool's description and schema are capability configuration, so a re-pin re-gates the agent". That reasoning reaches further than the digest does today.

Finding F-06 · what the sign-off does not cover

The digest's inputs are exactly the manifest, the required controls and their catalog text, the model pin, params.yaml and the agent's MCP pins. Four behaviour-setting inputs are outside it: the agent's system instruction (INSTRUCTION in src/aicoe/agents/<agent>.py), the in-process tool definitions, the policy bundle source (governance/policies/rego/tool_call.rego and its Cedar twin) and the guardrail patterns (guardrails.yaml). A loosening edit to the Rego refund rule that keeps the test suite green would leave the CRITICAL agent's sign-off valid. The gap is in the specification CTL-0022 transcribes, not in the code, and the fairness digest already includes the instruction text, so the two digests disagree on scope. Suggested fix and severity are in Appendix G.

Generic The general lesson: when you bind approval to a digest, list the release-unit layers explicitly and justify every exclusion. A prompt in a prompt-management service, a policy in a separate repository, or a model behind an alias are all ways a signed configuration can change without the signature noticing.

38.3Version identifiers

  • Content digests identify exactly what ran, for machines and evidence. Every evidence record should carry the release digest.
  • Semantic versions communicate intent to people. A workable rule for agents: major when the agent's effects, data classes or autonomy change (which will usually change its tier), minor for behaviour changes (prompt, model, tools), patch for fixes that should not change measured behaviour.
  • Interface versions for anything other systems call: the run API (Chapter 25) and the A2A agent card, whose changes affect callers.
  • Immutability. A published version never changes; a fix is a new version. Platform revisions (GEAP Agent Runtime revisions, Foundry agent versions, AgentCore configuration bundles) follow this rule Verify.

38.4Registries

Generic A registry answers: which agents exist, who owns them, what they can do, which version is where, and whether each is allowed to run. Every platform now has one (GEAP Agent Registry; AWS Agent Registry; the Agent 365 registry; Foundry Control Plane's asset inventory; ServiceNow AI Control Tower's discovery). An enterprise usually needs a registry of record above them, fed by reconciliation, because no platform registry sees the others (Chapter 45).

Reference build ARB's CTL-0023 makes the registry an enforcement input, not documentation. The registry file is generated by running conformance and the gate to a fixpoint, and three runtime enforcement points (chokepoint, tool gateway, model gateway) refuse a subject that is not registered and DEPLOYABLE at its current digest. A reconciliation command compares the registry with exports shaped like other platforms' listings and flags orphans and agents running on a maker's personal credentials. The plane-bypass tests ensure no production code path builds a plane without this check (Chapter 7).

38.5Environments and promotion

Generic Dev, test, staging and production for agents differ from services in what each uses: fake models and fixture systems in dev and CI; live models against synthetic data in test; production-like integrations with synthetic or masked data in staging. Promotion between them should be a gate decision, not a manual step.

Reference build docs/operating/GATE_AS_PROMOTION.md states the rule. make gov-fleet runs conformance against the live enforcement plane for every manifest and then the gate; it is a required CI check, so a BLOCKED agent cannot merge. The conformance report is "generated, never authored" and is not committed, because "the entire premise of the gate is that it must not believe a table a human could edit". DEPLOYABLE therefore means "the controls were exercised on this machine, just now".

The third prediction question: usually not. Agent outcomes vary between runs of the same input, and a few-point difference in task success needs hundreds to thousands of conversations to distinguish from noise. ARB's fairness work is the cautionary example: a criterion that cannot separate noise from signal must be held, not passed (D74).

38.7Rollback and what cannot roll back

Generic Rolling back the release unit restores code, prompts, pins and policy. It does not restore the world. The second prediction question's answer:

  • Effects already taken: refunds issued, tickets updated, messages sent. These need compensating actions, which is why reversible effects carry a reversal path and evidence of what was done (Chapter 22).
  • Memory written by the bad version: facts it extracted may be wrong. Tag memories with the version that wrote them so they can be found and purged.
  • Sessions in flight: decide whether they finish on the old version or are cancelled safely (Chapter 19).
  • Retired model versions: if the provider has withdrawn the previous model, the pin cannot roll back. Keep a declared, priced and gated fallback pin, and test it before you need it (Chapter 10).

38.11In the room

In the room
  • "How do you know what version was running when this happened?" "Every decision record carries the digest of the release unit: code, prompts, tools, model pin and policy. We can recompute it from the repository."
  • "Can we update the prompt without a release?" "You can make it fast, but not invisible: the prompt is part of the release unit and of the approval. A prompt service that bypasses that is a bypass of your sign-off."
